CAP定理
03
CAP 定理（Brewer's Theorem）：由 UC Berkeley 的 Eric Brewer 于 2000 年提出，2002 年由 Gilbert & Lynch 正
式证明。
核心结论：分布式系统中，一致性（C）、可用性（A）、分区容错（P）三者最多同时满足两个。
💡 类比：餐厅同时做到"菜品新鲜（C）、上菜飞快（A）、食材断货也不停业（P）"——现实中三者很难兼顾，总要取
舍。
特性
英文
含义
一致性 (C)
Consistency
所有节点同一时刻看到相同数据。
例：银行转账后，所有查询立即看到新余额
可用性 (A)
Availability
每个请求都收到响应（不保证是最新数据）。
例：系统总能回答，即使答案可能稍旧
分区容错 (P)
Partition Tolerance
节点间通信故障时系统仍可运行。
例：机房网线断了，各节点独立继续服务

🤔 为什么只能三选二？  网络故障（P）在真实环境中无法避免。分区发生时，节点 A 和节点 B 断联——此时只有两

CAP定理的现实理解
误解
纠正
CAP 三选二
不是静态"三选二"。P（网络分区）几乎不可避免，
实际是在分区发生时选 C 还是选 A
AP 系统完全不一致
AP 系统提供的是最终一致性，不是永远不一致。
例：朋友圈点赞数会在几秒内同步到所有人
CP 系统完全不可用
CP 系统只在分区期间拒绝服务，分区恢复后立刻恢复。
例：ZooKeeper 短暂不可用后自动重新选主恢复
📖 延伸：PACELC 模型（Daniel Abadi 提出）：CAP 只关注"出故障时怎么选"。系统正常
运行时同样面临延迟（L）vs 一致性（C）的权衡——是等所有副本同步后再响应（一致但
慢），还是立即返回（快但可能读到旧数据）？

BASE理论
07
BASE 是对 CAP 中 AP 路线的进一步阐述，是大型互联网系统（淘宝、微信、亚马逊）常用的设计理念。 核心思想：放
弃强一致性，换取高可用和高性能。
缩写
全称
含义
BA
Basically Available
允许部分功能降级或响应延迟，但系统整体依然可用。
例：淘宝大促时搜索变慢、但下单功能正常
S
Soft State
数据不需要时刻一致，允许副本间短暂不同步。
例：微博点赞数在各数据中心可短暂不一致

Consistent

例：DNS 更新后，全球各地 IP 解析逐步同步到新值

一致性模型
10
🟥 线性一致性（Linearizability）——最强的一致性
系统行为就像只有一个副本：写入完成后，所有后续读操作必须返回新值。
代价：每次写入需等所有副本确认，延迟高。典型系统：etcd、ZooKeeper

时间轴示例（线性一致性）：
Client A: Write(x=1) ────── 完成
Client B:           Read(x) → 必须返回 1（不能返回旧值 0）
🟢 最终一致性（Eventual Consistency）——最弱的一致性
允许短暂不一致，但停止写入后所有副本最终会收敛到相同值。
优势：低延迟、高可用。典型系统：DynamoDB、Cassandra、DNS 解析
时间轴示例（最终一致性）：
Write(x=1) → 副本 A: x=1（立即写入）
              副本 B: x=0（暂未同步）  副本 C: x=0（暂未同步）
  一段时间后 → 副本 A/B/C 全部: x=1（最终一致 ✔）

数据分片（Sharding）：将大规模数据集分割成多个子集并分布存储在不同节点，每个节点只负责部分数据的
读写，实现水平扩展、突破单机瓶颈。
💾  容量瓶颈
存储上限：单机磁盘有限，无法
应对 PB 级数据
📌 微信图片存储 > 100 PB，单机
根本装不下
⚡  性能瓶颈
读写 QPS 存在物理上限，单机无
法撑住高并发
📌 淘宝双11峰值写入 > 1亿次/秒，
远超单机极限
⚠  可用性风险
单点故障风险高，一台宕机即全
库不可用
📌 单库 MySQL 故障 → 整个业务
停摆
■  两大分片策略
🔢 哈希分片（Hash Sharding）
按 Key 的哈希值对节点数取模，决定数据存入哪个节点
✅ 优点：分布均匀，负载均衡好
⚠ 缺点：节点数变化时大量数据需迁移（扩容代价高）
📌 代表：Redis Cluster（CRC16 % 16384）
📏 范围分片（Range Sharding）
按 Key 的值范围划分区间，同一范围的 Key 存入同一节点
✅ 优点：范围查询高效（顺序扫描）
⚠ 缺点：容易产生数据倾斜（热点节点）
📌 代表：HBase、BigTable、Google Spanner

■ 核心原理
对数据的 Key 计算哈希值，然后对节点数 N 取模，决定
数据存储在哪个节点：
node_id  =  hash(key)  %  N
例：hash("user:1001") % 3 = 2  →  存入 Node 2
✅ 主要优点
• 数据均匀分布各节点，有效实现负载均衡
• 写入压力分散，避免单节点热点
• 代表：Redis Cluster 用 CRC16(key) % 16384 分配 16384 个槽位
⚠ 致命缺点
节点数 N 变化时，几乎所有数据映射关系都改变，引
发大规模数据迁移：
• 3台 → 4台：hash(key)%3 变为 hash(key)%4
  约 75% 的数据需要重新迁移！
• 无法支持高效范围查询（需扫描所有节点）
💡 解决方案：使用一致性哈希（→ 下一页）
// 哈希分片核心公式
node_id = hash(key) % N
// 3节点示例
hash("user:1001") % 3 = 2  // → Node 2
hash("order:5523") % 3 = 0  // → Node 0
// Redis Cluster 实际使用
slot = CRC16(key) % 16384

15

实

华
·

■ 设计目标
解决传统哈希节点增减时大量数据迁移的问题：
• 3台→4台，传统哈希迁移约 75% 数据
• 一致性哈希只需迁移约 1/N ≈ 25% 数据
■ 核心原理（Hash Ring）
哈希空间组成虚拟圆环（0 ~ 2³²−1），节点和 Key 均映射
到环上。
• Key 顺时针找最近节点存入
• 类比：钟表盘——数据找顺时针方向最近的刻度（节点）
✅ 节点增减优势
删节点：只将该节点数据迁给顺时针下一节点
加节点：只将新节点覆盖区间的数据迁入
结论：扩/缩容只影响 1/N 的数据！
虚拟节点：每个物理节点映射多个虚拟节点，使分布更均匀
代表系统：Cassandra、DynamoDB、Riak
▲ 哈希环示例
Node A/B/C 均匀分布在环上，数据 key 顺时针
找最近节点存入。
典型系统：Cassandra、DynamoDB、Riak

虚拟节点（Virtual Nodes）
17
⚠ 一致性哈希的遗留问题：节点在哈希环上的落点是随机的，少量节点时分布容易不均，某个
节点承接了一大片区间，成为热点。
解法：虚拟节点（VNode）
每个物理节点在哈希环上注册多个"分身"，这些分身均匀散落在环的各处。数据照样顺时针找最
近的节点，只不过现在找到的是某个分身，实际由对应的物理节点处理。
钟表盘比喻：3台服务器，各放3个贴纸，9个贴纸均匀贴满表盘——每台服务器大约各管三分之一。
节点 A  →  A-1(hash=10)   A-2(hash=80)   A-3(hash=190)
节点 B  →  B-1(hash=40)   B-2(hash=120)  B-3(hash=230)
节点 C  →  C-1(hash=60)   C-2(hash=150)  C-3(hash=250)
虚拟节点越多，分布越均匀。实践中通常每个物理节点对应 100～200 个虚拟节点，
Cassandra、DynamoDB 均采用此方案。

范围分片（Range Sharding）
18
原理：按 Key 的值范围将数据划分到不同节点，
每个节点负责一段连续区间。查找数据时直接定位
到对应区间的节点，无需遍历。
示例（按用户名首字母分片）：
Node A: key ∈[A, G)  →  alice, ben, fan
Node B: key ∈[G, N)  →  han, kim, max
Node C: key ∈[N, Z]  →  nao, sam, zhang
热点问题与解法：
若 Z 开头有大量明星账号，Node C 成热点 → 可对
热点区间再细分，或引入二级哈希打散。
典型系统：HBase（RowKey 范围自动分区）、
Spanner、BigTable

分片策略对比总结
19
🔵 哈希分片（Hash Sharding）
• 公式：node = hash(key) % N
• ✅ 数据分布均匀，避免热点
• ⚠ 不支持范围查询；扩容需大量迁移
• 改进：一致性哈希 + 虚拟节点（迁移量降至 
1/N）
• 典型：Redis Cluster（16384槽）、
DynamoDB、Cassandra
🟣 范围分片（Range Sharding）
• 公式：按 Key 值区间分配节点
• ✅ 范围查询高效；有序存储；支持排序分页
• ⚠ 数据倾斜时产生热点；需维护分区元数据
• 典型：HBase（RowKey 自动分区）、
BigTable、Spanner

🎯 如何选择？
选哈希分片，当：
• 需要均匀分散写压力（如用户行为日志）
• 主要是点查（按 Key 精确查找），不做区间扫描
• 例：用户账户系统、缓存集群、消息队列
选范围分片，当：
• 业务依赖范围查询（如按时间段查日志）
• 数据有天然顺序、需要排序或分页
• 例：时序数据库、订单按日期分区、监控指标
💡 实践中两者常结合使用：先按业务维度哈希分片，
再在单片内按时间范围分区（二级分片）。

数据复制模式
21
为什么需要复制？
高可用：节点宕机时副本顶上，服务不中断
低延迟：将副本部署在离用户近的地域
读扩展：多副本分担读请求，大促时吞吐翻倍
三种复制模式
① 主从（Leader-Follower）：主库写，从库
只读。MySQL / PostgreSQL
② 多主（Multi-Leader）：多地域写入，需
解决写冲突。CouchDB
③ 无主（Leaderless）：任意节点可写，靠 
Quorum 保一致。DynamoDB

① 主从复制详解
写操作只发给主库，主库把变更日志（binlog）同步给
所有从库。从库延迟通常在毫秒级。
✅ 优点：实现简单，读扩展容易，主流 RDB 默认支持
⚠ 缺点：主库宕机需选举新主，写入期间短暂不可用
② 多主复制详解
多个数据中心各有主库，本地写入后跨中心同步。适合
多地域部署场景。
