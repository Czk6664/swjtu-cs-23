六、模块依赖关系与运行方法

这部分主要结合代码本身来说明整个 DES 程序是怎么拆分和组织的。因为实验里不是只写一个大函数，而是分成了几个文件来做，所以报告这里也就按文件顺着讲，这样比较容易对应到实际代码。程序的目录结构如下：

```text
des_lab/
├── des_tables.py
├── common.py
├── key_schedule.py
├── round_function.py
├── des_core.py
└── main.py
```

这几个文件里，`des_tables.py` 放标准表，`common.py` 放基础操作，`key_schedule.py` 生成子密钥，`round_function.py` 做轮函数，`des_core.py` 负责加密和解密，`main.py` 负责最后的调用和输出。这样拆开以后，调试的时候会方便很多，因为某一步出错了，基本上都能很快定位到对应文件。对我来说，这种结构还有一个好处，就是看代码时不用来回翻很远的地方，整个流程基本上是顺着文件顺序就能读下去的。

从整个程序的组织方式来看，最开始我先考虑的不是 DES 的每一个公式，而是先把程序结构理顺。因为如果所有逻辑都堆在一个文件里，后面再想检查哪一步出问题会很麻烦，所以一开始就决定把通用函数、标准表和核心流程拆开。这样虽然文件数量多了一点，但实际写起来更清楚，后面改代码也更方便。对于实验报告来说，这种写法也更适合按步骤说明，不会显得太乱，而且每一部分都能比较自然地和代码对应起来。

（1）`common.py`：基础数据表示和通用函数。

一开始我先处理的是数据格式问题。DES 里面大部分操作都要按位处理，所以程序里统一用了字符串形式的 0/1 序列，也就是把十六进制输入先转成二进制字符串，然后再做置换、异或、拆分这些操作。这样做的好处是，前后每一步都用同一种格式，不容易乱。比如说，某一步如果输出长度不对，马上就能看出来；如果换成整数或者列表来回转换，反而不容易发现问题。实际写代码的时候，我也更习惯直接看字符串形式的比特串，因为长度和内容都比较直观。

`common.py` 里写的也都是一些很基础但很常用的函数，比如十六进制转二进制、二进制转十六进制、按表置换、异或、拆分和循环左移。代码大概是这样的：

```python
def hex_to_bits(hex_str: str, width: int = 64) -> str:
    value = int(hex_str, 16)
    return f"{value:0{width}b}"

def bits_to_hex(bits: str, width: int = 16) -> str:
    value = int(bits, 2)
    return f"{value:0{width}X}"

def permute(bits: str, table: list[int]) -> str:
    return "".join(bits[i - 1] for i in table)

def xor_bits(a: str, b: str) -> str:
    return "".join("1" if x != y else "0" for x, y in zip(a, b))
```

这些函数看起来都不复杂，但后面很多地方都在重复用。比如 `permute()` 就是通用置换，IP、IP^-1、E、P、PC-1、PC-2 都能用它；`xor_bits()` 则是轮函数里必须用到的。把这些公共操作放在一起，后面的代码就会清楚很多。再比如拆分左右半部、循环左移这些操作，如果单独在每个模块里各写一份，不仅容易重复，还容易写出不一样的版本，所以放在 `common.py` 里统一处理比较合适。这样做以后，很多地方都能少写不少重复代码，也更容易维护。

（2）`des_tables.py`：标准表统一管理。

DES 的表很多，如果分散写在各个函数里，不太好查，也容易抄错。所以我把所有标准表都放到了 `des_tables.py` 里面，包括 IP、IP^-1、E、P、PC-1、PC-2、移位表和 8 个 S 盒。这样做的好处就是，后面如果结果有问题，可以先回这个文件检查表本身有没有写错。这个文件基本上就是一些常量定义，形式大致如下：

```python
IP = [...]
IP_INV = [...]
E = [...]
P = [...]
PC1 = [...]
PC2 = [...]
SHIFT_SCHEDULE = [1, 1, 2, 2, 2, 2, 2, 2, 1, 2, 2, 2, 2, 2, 2, 1]
S_BOXES = [S1, S2, S3, S4, S5, S6, S7, S8]
```

因为这些表是固定不变的，所以单独放一个文件比较合适。后面不管是密钥调度还是轮函数，都只是去调用这里的表，不需要自己重新定义。调试的时候也比较简单，如果某个输出和标准答案不一样，就先看是不是表里某个位置写错了。像 IP 和 IP^-1 这种表，如果抄错一项，最后结果就会完全不对，所以我觉得集中管理是很必要的。实际上在实验里，很多问题并不是算法逻辑本身错了，而是表项顺序有细微差异，所以把这些固定内容集中起来，对排错帮助很大。

（3）`key_schedule.py`：生成 16 个子密钥。

密钥调度这一块是从原始密钥出发，生成每一轮要用的 48 bit 子密钥。程序里先做 PC-1，把 64 bit 密钥变成 56 bit，再分成左右两个 28 bit，然后按移位表循环左移，最后通过 PC-2 得到每轮子密钥。这个过程看起来步骤比较多，但实际上就是把原始密钥按标准一步一步加工成轮密钥。

对应到代码，核心函数就是 `generate_subkeys()`：

```python
def generate_subkeys(key_hex: str) -> list[str]:
    key_bits = hex_to_bits(key_hex, 64)
    permuted = permute(key_bits, PC1)
    c, d = split_bits(permuted, 28)
    subkeys = []
    for shift in SHIFT_SCHEDULE:
        c = left_shift(c, shift)
        d = left_shift(d, shift)
        subkeys.append(permute(c + d, PC2))
    return subkeys
```

这个函数的思路就是先处理原始密钥，再一步一步生成 16 个子密钥。写的时候我比较关注的是两个长度：一个是 PC-1 后必须变成 56 bit，另一个是最后每个子密钥都必须是 48 bit。实验时我也会把子密钥打印出来看看，确认每一轮都在正常变化。因为子密钥如果有一轮不对，后面的 16 轮都会受到影响，所以这一块虽然代码不长，但其实很关键。还有一点就是，移位表不是每轮都一样，这就要求程序必须严格按照表来左移，不能图省事直接写成固定左移量，否则结果就会偏掉。

（4）`round_function.py`：实现轮函数 F。

轮函数 F 是 DES 中每轮计算的核心，代码也是单独放在一个文件里写的。它接收 32 bit 的右半部分和 48 bit 的子密钥，先扩展、再异或、再做 S 盒代换，最后做一次 P 置换。这个模块虽然代码量不算特别大，但实际上是最容易出问题的地方之一，因为中间每一步都对位序和长度要求很严格。

主要代码是这样：

```python
def round_function(r32: str, subkey48: str) -> str:
    expanded = permute(r32, E)
    mixed = xor_bits(expanded, subkey48)
    substituted = s_box_substitution(mixed)
    return permute(substituted, P)
```

这里面最容易写错的还是 S 盒。因为 48 bit 要分成 8 组 6 bit，每一组都要根据首尾位找行号，中间四位找列号，再到对应的 S 盒里查表。如果这个地方写错，后面的结果基本都会错。也就是说，这一部分不是只是把字符串切开那么简单，而是要按照 DES 的规则重新算出每一组的输出值。程序写到这里的时候，我最先检查的也是这里，因为只要 S 盒查表有问题，最后密文就肯定不对。

为了方便调试，我把 S 盒查表单独拆出来了：

```python
def s_box_lookup(chunk6: str, sbox: list[list[int]]) -> str:
    row = int(chunk6[0] + chunk6[5], 2)
    col = int(chunk6[1:5], 2)
    value = sbox[row][col]
    return f"{value:04b}"
```

这样写以后，调试起来会更直观一些，至少能清楚看到每个 6 bit 是怎么变成 4 bit 的。S 盒这一部分如果跑通了，轮函数其实就已经成功了一大半。因为 DES 的非线性主要就是靠这里体现出来的，所以这一块我在实验里也反复检查过几次，确保没有把行和列搞反。对于报告来说，这里也最值得多写一点，因为它正好体现了代码里最核心的计算过程。

（5）`des_core.py`：加密、解密和一致性验证。

前面的几个文件其实都还是在做局部工作，真正把 DES 整个流程串起来的是 `des_core.py`。这里面包含单块加密、单块解密，还有加密后再解密的往返验证。也就是说，前面准备好的位串处理、子密钥和轮函数，到这里才真正组合成完整的 DES 加密过程。

加密过程基本就是照着 DES 的标准流程写的：先做 IP 置换，再分成左右两部分，然后循环 16 轮，最后交换左右半部，再做 IP^-1。代码大概长这样：

```python
def des_encrypt_block(plaintext_hex: str, key_hex: str):
    block = hex_to_bits(plaintext_hex, 64)
    subkeys = generate_subkeys(key_hex)
    state = permute(block, IP)
    l, r = split_bits(state, 32)
    for subkey in subkeys:
        new_l = r
        new_r = xor_bits(l, round_function(r, subkey))
        l, r = new_l, new_r
    preoutput = r + l
    ciphertext = bits_to_hex(permute(preoutput, IP_INV), 16)
    return ciphertext
```

这个地方我自己觉得最重要的是最后那一步交换左右半部。前面 16 轮都写对了，如果这里忘了交换，最终结果还是不对，所以我在实验里也特意检查过这一点。还有一个容易忽略的地方是，IP 置换做完之后要先拆分成左右半部，再按轮次更新，如果拆分位置写错，后面所有轮的输入都会出问题。也正因为这样，`des_core.py` 其实是最能体现整个程序是否真的跑通的地方。

解密函数就更简单一些，本质上只是把子密钥倒过来用：


也就是说，加密和解密的主体流程其实是一样的，只是子密钥顺序相反。这个地方也正好说明 Feistel 结构为什么方便：不需要再单独写一套完全不同的解密算法。往返验证这一点在实验里也很有用，因为它可以直接看出程序是不是把整个流程都写对了。如果加密后再解密能恢复原文，那基本上就说明前面几层的逻辑都没大问题。

（6）`main.py`：最后的调用和输出。

`main.py` 不是负责实现 DES 逻辑的，它主要是把前面的模块调用起来，然后把结果打印出来。程序启动后会在这里解析输入参数，再决定是跑演示模式还是跑单次测试。从结构上看，它更像是整个程序的“入口”和“展示层”。

一般来说它会做这些事：

- 读取密钥、明文或密文；
- 调用加密或解密函数；
- 打印结果；
- 统计运行时间；
- 生成报告用的输出文本。

例如，在演示模式下，程序会自动运行一些预置测试向量，包括标准向量、全 0 测试、交替位型测试等，然后把每个测试的输入输出都输出到终端或 txt 文件中。这样做的好处是，既可以检验程序是否正确，也可以直接作为实验报告中的结果部分。对我来说，这一块其实更多是“把前面写好的功能统一展示出来”，所以代码本身不会太复杂，但它决定了最后看起来是不是一个完整程序。也就是说，前面模块负责“算”，这里负责“看结果、记结果”。

（7）运行方式。

程序的运行方式也比较简单。进入实验二目录后，直接执行 `python des_lab.py` 或 `python main.py` 就可以。如果不带参数，程序默认就跑演示模式；如果带上密钥、明文或者密文，就按参数去执行对应的加密或解密。

比如：

```python
python des_lab.py --mode single --key 133457799BBCDFF1 --plaintext 0123456789ABCDEF
```

这种方式比较适合单独测试某一组输入，也方便我在调试的时候反复改参数看结果。尤其是在检查程序是否和标准向量一致时，这种单次运行的方式很直观，不需要每次都改代码，只要改命令行参数就行。运行时如果发现结果不对，也能很快判断是输入问题还是程序逻辑问题，这一点在实验中挺重要。

（8）实验记录和调试输出。

为了方便看程序有没有跑对，我在代码里也保留了一些调试输出，比如每一轮的左右半部状态、最后的密文、解密后的结果，以及是否能恢复原文。对 DES 这种分组密码来说，这些中间结果其实比最后答案更有用，因为一旦哪里错了，可以顺着轮次往前找。很多时候，最终输出错了不代表整段代码都错了，可能只是某一轮的输入或者某个表项有偏差，所以保留中间状态是很有必要的。

例如可以这样打印每轮状态：

```python
for i, subkey in enumerate(subkeys, start=1):
    new_l = r
    new_r = xor_bits(l, round_function(r, subkey))
    l, r = new_l, new_r
    print(f"Round {i}: L={l} R={r}")
```

如果加密后再解密能恢复原文，说明整个链路基本是通的；如果不行，就可以根据中间轮状态一步一步排查问题出在哪个文件里。报告里写到这里，也就能比较自然地说明程序是怎么实现和怎么验证的。除了输出轮状态，我还会把最终的密文和解密结果一起记下来，方便和标准答案对比，这样实验结果部分也更容易整理。这个过程虽然看起来是“输出信息”，但实际上它是实验验证的一部分。

总体来说，这次实验的代码思路还是比较清楚的：先把公共函数和标准表拆开，再做子密钥和轮函数，最后在 `des_core.py` 和 `main.py` 里把流程串起来。这样写下来以后，代码本身比较好维护，报告也比较容易按实现过程来写。
