## 二、OSI 安全体系结构（CH4 重点）

国际标准（OSI 安全体系结构，国标 GB/T 18794）定义了两个核心概念，一定要分清：

- **安全服务**：要达到的**安全目标/功能**（"我想要什么效果"）。
- **安全机制**：实现服务的**技术手段**（"用什么方法做到"）。

> 比喻：安全服务是"我要房子防盗"（目标），安全机制是"装防盗门、监控、报警器"（手段）。一个服务可以由多个机制实现，一个机制也能支持多个服务。

### 2.1 五种安全服务（必背）

| 服务 | 作用 | 一句话 |
|------|------|--------|
| **鉴别 (Authentication)** | 确认对方身份真实 | 你是不是你说的那个人？|
| **访问控制 (Access Control)** | 防止非授权使用资源 | 你有没有权限用这个？|
| **数据机密性 (Confidentiality)** | 防止信息泄露 | 别人看不到内容 |
| **数据完整性 (Integrity)** | 防止信息被篡改 | 内容没被改过 |
| **抗抵赖 (Non-repudiation)** | 防止事后抵赖 | 做过的事赖不掉 |

其中鉴别又分：**对等实体鉴别**（确认通信对方身份）和**数据源鉴别**（确认数据来源）。

### 2.2 八种安全机制（必背）

| 机制 | 作用 |
|------|------|
| ① **加密** | 提供机密性，也支持其他机制 |
| ② **数字签名** | 不可伪造、不可抵赖 |
| ③ **访问控制** | 按权限控制访问 |
| ④ **数据完整性** | 用附加码验证数据没被改 |
| ⑤ **鉴别交换** | 通过"握手"确认身份，防重放 |
| ⑥ **通信业务流填充** | 填充无用数据，防流量分析 |
| ⑦ **路由选择控制** | 选安全可靠的路由路径 |
| ⑧ **公证机制** | 第三方公证，保证完整性、原发性等 |

> 记忆技巧：把它们和五种服务对应起来——比如"加密"主要支持机密性，"数字签名"支持抗抵赖和完整性，"鉴别交换"支持鉴别服务。

## 三、密码技术基础（CH4 重点）

### 3.1 对称密码 vs 公钥（非对称）密码

这是整门课最重要的对比之一：

| 对比项 | 对称密码 | 公钥（非对称）密码 |
|--------|---------|-------------------|
| 密钥 | 加密解密用**同一把**密钥 | **一对**密钥：公钥 + 私钥 |
| 速度 | **快** | **慢** |
| 密钥分发 | **难**（怎么安全地把密钥给对方？）| 容易（公钥可以公开）|
| 密钥数量 | n 个人需要 **n(n-1)/2** 把密钥 | 每人一对即可 |
| 典型算法 | DES、3DES、AES | RSA、ECC |
| 主要用途 | 加密大量数据 | 数字签名、密钥分发 |

**公钥密码的核心规则（务必理解）：**
- **公钥加密 → 私钥解密**：用于**保密**（只有私钥拥有者能解开）。
- **私钥加密（签名）→ 公钥验证**：用于**签名/身份证明**（证明这是我发的）。

> 比喻：公钥像一把"只能锁不能开"的锁，谁都能拿去锁箱子（加密），但只有你的私钥钥匙能开。反过来，你用私钥"盖章"（签名），所有人都能用你公开的章样核对真伪。

**对称密码两种类型：**
- **序列密码（流密码）**：逐比特加密，速度快，错误扩散小。
- **分组密码**：把明文分成固定长度的块加密，扩散性好，对篡改有免疫性。

### 3.2 消息认证码 MAC（Message Authentication Code）

- **作用**：既能**验证消息完整性**（没被改），又能**验证消息来源**（是对方发的）。
- **原理**：双方共享一个密钥 K，发送方用 K 对消息算出 MAC 一起发出；接收方用同样的 K 重新算 MAC，比较是否一致。
- **特点**：因为攻击者不知道 K，无法伪造正确的 MAC。
- **缺点**：**没有保密作用**（消息本身没加密）；需要双方共享密钥。

### 3.3 消息摘要（Hash/哈希）

- 用哈希函数（MD5、SHA-1 等）把消息压成固定长度的**摘要（digest）**。
- 特点：**单向不可逆**、**雪崩效应**（改一点摘要大变）、**抗碰撞**。
- 与 MAC 区别：摘要**不需要密钥**；但单独用摘要无法防篡改（攻击者可同时改消息和摘要），所以常和加密/签名结合。

### 3.4 数字签名（必考）

数字签名 = **私钥签名 + 公钥验证**，通常配合哈希使用：

**签名过程（发送方 A）：**
1. 对消息 M 算哈希，得到摘要。
2. 用 A 的**私钥**加密摘要 → 这就是数字签名。
3. 把 M 和签名一起发给 B。

**验证过程（接收方 B）：**
1. 用 A 的**公钥**解密签名 → 得到原摘要。
2. 自己对 M 重新算哈希 → 得到新摘要。
3. 两个摘要一致 → 证明：①确实是 A 发的（鉴别）②没被篡改（完整性）③A 抵赖不掉（抗抵赖）。

**数字签名的作用（5 个）：**
身份鉴别、防假冒、抗抵赖、防篡改、具有法律效力。

> 重点：**先签名后加密**还是**先加密后签名**？课件强调要**先签名后加密**。如果先加密后签名，攻击者截获后可以去掉签名换成自己的签名，造成混乱。

## 四、鉴别技术（CH5 重点）

### 4.1 鉴别的基本概念

- **鉴别（Authentication）**：确认实体"是它所声称的那个"。
- 是**最重要的安全服务之一**，其他所有安全服务都依赖它。
- 用来**对抗假冒攻击**。
- 角色：**示证者 P**（声称者，出示证件的人）、**验证者 V**（检验的人）、**可信第三方 TP**、**攻击者**。

### 4.2 实现鉴别的三种途径（必背）

| 途径 | 英文 | 例子 |
|------|------|------|
| 你**知道**什么 | What you **know** | 口令、密码、PIN |
| 你**拥有**什么 | What you **have** | 身份证、智能卡、令牌、U盾 |
| 你**是**什么 | What you **are** | 指纹、虹膜、人脸、声纹 |

组合使用就是**双因素/多因素认证**（比如密码 + 短信验证码）。

### 4.3 口令机制及其脆弱点

口令（password）是最常用的鉴别方式，但有很多弱点：
- **外部泄露**、**口令猜测**、**线路窃听**、**危及验证者**（服务器口令库被偷）、**重放攻击**。

**防护手段：**
- 对付线路窃听：**一次性口令 OTP**、引入**散列函数**、**加盐（Salt）**。
- **加盐**：在口令后加一段随机字符串再做哈希，让攻击者无法用预先算好的"字典表"破解（防字典攻击）。

### 4.4 一次性口令 OTP（One-Time Password）

- **核心特征**：**每次认证使用不同的口令**。
- **作用**：对付**重放攻击**（攻击者就算截获了这次口令，下次也没用）。
- 实现方式：共享随机口令串、随机序列生成器同步、时间戳同步（如手机动态令牌）。

### 4.5 挑战-应答（Challenge-Response）

- **原理**：验证者给声称者发一个**随机的挑战值**，声称者用它参与运算后返回。
- **防重放的关键**：每次挑战值都**不同、不可预测、不重复**，所以每次传输的鉴别信息都不一样。
- 安全性取决于哈希函数的安全性。

### 4.6 零知识证明（Zero-Knowledge Proof）

非常重要也很有意思的概念：

- **目标**：证明者向验证者**证明自己知道某个秘密，但不泄露这个秘密本身**。
- **三个原则：**
  1. **完备性**：真的假不了（真的知道，一定能通过验证）。
  2. **合理性**：假的真不了（不知道的人，几乎不可能蒙混过关）。
  3. **零知识**：验证者只知道"对方有这个能力"，**得不到任何其他信息**。

> 经典例子——**山洞问题**：阿里巴巴知道开暗门的咒语。他先进山洞，盗贼在洞口随机喊"从 C 出来"或"从 D 出来"。如果阿里巴巴真知道咒语，每次都能从指定方向出来；如果不知道，蒙对的概率每次只有 1/2，做 16 轮后蒙混过关概率只有 1/65536。这样既证明了他知道咒语，又没暴露咒语内容。

### 4.7 Kerberos 鉴别协议

- 基于**对称密钥加密**和**票据（Ticket）**的网络身份鉴别协议（MIT 开发）。
- 核心组件：**KDC（密钥分发中心）**，包含 **AS（认证服务器）** 和 **TGS（票据授权服务器）**。
- 流程简化版：
  1. 向 AS 请求 → 拿到**票据授权票据 TGT**。
  2. 拿 TGT 向 TGS 请求 → 拿到**服务票据 Ticket**。
  3. 拿 Ticket 向服务器请求服务。
- **优点**：单点登录（拿到 TGT 后不用重复输密码）。
- **缺点**：AS/TGS 集中管理易成瓶颈；需要**时钟同步**；密钥管理随用户增多变复杂。

## 五、访问控制（CH6 重点）

### 5.1 基本概念

- **目标**：防止对资源的**未授权访问**，让资源在授权范围内使用。
- **三元组 (S, A, O)**：
  - **主体 S (Subject)**：发起者，主动方（用户、程序、进程）。
  - **客体 O (Object)**：被访问的对象，被动方（文件、数据库、设备）。
  - **访问操作 A (Access)**：读、写、执行、删除等。
- **两个重要过程**：先**鉴别**（验证身份），后**授权**（限制权限）。
- **最小特权原则**：用户只拥有完成职责所需的**最小权限集合**，不给多余权限。
- 和 **AAA** 相关：鉴别（Authentication）、授权（Authorization）、审计（Audit/Accounting）。

### 5.2 实现机制：ACL vs 能力表（必考对比）

访问控制矩阵（行是主体，列是客体）有两种拆分方式：

| 对比项 | 访问控制表 ACL | 能力表 Capability List |
|--------|---------------|----------------------|
| 按什么拆分 | 按**列**（客体）| 按**行**（主体）|
| 关联对象 | 与**客体**关联 | 与**主体**关联 |
| 保存位置 | 客体 | 主体 |
| 记录内容 | 谁能访问这个客体 | 这个主体能访问什么 |
| 浏览某客体的所有权限 | **容易** | 困难 |
| 浏览某主体的所有权限 | 困难 | **容易** |
| 权限传递/回收 | 回收容易、传递难 | 传递容易、回收难 |
| 适用 | 集中式系统 | 分布式系统 |

> 记忆：**ACL 跟着"东西"走（客体），能力表跟着"人"走（主体）。**

### 5.3 自主访问控制 DAC（Discretionary Access Control）

- **含义**：客体的**属主（创建者）自己决定**谁能访问它。
- **特点**：灵活、易用、可扩展，常用于商业系统。
- **缺点**：**安全性不高**——信息在传递过程中权限会被改变；容易受**特洛伊木马**威胁（木马以你的权限偷偷做坏事）。
- 例子：Linux 的 `chmod`、Windows 文件权限。

### 5.4 强制访问控制 MAC（Mandatory Access Control）

- **含义**：由**系统管理员统一**按安全级别强制控制，**客体属主无权修改**。
- 主体和客体都分配**安全级别**（如：公开 < 秘密 < 机密 < 绝密）。
- 应用于**军事等高安全要求**系统。
- 通过"上读/下写"或"下读/上写"实现**单向信息流**。

### 5.5 BLP 模型 vs Biba 模型（必考对比）

这两个是强制访问控制的经典模型，**对偶关系**，最容易考：

| 模型 | 保护目标 | 规则 | 记忆 |
|------|---------|------|------|
| **Bell-LaPadula (BLP)** | **机密性** | **下读/上写**（不上读、不下写）| 防止机密信息向下泄露 |
| **Biba** | **完整性** | **上读/下写**（不下读、不上写）| 防止低质量信息向上污染 |

**详细解释：**

- **BLP（保机密性）**：
  - **不上读**：低级别用户不能读高密级信息（防泄密）。
  - **不下写**：高级别用户不能把机密写到低密级区域（防泄密）。
  - 信息只能**从低流向高**。
  - 应用：**防火墙**（隔离内外网，只允许内→外发起）。

- **Biba（保完整性）**：
  - **不下读**：高完整性主体不读低完整性数据（防被污染）。
  - **不上写**：低完整性主体不能写高完整性数据（防篡改）。
  - 应用：**Web 服务器**（互联网用户只能读，不能改服务器数据）。

> 记忆口诀：**BLP 保密——下读上写；Biba 完整——上读下写。** 注意"写"代表信息流动方向。

### 5.6 基于角色的访问控制 RBAC（Role-Based Access Control，必考）

- **核心思想**：不直接给用户分配权限，而是通过**角色**这个中间层。
  - **用户 → 角色 → 权限**
- **核心元素**：用户（User）、角色（Role）、权限（Permission）、会话（Session）。
- **多对多关系**：一个用户可有多个角色，一个角色可给多个用户；一个角色可有多个权限。
- **优点**：
  - 便于授权管理（人员变动只需改角色分配）。
  - 容易实现**最小特权**、**职责分离**等安全策略。
  - 支持**角色继承**、**角色互斥**、**角色基数限制**。
- **RBAC96 系列**：
  - RBAC0：核心。
  - RBAC1：+ 角色继承。
  - RBAC2：+ 约束（责任分离）。
  - RBAC3：= RBAC1 + RBAC2（完整模型）。

> 例子（银行）：定义"出纳员""分行管理者""审计员"等角色，给每个角色分配权限。来个新员工，直接给他分配"出纳员"角色就行，不用一项项设权限。

### 5.7 其它

- **TCSEC（橘皮书）**：美国可信计算机系统评估标准，把安全分 A/B/C/D 四类八级。大多数通用操作系统（Windows、Linux）是 **C2 级**（控制访问保护级）。
- **集中式访问控制**：RADIUS、TACACS+、Diameter。
- **非集中式**：域（Domain），跨域访问需建立信任关系。
