## 1. 课程设计题目

Web 登录系统安全加固与审计日志设计。在实现一个最小可用登录系统的基础上，
完成五项安全加固：**密码哈希存储、登录失败限制与账号锁定、登录审计日志、异常登录检测、安全审计输出**。

## 2. 项目背景

登录系统是 Web 应用的安全入口，是攻击者的首要目标。常见威胁包括：

- **明文/弱哈希存储口令**：一旦数据库泄露，口令直接暴露；
- **暴力破解 / 撞库**：自动化工具高频尝试口令；
- **异常登录**：异地、非工作时间、高频请求等可疑行为缺乏感知；
- **缺乏审计**：登录行为无记录，事后无法追溯。

本课程设计针对上述问题，构建一个带安全加固与审计能力的登录系统，做到 **有场景、有数据、有流程、有规则、有实现、有测试、有结果、有分析**。

### 4.2 安全需求

- 口令绝不明文存储；
- 统一“用户名或口令错误”提示，防止用户名枚举；
- 所有 SQL 使用参数化查询，防止 SQL 注入；
- 失败限制 + 锁定，抵抗暴力破解；
- 全量审计可重复执行，输出结构化结果。

### 4.3 异常规则需求（任务书四类异常）

| 异常类型 | 任务书规则示例 | 本人设计的判断规则 |
|----------|----------------|--------------------|
| 暴力尝试 | 5 分钟内失败超过 5 次 | 5 分钟窗口内失败 **≥ 5** 次 → 锁定 10 分钟 |
| 异地登录 | 同账号短时间不同 IP | **10 分钟**内同账号出现 **≥ 2** 个不同 IP |
| 非工作时间 | 晚 23:00 后登录 | **23:00–06:00** 之间成功登录 |
| 高频登录 | 1 分钟内超过阈值 | **60 秒**内请求 **≥ 10** 次 |

> 上述阈值全部集中在 `config.py`，**由本人结合自身上机作息与实验场景设计**，
> 答辩时可现场修改任一数值并重新运行验证（详见第 13 节）。

## 5. 技术方案

### 5.1 系统架构

```
浏览器  ──HTTP──►  Flask 路由层 (app.py)
                        │
          ┌─────────────┼──────────────┐
          ▼             ▼              ▼
    security.py     audit.py        db.py
   (认证/哈希/锁定) (异常检测/审计) (SQLite 数据访问)
          └─────────────┴──────────────┘
                        ▼
                  SQLite (users / login_logs / audit_alerts)
        所有阈值集中于 config.py（个性化安全规则）
```

模块职责：

- **config.py**：集中存放全部个性化安全阈值；
- **db.py**：SQLite 建表与参数化读写；
- **security.py**：口令哈希、强度校验、失败计数、锁定、登录认证主流程；
- **audit.py**：实时异常检测 + 离线全量审计；
- **app.py**：Flask 路由与页面渲染。

### 5.2 密码哈希方案

采用 Werkzeug 的 `generate_password_hash(method="pbkdf2:sha256:260000")`：

- **加盐**：每个口令使用独立随机盐，相同口令哈希值不同，抵抗彩虹表；
- **慢哈希**：26 万次迭代，显著抬高离线爆破成本；
- **恒定时间比较**：`check_password_hash` 防止时序侧信道。

存储样例（真实截取）：`pbkdf2:sha256:260000$mQ08o2ymVe7...`，库中无任何明文。

### 5.3 数据库设计

```sql
-- 用户表
users(id, username UNIQUE, password_hash, created_at,
      failed_count, locked_until, last_login_at)
-- 登录日志表
login_logs(id, username, ip, user_agent, success, reason, created_at)
-- 审计告警表
audit_alerts(id, username, alert_type, detail, created_at)
-- 索引：加速审计扫描
INDEX idx_logs_user_time ON login_logs(username, created_at)
```

`reason` 取值：`ok / wrong_password / user_not_found / locked`，是审计判断的关键字段。

## 9. 系统实现

### 9.1 登录认证核心（节选 `security.authenticate`）

认证流程严格按图 2 的四个分支实现：

1. **账号已锁定** → 记录 `locked` 日志，直接拒绝；
2. **用户不存在** → 记录 `user_not_found`，返回统一提示（防枚举）；
3. **口令错误** → 记录 `wrong_password`，失败计数 +1，达阈值即锁定并告警；
4. **认证成功** → 记录 `ok`，清零计数，运行实时异常检测并提醒。

### 9.2 失败限制与锁定

`count_recent_failures` 基于 **登录日志按时间窗口统计**（而非简单累加计数器），
因此“5 分钟内”这一时间语义是精确的；达到 `MAX_FAILED_ATTEMPTS=5` 即写入 `locked_until = now + 10 分钟`。

### 9.3 异常检测与审计

- **实时检测**（登录成功瞬间）：异地、非工作时间、高频，命中即弹出提醒；
- **离线全量审计**：`run_full_audit` 按时间回放全部日志，对四类规则逐条匹配并去重，
  输出结构化报告（总数 / 成功 / 失败 / 各类告警明细）。

## 13. 问题与改进

### 13.1 遇到的问题

1. **时间窗口统计**：最初用简单计数器累加失败次数，无法体现“5 分钟内”语义；
   改为基于日志按时间窗口统计后才精确。
2. **用户枚举风险**：用户不存在与口令错误若返回不同提示会泄露账号存在性；
   统一为“用户名或口令错误”后修复。
3. **审计可重复性**：重复审计会重复写告警；通过审计前 `clear_alerts` + 去重集合解决。

### 13.2 改进方向

- 引入图形验证码 / TOTP 二次验证（任务书提到的二次验证模拟）；
- 基于 IP 地理库做真正的异地判定（当前为同账号多 IP 启发式）；
- 接入限流中间件，对高频来源 IP 自动限流；
- 告警推送（邮件 / Webhook），并接入集中式日志（如 ELK）。

### 13.3 答辩可现场修改的参数（演示“可验证”）

修改 `config.py` 任一阈值后重新运行 `python run_tests.py` 或刷新 `/audit` 即可验证，例如：

- `MAX_FAILED_ATTEMPTS` 5 → 3：锁定将更早触发；
- `HIGH_FREQ_THRESHOLD` 10 → 5：高频告警数量上升；
- `OFF_HOURS_START` 23 → 22：更多登录被判非工作时间。
