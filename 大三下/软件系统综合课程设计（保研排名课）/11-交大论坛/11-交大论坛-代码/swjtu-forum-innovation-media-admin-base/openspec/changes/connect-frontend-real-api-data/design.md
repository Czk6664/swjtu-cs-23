## Context

当前 `jiaodaluntan` 的后端已经具备相对完整的业务接口，覆盖认证、帖子、评论、成长体系、举报与后台治理，且统一返回 `ApiResponse<T>`。前端则是一个 Vite 多页应用，各页面通过 `frontend/vite.config.js` 作为独立入口，现阶段页面结构和视觉已经落地，但交互大多仍停留在静态示例或本地假动作。

这次改动是一个典型的跨模块联调变更：需要同时调整共享前端运行时、多个页面入口、鉴权状态管理、接口请求封装和页面数据映射。如果直接在每个页面零散接接口，后续会很快出现重复请求逻辑、权限处理不一致、空态/错误态风格割裂的问题。

## Goals / Non-Goals

**Goals:**
- 建立统一的前端 API 访问层，兼容现有 `/api` 代理、`ApiResponse` 包装和 JWT 本地存储。
- 让论坛前台页面能够读取真实分区、帖子、评论、用户资料和互动数据，并触发关键写操作。
- 让成长与商城页面能够读取真实成长数据，并执行签到、兑换等实际动作。
- 让后台页面能够读取真实治理数据，并执行审核、封禁、推荐策略更新等核心管理操作。
- 为没有真实接口支撑的展示位提供统一的“待接入/暂无数据”机制，移除混杂的 mock 体验。

**Non-Goals:**
- 不在本次变更中重做整套视觉设计或重新拆分页面结构。
- 不新增大型前端框架或将多页应用改造为 SPA。
- 不为后端尚未提供的聚合看板接口强行新增大量新 API；优先组合现有接口完成页面。
- 不在本次变更中解决所有分页、筛选和性能优化问题，只保证关键路径可联调、可演示。

## Decisions

### 1. 保留多页架构，在 `frontend/assets/app.js` 中集中实现共享 API/runtime

前端已经是 MPA 结构，短期内改成组件化 SPA 成本过高，也会打乱刚刚完成的静态落地页。更稳的做法是在现有 `assets/app.js` 中恢复共享运行时职责，集中处理：
- `fetch` 封装与 `ApiResponse` 解包
- JWT 注入与 401/403 统一处理
- 登录态恢复、登出、`/auth/me` 同步
- 页面级 bootstrap 分发
- 通用 loading / empty / error / toast UI

备选方案是每个页面单独内联请求逻辑，但那会导致 10+ 页面重复处理 token、错误提示和 envelope 解析，维护成本太高。

### 2. 采用“页面 bootstrap + slot 渐进增强”，而不是完全动态重绘整页

当前页面 HTML 已经具备较完整的静态结构。实现时应保留主要布局和视觉骨架，只在每个页面约定的 `data-slot` 容器内注入真实数据列表、详情块或状态信息。这样可以：
- 减少重写已验收的视觉结构
- 保持现有测试对 `data-slot` 的约束不变
- 让静态稿和真实数据态共存，便于逐页联调

备选方案是由 JS 完整接管整页 DOM，但这会放大代码量，也更容易把视觉回退成“脚本生成页面”。

### 3. 认证采用“匿名可读、登录可写、页面内降级提示”的策略

后端已允许部分只读内容匿名访问，例如分区、公开帖子、热榜等；写操作和用户私域数据则要求 JWT。前端应遵循这个边界：
- 首页、帖子详情、热榜可匿名读取
- 点赞、收藏、评论、发帖、签到、兑换、后台管理等动作需登录
- 未登录用户点击写操作时，前端不直接报错，而是引导到登录页并保留回跳意图

这比“整页一刀切必须登录”更符合论坛产品习惯，也更贴合现有后端权限模型。

### 4. 优先复用现有后端接口，缺失聚合数据由前端轻组合

后台总览、个人中心、成长中心里有部分卡片型数据，本次优先通过现有接口组合得到，例如：
- 首页：`/sections` + `/posts/recommend` 或 `/posts/hot`
- 详情页：`/posts/{id}` + `/posts/{id}/comments`
- 个人中心：`/auth/me` + `/posts/mine` + `/posts/favorites` + `/posts/history`
- 运营总览：`/admin/posts/pending` + `/admin/reports/summary` + `/admin/redemptions/pending`

只有当某页无法通过现有接口组合出可用体验时，才在实施阶段评估是否补后端聚合端点。

### 5. 用显式状态组件替代静态文案兜底

当前不少页面写死了“看起来像数据”的示例内容。接真实接口后，这些区域必须具备三种状态：
- loading：正在请求
- empty：接口成功但暂无数据
- error：请求失败，可重试

这样即使 demo profile 或数据库为空，页面也不会再回退成误导性的 mock 叙事。

## Risks / Trade-offs

- [多页入口多、逻辑分散] → 通过共享 runtime 与 page bootstrap 表统一入口，避免每页各写一套请求逻辑。
- [后端实体直接透出，字段命名未做前端友好封装] → 在前端 runtime 增加轻量 mapper，把页面真正依赖的字段做一次归一化。
- [部分管理页需要多个接口拼装，首屏请求数增加] → 先按页面拆分并行请求，后续如明显影响体验再考虑后端聚合接口。
- [未登录用户触发写操作容易产生跳转割裂] → 为需要登录的动作统一保留目标页面与上下文，登录成功后尽量回跳。
- [页面从静态文案切换到真实数据后，空数据库会显得“内容少”] → 使用 demo profile 或明确空态说明，避免误以为页面损坏。

## Migration Plan

1. 先恢复共享 `app.js` 的 API/runtime 能力，并接通认证、公共读取和错误处理。
2. 按“前台内容 → 成长体系 → 后台治理”的顺序逐组接入页面，保证每一步都可单独构建与验证。
3. 在联调环境中用 demo profile 或已有种子数据验证页面表现，确保不是依赖静态文案撑页面。
4. 若某些卡片无法由现有接口组合，在实现阶段单独列出后端补口需求，不阻塞已能打通的路径。
5. 回滚策略保持简单：页面保留静态骨架，若某项联调失败，可暂时禁用对应动作并显示“待接入”状态，而无需回滚整套视觉结构。

## Open Questions

- 首页最终默认读取 `/posts/recommend` 还是匿名时固定读取 `/posts/hot`，是否需要前端根据登录态自动切换。
- 推荐策略页是否只支持查看与更新配置，还是同时要展示预览结果与解释原因。
- 个人中心中的“校园身份认证”是否要在这一轮就接入真实提交表单，还是先只展示认证结果。
