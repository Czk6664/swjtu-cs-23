【第3章 需求工程 —— 依据真实PPT逐页转写的大纲（51页）】

学习目的与意义：需求工程的目标、需求的分类、需求工程（过程）、需求规格说明书

一、为什么要进行需求工程
- 美国 IT 项目统计（Standish Group / CHAOS Report）：大量项目失败/超支，其中与"需求"相关的原因占很大比例（需求不完整、用户参与不足、需求频繁变更等）
- 说明：需求问题是项目失败的首要根源

一、需求工程的目标
- 需求工程：对需求进行获取、分析、规格说明、验证和管理的系统化过程（1997年定义）
- 最终产物：需求规格说明书（SRS）

一、需求工程的重要性
- 需求是项目成功/失败的关键因素
- 需求错误发现得越晚，修复代价越高（代价随阶段指数增长）

二、需求分类
1. 用户需求与系统需求（需求层次）
   - 概貌需求 / 概要（用户）需求 / 详细（系统）需求
   - 用户需求：用自然语言和图表描述系统需提供的服务及约束（面向用户）
   - 系统需求：详细描述系统功能、服务和约束（面向开发者）
   - 案例：心理健康助人者系统
2. 功能性需求与非功能性需求（重点）
   - 功能需求：系统应当提供的功能、服务、行为（"做什么"）
   - 非功能需求：对系统的约束和质量属性，包括性能、可靠性、可用性、安全性、可维护性、可移植性等
     · 非功能需求分类：产品需求、组织需求、外部需求
     · 非功能需求度量：性能（每秒处理事务数/响应时间）、空间（内存/存储）、可靠性（MTTF等）、健壮性、可移植性
   - 案例：广告DM平台、SaaS化IM对异构配置的注册登录

三、需求工程过程（五个活动，重点）
   需求获取 → 需求分析与协商 → 需求规格说明 → 需求验证 → 需求管理（迭代/螺旋进行）
1. 需求获取（需求捕获）
   - 来源：涉众(stakeholders)、已有系统、相关文档、领域知识
   - 方法与技术：访谈/面谈、问卷调查、现场观察、原型法、场景/用例、头脑风暴
   - 案例：心理健康助人者系统需求获取
2. 需求分析与协商
   - 分析活动：对获取的需求进行分类、抽象、建模
   - 需求建模：用模型表达需求
   - 冲突协商：解决涉众间需求冲突
3. 组织（场景描述）：用场景/案例组织需求（广州楼栋登记系统等案例）
4. 需求规格说明
   - 重要性：作为开发、测试、验收的依据
   - 内容：功能需求、非功能需求、接口、约束等
   - 编写方法：自然语言描述、结构化语言描述、可视化（图形/模型）描述
   - 结构化需求规格说明、需求规格说明模板（参考 IEEE 830 / SRS 模板）
5. 需求有效性验证（需求验证与确认 V&V）
   - 验证技术：需求评审、原型、测试用例
   - 验证内容：有效性、一致性、完整性、现实性（可行性）、可验证性
   - 需求确认：与用户确认需求正确

四、需求规格说明书（SRS 文档结构，重点）
封面（系统名、版本号、作者、日期）
1. 概述（编写目的、范围、定义、参考资料）
2. 总体描述（系统范围、系统上下文模型 Context Model：系统与外部实体的交互）
3. 功能需求
   3.1 业务需求 / 用例图
   3.2 功能需求分析（用例描述表）
   3.3 数据需求分析（数据流图、数据字典、ER图/数据表条目）
4. 非功能需求（4.1 性能需求、4.2 资源需求、4.3 安全需求等）
5. 接口需求 / 系统的界面上下文环境
