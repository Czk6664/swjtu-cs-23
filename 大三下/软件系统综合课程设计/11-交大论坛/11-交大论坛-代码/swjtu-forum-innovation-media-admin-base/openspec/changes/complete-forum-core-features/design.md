## Context

项目当前是 Spring Boot 后端 + Vite 多页面前端。后端已经提供认证、帖子、评论、成长、举报、后台治理等接口，默认可用 H2 本地数据库启动；前端已经接入真实 API，但主要运行时集中在 `frontend/assets/app.js`，页面仍保留大量静态 HTML shell。上一轮真实使用中已经暴露出典型问题：接口可用但浏览器来源、权限跳转、动态渲染、后台入口和真实路径烟测没有统一收口。

这次设计的重点不是继续做“静态展示页”，而是把课程设计变成一个老师可以按游客、普通用户、管理员三类角色连续操作的校园论坛。核心约束是：保持现有 Vite MPA 架构和交大蓝视觉风格，不引入大型前端框架，优先复用已有后端接口，只在真实功能闭环缺口明显时补小型后端接口。

## Goals / Non-Goals

**Goals:**

- 补齐论坛最基本的真实功能闭环：浏览、搜索、版块筛选、发帖、详情、评论、互动、个人中心和后台治理。
- 让用户对每个关键动作都得到可信反馈，包括成功、待审核、权限不足、空数据和接口失败。
- 消除真实路径中最容易被老师点出来的 bug：登录回跳、403、静态内容残留、删除约束失败、后台误入、数据为空页面像坏掉。
- 建立覆盖游客、普通用户、管理员的 smoke test 矩阵，作为后续交付检查入口。
- 逐步降低前端单文件运行时风险，为后续维护留下清晰模块边界。

**Non-Goals:**

- 不把 Vite MPA 改成 Vue/React SPA。
- 不追求复杂社交功能，如私信、实时在线聊天、WebSocket 协同编辑。
- 不实现真实学校统一身份认证，只保留课程项目可演示的校园身份状态与校内邮箱/学号信息。
- 不重做整套视觉系统，只在现有交大蓝主题和页面风格上补真实功能。
- 不把所有后台统计都做成复杂 BI，只保证治理流程可用、数据可解释。

## Decisions

### 1. 以“核心旅程”而不是“页面数量”组织实施

功能补齐按用户旅程分组：游客发现内容、普通用户参与内容、用户管理自己内容、管理员治理内容。这样可以避免每页补一点但流程仍断裂。

备选方案是按 HTML 页面逐个补功能，但这会继续放大“页面看起来有、真实路径不通”的问题。

```text
游客
  └─ 浏览首页/版块/搜索/详情
        ↓ 登录
用户
  └─ 发帖/评论/点赞/收藏/举报/管理自己的帖子
        ↓ 管理员审核
管理员
  └─ 待审内容/举报/用户/版块/推荐策略
```

### 2. 保留 MPA，但把共享运行时拆出清晰边界

现有 `frontend/assets/app.js` 已经接近 1000 行，继续加功能会让 bug 定位变慢。实施时应保持页面入口不变，但把逻辑按职责拆分为 API、session、render utils、page modules、smoke helpers 等小模块；如果时间不足，至少先在同一文件中建立清晰分区和统一 helper，避免每个页面重复写 fetch、toast、权限判断。

备选方案是立即全面重构为组件框架，但课程项目当前更需要稳定可交付，框架迁移风险高。

### 3. 前端显示状态以后端真实状态为准

帖子发布可能直接公开，也可能因敏感词进入待审核；删除可能因评论外键约束失败；后台审核可能改变帖子状态。前端不能再用固定文案假定成功，而必须根据 API 返回数据和错误码展示状态。

```text
POST /api/posts
   ├─ status = PUBLISHED  → 跳转详情并提示发布成功
   └─ status = PENDING    → 显示待审核说明，可回到我的帖子
```

### 4. 删除优先采用“软删除/隐藏”语义

论坛系统里帖子通常不建议物理删除，尤其当前数据库存在评论、点赞、收藏、浏览历史等外键。用户删除自己的帖子和管理员删除帖子，应优先落成“隐藏/撤回/关闭展示”的软删除行为；只有后台确认无关联数据时才允许物理删除。

备选方案是级联删除所有关联数据，但这会破坏举报、积分和操作日志等审计信息，不适合课程展示中的治理闭环。

### 5. 后台治理以“能处理真实队列”为优先

后台不需要堆很多看板卡片，最重要是管理员能完成真实工作：看到待审帖子、看到举报、处理通过/驳回/隐藏、封禁/解封用户、管理版块。所有操作都要刷新列表并给出结果反馈。

### 6. Smoke test 成为功能完成标准

每个补齐任务不以“代码写完”为完成，而以路径通过为完成。至少覆盖：

- 游客浏览首页、搜索、进入详情。
- 新用户注册/登录、发布帖子、评论、点赞、收藏。
- 用户进入个人中心查看自己的帖子、收藏、历史，编辑或撤回帖子。
- 管理员登录、审核帖子、处理举报、封禁/解封用户、管理版块。
- 未登录或普通用户访问后台时得到友好提示而不是白屏或死循环。

## Risks / Trade-offs

- [前端单文件继续膨胀] → 优先拆分 shared runtime 和 page handlers；若时间紧，至少建立清晰分区并补测试锁住行为。
- [补功能范围过大] → 以“老师最可能点击的论坛核心路径”为边界，通知只做基础站内反馈，不做实时推送。
- [真实数据为空导致页面看起来没内容] → 本地启动器继续初始化基础版块、管理员和示例帖；页面必须有清晰空态。
- [删除帖子触发外键约束] → 用户侧采用撤回/隐藏，管理员侧保留审计记录，不默认物理删除。
- [权限 bug 在浏览器里才暴露] → smoke test 必须覆盖 `localhost` 和 `127.0.0.1` 本地来源，覆盖游客/用户/管理员三类角色。
- [后端接口返回实体字段不稳定] → 前端增加轻量 mapper，只依赖页面真正需要的字段。

## Migration Plan

1. 先冻结当前可启动状态，记录默认管理员、H2 数据库、Vite 代理和关键页面地址。
2. 补齐后端缺口：用户帖子编辑/撤回、版块管理必要接口、删除/隐藏语义、必要的通知或操作反馈数据。
3. 补齐前端用户路径：搜索/版块/详情/发帖/评论/互动/个人中心。
4. 补齐后台路径：待审、举报、用户、版块、推荐策略操作结果刷新。
5. 拆分或整理共享运行时，并补前端运行时测试。
6. 编写并执行 smoke test 矩阵，修复真实浏览器路径暴露的问题。
7. 若某项新功能风险超出课程周期，保留明确“暂未开放”状态，不再使用假数据冒充已完成。

## Open Questions

- 用户删除自己的帖子最终命名为“删除”“撤回”还是“隐藏”？建议 UI 使用“撤回”，后端保持软删除。
- 基础通知是否需要持久化表，还是先用操作反馈和个人中心提醒完成课程展示？
- 搜索是否只做标题/正文关键字，还是同时支持版块、作者、标签组合筛选？建议第一轮支持关键字 + 版块 + 标签。
