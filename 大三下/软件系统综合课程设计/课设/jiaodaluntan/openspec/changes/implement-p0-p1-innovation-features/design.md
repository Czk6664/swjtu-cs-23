## Context

项目当前是前后端分离的校园论坛系统，后端基于 Spring Boot/JPA，前端为 Vite 多页面模块化结构。现有系统已经有发帖、评论、用户、版块、成长中心、推荐、后台统计等基础能力，但创新功能之间还没有形成强闭环。

本次变更基于 `创新功能实现计划.md` 的 P0/P1 范围推进，重点让普通用户主流程可用、让校园特色更明显、让后台统计更适合课程设计展示。代码中已存在 `GrowthDiscoveryService` 的成就展示、`user_tags/tags` 用户兴趣标签关系、`AnalyticsService` 的后台热榜数据，因此设计上优先复用已有能力，避免重复建设。

## Goals / Non-Goals

**Goals:**

- 实现问答采纳、已解决状态和贡献值联动，让课程互助帖子形成问题解决闭环。
- 将现有成长中心的“派生成就”升级为可展示、可检查、可复用的校园徽章体系。
- 增加发帖模板、热门话题、校园身份标签，提升普通用户使用体验和真实校园论坛感。
- 使用 Anime.js 增强首页和关键页面动效，在不牺牲性能的前提下让论坛更有动感。
- 增加兴趣圈子与数据大屏增强，形成创新展示点和管理侧统计能力。
- 保证普通用户页面不再误入管理员权限提示，新增普通接口必须保持公开或登录用户可访问。
- 新增数据结构必须兼容现有数据，避免破坏当前可运行版本。

**Non-Goals:**

- 不实现 P2 功能，如弹幕评论、高能预警、新生手册、学习资料库。
- 不引入新的外部数据库、消息队列或前端框架。
- 不重构整个权限体系，只在新增接口中明确普通用户、登录用户、管理员的访问边界。
- 不要求一次性实现复杂推荐算法；身份标签先服务于展示和现有推荐基础。

## Decisions

### 1. 按“主流程优先”分阶段实现

先实现问答采纳和已解决状态，再做徽章联动，之后做模板、热榜、身份标签、数据大屏，最后实现兴趣圈子。这样可以确保每个阶段都有可演示成果，不会因为圈子这种大功能拖慢整个分支。

替代方案是按计划文档序号一次性并行实现所有功能，但这会同时修改帖子、评论、用户、后台、导航和页面结构，回归风险较高。

### 2. 问答采纳使用事务保障单帖唯一最佳答案

采纳接口在 `PostService` 内完成校验和状态更新：校验当前用户是否为楼主，清除旧采纳评论，设置新采纳评论，更新帖子 `acceptedCommentId`。该逻辑必须在事务中完成，避免并发点击导致多个评论同时被采纳。

替代方案是前端控制只显示一个采纳按钮，但前端无法提供权限和并发保证。

### 3. 徽章体系以持久化 `Badge/UserBadge` 为主，兼容现有成长中心

现有 `GrowthDiscoveryService.achievements()` 会按当前统计即时派生成就。本次新增 `BadgeService` 后，徽章定义和已获得徽章进入数据表，行为触发时幂等授予；成长中心可以继续展示进度型成就，但个人主页和帖子详情以持久化徽章为准。

替代方案是完全沿用派生成就，不建表。这样实现更快，但无法保存获得时间、无法支持详情页展示、无法做“新获得徽章”通知。

### 4. 热门话题复用 `AnalyticsService`，但公开接口只返回安全字段

`AnalyticsService` 已经有 `trendingTags()` 和 `hotPosts()` 私有方法。实现时应提取为可复用公共只读方法，并在 `PostController` 暴露公开接口。返回内容只包含标签、计数、帖子 ID、标题、热度、互动数等公开信息，不泄露后台统计细节。

替代方案是在前端从后台接口读取，但这会继续触发管理员权限问题，不适合普通用户首页。

### 5. 首页热点词云使用今日话题拼成 `SWJTU`

首页热点词云从公开热门标签接口获取今日或近期热点话题，将词条按权重分布到 `SWJTU` 字母轮廓中。实现时优先使用 SVG/HTML 绝对定位和 CSS transform，Anime.js 负责入场、漂浮、呼吸、权重变化等动效。词云需要提供静态降级：当动画不可用或用户偏好减少动态效果时，仍能显示 `SWJTU` 形态或普通热门标签列表。

替代方案是使用随机圆形词云，但这缺少交大识别度；也不建议引入大型词云库，避免增加打包体积和调试成本。

### 6. Anime.js 作为前端打包依赖而非外部资源

前端在 `frontend/package.json` 中添加 `animejs` 依赖，并通过 ES module import 在前端模块中使用，由 Vite 打包到 `dist`。不得从 CDN 加载 Anime.js，也不得引用 `D:\skills`、`anime-master` 等本地外部目录，确保交付包复制到其他电脑后仍可运行。

替代方案是直接复制第三方源码文件到 assets，但 npm 依赖由构建系统管理更清晰，也更容易在打包时一起产出。

### 7. 动效只使用 transform 与 opacity 等低成本属性

首页卡片、热榜、词云和状态切换动画优先使用 `transform`、`opacity`、`filter` 的轻量变化，避免频繁动画化 `width`、`height`、`top`、`left` 等触发布局重排的属性。动画需要在页面卸载或重新渲染时清理，避免重复绑定和卡顿。

替代方案是大量使用复杂粒子、模糊和滚动联动，但当前课程设计更需要稳定、舒服和可打包。

### 8. 校园身份标签复用 `User.tags` 与 `Tag.category`

系统已有 `user_tags` 多对多关系和 `Tag` 实体，本次不新增用户标签表。兴趣标签统一使用 `Tag.category = "interest"`，用户更新时只替换兴趣标签集合，避免影响帖子标签展示。

替代方案是新增独立 `identity_tags` 表，但会与已有标签体系重复。

### 9. 兴趣圈子作为 P1 后段能力，先保证基础闭环

圈子新增 `Circle`、`CircleMember`，帖子新增可选 `circleId`。发帖可以不选圈子，普通版块流程不受影响。圈子创建需要登录，后续可通过后台审核或状态字段控制可见性。

替代方案是先只做静态圈子入口，但这不满足“创建和加入圈子”的创新要求；因此本次做基础数据模型和核心接口，但排在 P1 末位。

### 10. 数据大屏增强不引入复杂图表依赖

后台数据大屏优先使用现有前端样式和轻量图表实现，报告导出以 HTML/打印友好的结构为主。不新增 ECharts 等依赖，避免打包体积和离线交付风险。

替代方案是接入大型图表库，视觉效果更强，但课程设计交付的可运行稳定性更重要。

## Risks / Trade-offs

- [风险] 同时新增多张表和字段可能影响启动迁移。→ 使用兼容字段默认值，新增关系均为可空或独立表，依赖 JPA 自动迁移前先验证本地启动。
- [风险] 徽章体系和现有成长中心重复展示。→ 明确持久化徽章用于个人主页/帖子详情，成长中心保留进度卡片，必要时由 `BadgeService` 提供统一数据。
- [风险] 采纳奖励被重复发放。→ `accept` 操作只在从未采纳切换到新评论时发放奖励，取消采纳不反复补偿，接口幂等处理。
- [风险] 普通首页调用后台统计导致 403。→ 热门话题使用公开 `/posts/*` 接口，不复用 `/admin/*` 路由。
- [风险] 动画效果过重导致首页卡顿。→ 限制同时运动元素数量，使用 transform/opacity，支持减少动态效果降级。
- [风险] Anime.js 通过外部路径加载导致交付包不可用。→ 只通过 `frontend/package.json` 声明依赖并由 Vite 打包。
- [风险] 圈子功能牵涉导航、发帖、列表筛选，容易扩大范围。→ 将圈子列为 P1 后段，先完成列表、详情、加入、圈内帖子，不做复杂审核、置顶、圈主治理。
- [风险] 数据大屏计算实时聚合可能变慢。→ 先按现有表做轻量聚合和数量限制，避免全表复杂扫描；后续可补缓存。

## Migration Plan

1. 在创新分支创建后先确认当前系统可启动，并保留干净基线提交。
2. 按 P0 到 P1 顺序小步提交：问答采纳、徽章 MVP、模板、热榜、身份标签、数据大屏、圈子。
3. 每个阶段完成后运行后端测试、前端构建和浏览器冒烟测试，重点验证普通用户不触发管理员权限。
4. 数据库迁移通过 JPA `ddl-auto=update` 添加字段/表；新增 bootstrap 数据必须幂等。
5. 如某个 P1 后段功能阻塞，应允许回退该阶段提交，不影响 P0 和前面 P1 能力。

## Open Questions

- 圈子创建是否需要管理员审核，还是登录用户可直接创建后状态为正常。
- 徽章奖励是否只增加贡献值，还是同时写入积分/经验历史。
- 数据大屏报告导出是否需要后端生成 HTML，还是前端基于接口数据生成可打印页面。
