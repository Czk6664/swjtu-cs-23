## 一、访问控制的基本概念

### 1.1 目标
防止对资源（计算/通信/信息资源）进行**未授权访问**，使资源在授权范围内使用——**决定用户能做什么**。

### 1.2 防的是两种"非法"
- 非法用户对系统资源的使用。
- **合法用户对系统资源的非法使用**（越权）。

### 1.3 三元组 (S, A, O)

| 元素 | 名称 | 说明 | 例子 |
|------|------|------|------|
| **S** | 主体 Subject | 发起者，**主动**实体 | 用户、程序、进程 |
| **O** | 客体 Object | 被操作对象，**被动**实体 | 文件、数据库、设备 |
| **A** | 访问 Access | 操作 | 读、写、执行、删除 |

> 主体和客体的关系是**相对的**，角色可以互换。

### 1.4 两个重要过程
1. **鉴别**（第一步）：检验主体身份合法性。
2. **授权**（第二步）：限制用户对资源的访问权限。

### 1.5 标识（Identification）
- 标识是实体身份的计算机表达（如 UNIX 中用户的 UID 是 0~65535 的整数）。
- 作用：**访问控制**（控制是否允许操作）+ **审计**（追踪谁做的）。

### 1.6 最小特权原则
用户和进程只拥有完成职责所需的**最小权限集合**。

### 1.7 AAA
访问控制常和 **鉴别（Authentication）、授权（Authorization）、审计（Audit）** 联系在一起。

## 二、访问控制的实现机制

### 2.1 访问控制矩阵
用矩阵表示：**行=主体，列=客体，矩阵元素=权限**。

```
        客体x        客体y        客体z
主体a   R,W,Own                  R,W
主体b   R           R,W,Own
主体c                            R
主体d   R,W         R,W
```

这个矩阵很大很稀疏，实际中**按行或按列**拆分存储：

### 2.2 ACL vs 能力表（核心对比，必考）

| 对比项 | 访问控制表 ACL | 能力表 Capability List |
|--------|---------------|----------------------|
| 拆分方式 | 按**列**（客体）| 按**行**（主体）|
| 关联对象 | **客体** | **主体** |
| 保存位置 | 客体 | 主体 |
| 记录内容 | 谁能访问这个客体 | 这个主体能访问什么 |
| 浏览客体权限 | **容易** | 困难 |
| 浏览主体权限 | 困难 | **容易** |
| 权限传递 | 困难 | 容易 |
| 权限回收 | 容易 | 困难 |
| 适用系统 | 集中式 | 分布式 |

> 记忆：**ACL 贴在"东西"上（客体），能力表揣在"人"身上（主体）。**

**ACL 的问题**：主体数量多时表很庞大，人员变动时修改困难。**解决**：引入**用户组**（如 `*.INFO.rw` 表示 INFO 组所有用户有读写权限）。

### 2.3 其他实现
- **访问控制安全标签**：给主体和客体打安全级别标签（绝密/机密/秘密/未分类）。
- **锁与钥匙**：客体用密钥加密（锁），主体有解密钥匙，兼具 ACL 和能力表特征，有动态性。

## 三、访问控制模型分类总览

```
访问控制模型
├── 自主访问控制 DAC ── 访问矩阵、ACL、能力表
├── 强制访问控制 MAC
│   ├── 保密性模型：Bell-LaPadula (BLP)
│   ├── 完整性模型：Biba、Clark-Wilson
│   └── 混合策略：Chinese Wall
└── 基于角色的访问控制 RBAC
```

## 四、自主访问控制 DAC（Discretionary Access Control）

### 4.1 含义
允许客体的**属主（创建者）自己决定**主体对该客体的访问权限。

### 4.2 特点
- 灵活、易用、可扩展，**常用于商业系统**。
- 是**分布式授权管理**模式。
- **缺点：安全性不高**。

### 4.3 两大安全隐患
1. **无法控制信息流动**：用户 A 可把对客体 O 的权限传给 B，使本来无权的 B 也能访问 O。
2. **特洛伊木马威胁**：木马附在合法程序中，以你的权限偷偷做坏事（如把 `/etc/passwd` 邮件发给黑客）。

### 4.4 实例
- **Linux 文件权限**：`drwxr-x--x`，三种权限 r(读)/w(写)/x(执行)，四类用户 root/所有者/所属组/其他用户。用 `chmod`、`chown` 修改。
- **Windows**：通过安全标识、访问令牌、安全描述符、自主访问控制表实现。

## 五、强制访问控制 MAC（Mandatory Access Control）

### 5.1 含义
由**系统管理员统一**按强制策略控制，**客体属主无权修改**。主体和客体都分配**固定的安全级别**。

- 安全级别：`未分类 < 秘密 < 机密 < 绝密`（普密<秘密<机密<绝密）。
- 应用于**军事等高安全要求**系统。
- 可与 DAC 结合使用。

### 5.2 四种访问方式（关键）
"写"代表信息流动方向：

| 操作 | 含义 |
|------|------|
| 下读 (Read Down) | 主体级别 > 客体级别，允许读 |
| 上读 (Read Up) | 主体级别 < 客体级别，允许读 |
| 下写 (Write Down) | 主体级别 > 客体级别，允许写 |
| 上写 (Write Up) | 主体级别 < 客体级别，允许写 |

两种组合 → 两种目标：
- **下读 / 上写** → 信息从低流向高 → 保证**机密性**。
- **上读 / 下写** → 实现**完整性**。

### 5.3 BLP 模型 vs Biba 模型（核心，必考）

这两个模型是**数学上对偶**的关系：

| 模型 | 时间 | 保护目标 | 规则 | 应用 |
|------|------|---------|------|------|
| **Bell-LaPadula (BLP)** | 1973 | **机密性** | **下读 / 上写**（不上读、不下写）| 防火墙 |
| **Biba** | 1977 | **完整性** | **上读 / 下写**（不下读、不上写）| Web 服务器 |

**BLP（保机密性）详解：**
- **不上读**：低级别用户不能读高密级信息（防泄密）。
- **不下写**：高级别用户不能把机密写入低密级区（防泄密）。
- 信息只能**从低流向高**。
- 应用例子：**防火墙**隔离内外网——不上读（阻止 Internet 访问内网）、不下写（不允许敏感数据流向 Internet）。

**Biba（保完整性）详解：**
- **不下读**：高完整性主体不读低完整性数据（防被污染）。
- **不上写**：低完整性主体不能写高完整性数据（防篡改）。
- 应用例子：**Web 服务器**——Internet 用户只能读服务器数据，不能改它。

> 记忆口诀：**BLP 保密——下读上写；Biba 完整——上读下写。**

### 5.4 其他强制模型
- **Clark-Wilson**（1987）：以事务处理为基础的完整性模型，用于商业系统。
- **Chinese Wall**（1989）：同时考虑保密性与完整性，解决**商业利益冲突**。

### 5.5 DAC vs MAC 对比

| | DAC | MAC |
|------|-----|-----|
| 粒度 | 细 | 大 |
| 灵活性 | 高 | 不高 |
| 安全性 | 低 | **强** |
| 谁控制 | 客体属主 | 系统管理员 |

## 六、基于角色的访问控制 RBAC（重点，必考）

### 6.1 核心思想
不直接给用户分配权限，而是通过**角色**这个中间层：

> **用户 → 角色 → 权限**

一个用户必须扮演某种角色，并**激活**它，才能访问对象。

### 6.2 核心元素

| 元素 | 说明 |
|------|------|
| **用户 (User)** | 访问资源的主体 |
| **角色 (Role)** | 一种岗位，代表资格、权利、责任 |
| **权限 (Permission)** | 对客体的操作权力（权限=操作+客体）|
| **会话 (Session)** | 用户访问时建立的会话，一次会话可激活多个角色 |

**两个关联：**
- **用户分配（UA）**：用户 ↔ 角色。
- **权限分配（PA）**：角色 ↔ 权限。

### 6.3 多对多关系
- 一个用户可有多个角色，一个角色可给多个用户。
- 一个角色可有多个权限，一个权限可给多个角色。

### 6.4 银行实例

| 角色 | 权限 |
|------|------|
| 出纳员 | 修改顾客账号记录 |
| 分行管理者 | 修改记录 + 创建/终止账号 |
| 顾客 | 查询自己的账号 |
| 系统管理者 | 开关系统，但不能读/改账号信息 |
| 审计员 | 读任何数据，但不能修改 |

> 好处：来个新出纳员，直接分配"出纳员"角色就行，不用一项项设权限。

### 6.5 高级特性
- **角色继承**：子角色继承父角色的许可（避免重复设置）。
- **角色互斥**：某些操作一个用户不能同时做（静态/动态互斥）—— 实现**职责分离**。
- **角色基数限制**：某角色在某时段只能由一定人数占用。

### 6.6 RBAC96 系列模型

| 模型 | 内容 |
|------|------|
| **RBAC0** | 核心部分 |
| **RBAC1** | RBAC0 + **角色继承（RH）** |
| **RBAC2** | RBAC0 + **约束（责任分离）** |
| **RBAC3** | RBAC1 + RBAC2 = 完整模型 |

### 6.7 RBAC 的优点
- 便于授权管理（人员变动只改角色分配）。
- 便于处理工作分级。
- 容易实现**最小特权、职责分离**等安全策略。
- 便于任务分担。

## 七、操作系统中的访问控制 & 评估标准

- **TCSEC（橘皮书）**：1985 年美国国防部发布的《可信计算机系统评估标准》，分 **A/B/C/D 四类八级**，D 最低 A 最高。
  - 大多数通用操作系统（Windows、Linux）是 **C2 级**（控制访问保护级）。
- **彩虹系列**：橘皮书的一系列补充标准。
- **CC（通用准则）**：1998 年起取代 TCSEC 和 ITSEC，是国际通用的 IT 安全评估标准（2005 年正式取代 TCSEC）。
- **Windows / Linux 都用自主访问控制（DAC）**。

### 集中式 vs 非集中式访问控制
- **集中式**：RADIUS、TACACS、TACACS+、Diameter。
- **非集中式**：**域（Domain）**——一个信任范围，跨域访问需建立**信任关系**（可单向或双向）。

## 八、本章小结

- 访问控制解决"**你能干什么**"，三元组 **(S, A, O)**，先鉴别后授权，遵循**最小特权**。
- 实现机制：访问矩阵 → **ACL（贴客体）/ 能力表（贴主体）**。
- 三大模型：
  - **DAC**：属主自己定，灵活但安全性低，怕木马。
  - **MAC**：管理员强制定，安全性强。**BLP 保密性（下读上写）、Biba 完整性（上读下写）**。
  - **RBAC**：用户→角色→权限，便于管理，支持继承/互斥/职责分离。
- 评估标准：TCSEC（橘皮书，通用 OS 为 C2 级）→ CC 通用准则。
