调度器原理：预选与优选
01
p  kube-scheduler 调度流程
n 调度（Scheduling）是指将未绑定节点的Pod分配到合适Worker节点的过程。
kube-scheduler通过两阶段筛选完成调度决策。
p 两阶段调度
p 预选常见规则
阶段
名称
说明
阶段1
预选（Filtering / Predicates）排除不满足条件的节点，得到候选节点列表
阶段2
优选（Scoring / Priorities）
对候选节点评分（0-100），选择得分最高的节点
规则
说明
PodFitsResources
节点剩余资源≥Pod的Request
PodFitsHostPorts
节点端口无冲突
MatchNodeSelector
节点标签匹配Pod的nodeSelector
NoTaintUnlessTolerated
节点Taint需被Pod Toleration匹配
CheckNodeMemoryPressure 节点无内存压力
p 优选常见规则
规则
说明
LeastRequestedPriority
优先选择剩余资源最多的节点
（分散调度）
BalancedResourceAllocation
CPU和内存使用率更均衡的节点
得分更高
NodeAffinityPriority
匹配亲和性规则的节点得分更
高
InterPodAffinityPriority
满足Pod亲和性的节点得分更高

污点与容忍（Taints & Tolerations）
01
p 污点（Taint）是节点的属性，表示该节点拒绝接受特定Pod的调度。容忍（Toleration）是Pod的
属性，表示该Pod可以容忍某个节点的污点。
n 亲和性= Pod主动选择节点（"我想去哪"）
n 污点/容忍= 节点排斥Pod（"谁不能来"），Pod可声明豁免
p Taint效果类型
p 操作命令
Effect
说明
NoSchedule
不调度新Pod到该节点（已运行的Pod不受影响）
PreferNoSchedule
尽量不调度，但不保证
NoExecute
不调度新Pod，且驱逐已运行的不匹配Pod
p 典型场景
n GPU节点：Taint为`gpu=true:NoSchedule`，只
有需要GPU的Pod才容忍该Taint
n Master节点：默认Taint `node-
role.kubernetes.io/master:NoSchedule`，避免业
务Pod调度到Master

StatefulSet有状态应用管理
02
p StatefulSet是Kubernetes中管理有状态应用的工作负载控制器。与Deployment不同，
StatefulSet为每个Pod提供稳定的网络标识和持久化存储，确保Pod的身份在重建后保持不变。
p StatefulSet vs Deployment
特性
Deployment
StatefulSet
Pod名称
随机后缀（web-7d9f8c-xk2l3）有序固定（web-0, web-1, web-2）
网络标识
无稳定标识
稳定的DNS名称（web-0.web-svc）
存储
Pod重建后存储丢失
每个Pod绑定独立的PVC，重建后保留
启动/停止顺序并行
有序（0→1→2启动，2→1→0停止）
适用场景
无状态应用（Web API）
有状态应用（数据库、消息队列）

n Pod →PVC（存储请求）→PV（存储资源）→底层存储（云盘/NFS/Ceph）

n 回收策略

定义与背景
05
p 问题：微服务通信的复杂性，随着微服务数量增长，服务间通信面临诸多挑战：
n 流量管理（负载均衡、重试、超时）
n 安全（加密通信、身份认证）
n 可观测性（链路追踪、指标、日志）
传统方式：在每个服务中嵌入SDK（如Spring Cloud、Hystrix）——语言绑定，侵入性强
p Service Mesh定义
n 服务网格（Service Mesh）是一个专门用于处理服务间通信的基础设施层。它通过在每
个服务旁部署一个轻量级网络代理（Sidecar），以透明的方式处理服务发现、负载均
衡、故障恢复、指标采集和安全通信。——William Morgan, Buoyant CEO, 2017
n 核心价值
传统SDK方式
Service Mesh
业务代码中嵌入通信逻辑
通信逻辑下沉到基础设施
语言绑定（Java SDK无法用于Go服务）语言无关（Sidecar代理）
升级SDK需要修改并重新部署所有服务升级代理不影响业务代码
每个服务单独实现熔断/限流
统一的策略管理

金丝雀发布（Canary Release）与流量灰度
05
p 金丝雀发布是一种渐进式发布策略，先将少量流量导向新版本，观察无异常后逐步扩大新
版本的流量比例，直到全量切换。
p Istio实现金丝雀发布
n 阶段1: v1=100%, v2=0%    →部署v2，不导入流量
n 阶段2: v1=90%,  v2=10%   →10%流量到v2，观察指标
n 阶段3: v1=50%,  v2=50%   →扩大到50%
n 阶段4: v1=0%,   v2=100%  →全量切换到v2
p 对比其他发布策略
策略
原理
风险
回滚速度
滚动更新
逐步替换旧Pod
中等
慢（需回滚Deployment）
蓝绿部署
两套完整环境切换
低
快（切换路由）
金丝雀发布
按比例分流
最低
最快（调整权重）
A/B测试
按条件（用户/地区）分流

快
