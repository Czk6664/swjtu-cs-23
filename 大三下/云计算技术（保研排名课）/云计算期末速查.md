# 云计算期末速查

---

## 一、云计算概述

**NIST 定义**：云计算是一种计算模型，允许无处不在、便捷、按需的网络访问共享可配置计算资源池，资源能以最小管理代价快速配置和发布。

**NIST 五大特征**：
1. **按需自服务**：用户自动配置计算能力，无需人工交互（API 调用）
2. **弹性扩展**：快速横向扩展（Scale-out）或缩减（Scale-in），对消费者看起来能力无限
3. **资源池化**：多租户（multi-tenancy），上万台服务器融合成资源池，互相隔离
4. **网络访问**：通过标准机制在网络上获取，支持异构客户端
5. **按量计费**：资源利用率从传统 10%~15% 提升至 80%（5~7倍）

**大数据 4V+1C**：Volume（PB/EB级）、Velocity（极速响应）、Variety（结构化/半结构化/非结构化）、Value（价值密度低，海量沙砾中淘金）、Complexity（分析难度指数上升）

**服务模式对比**（房屋类比：IaaS=聘请工人盖房，PaaS=租房自带水电，SaaS=拎包入住）：

| 模型 | 用户管理 | 提供商管理 | 典型产品 |
|------|---------|-----------|---------|
| IaaS | OS+中间件+应用+数据 | 硬件+网络+虚拟化 | Amazon EC2/S3、ECS |
| PaaS | 应用+数据 | 硬件~运行时全栈 | GAE、Azure、Hadoop |
| SaaS | 数据（仅数据） | 全部 | Google Apps、Salesforce |

**新兴服务模式**：FaaS（函数即服务，按调用计费）、CaaS（容器即服务）

**部署模式**：

| 部署模式 | 优点 | 缺点 | 适用场景 |
|---------|------|------|---------|
| 公有云 | 零初始成本、极致弹性 | 数据控制权较弱 | 互联网应用、初创企业 |
| 私有云 | 最高安全与隐私、满足合规 | 成本极高、需专门IT团队 | 政府、大型金融机构 |
| 混合云 | 兼顾安全与弹性 | 架构最复杂 | 核心数据本地+突发溢出公有云 |
| 社区云 | 多方均摊、满足行业标准 | 协调成本高 | 医疗联盟、高校科研 |

**三大基础设施**：
- 计算：虚拟化（Hypervisor，强隔离）、容器（共享内核，轻量）
- 存储：分布式存储（多副本）、对象存储（扁平命名空间，S3/OSS，URL访问）
- 网络：SDN（控制面与数据面分离）、弹性负载均衡

**数据中心选址关键**：最大物理开销是电力和制冷；选址寻找便宜电力+自然冷源（如 BAT 在贵州山区建数据中心）；超大规模：单管理员可管超1000台服务器

## 二、虚拟化与 Docker

### 虚拟化

**定义**：将计算机各种实体资源（CPU、内存、磁盘、网络）予以抽象、转换后呈现，可供分割组合为多个虚拟计算机环境。虚拟机从软件角度看 = 真实机器。

**Hypervisor/VMM 职责**：(1) 物理资源→虚拟资源的逻辑映射 (2) 虚拟机上下文隔离，保障多租户安全

**软件虚拟化 vs 硬件虚拟化**：
- 软件：VMM 捕获翻译特权指令，兼容性好但开销大，实现复杂（QEMU、VMware）
- 硬件：CPU 架构级支持，增加专门给虚拟机的特权指令通道（Ring-1），无需软件干预，性能极高（Intel VT-x、AMD-v）

**Hypervisor 两种架构**：

| | 寄居型（Hosted） | 裸机型（Bare-metal） |
|---|---|---|
| 位置 | 运行在 Host OS 之上 | 直接运行在硬件上 |
| 代表 | VMware Workstation | KVM |
| 优点 | 兼容性好、部署方便 | 性能接近物理机 |
| 缺点 | I/O 经 Host OS 转发，开销大 | 硬件兼容要求严格 |

**CPU 虚拟化**：
- 软件虚拟化：VMM 截获 Ring0 指令并转化
- 硬件虚拟化（VT-x）：Root 模式（VMM）+ Non-Root 模式（VM），Non-Root 也有 Ring0-3，仅影响物理硬件的指令才 VM Exit 给 VMM

**内存虚拟化**：虚拟地址 → Guest 伪物理地址 → 物理地址
- **影子页表（SPT）**：Hypervisor 软件维护，拦截同步，慢
- **扩展页表（EPT）**：MMU 硬件两次转换，快

### 容器 vs 虚拟机

| | 虚拟机 | 容器 |
|---|---|---|
| OS | 完整 Guest OS | 共享宿主内核 |
| 启动 | 分钟级 | 秒/毫秒级 |
| 占用 | GB 级 | MB 级 |
| 性能损耗 | 较大（Hypervisor） | 极小（原生） |
| 隔离 | 硬件级，强 | 进程级/Namespace，较弱 |

### Docker 核心

**架构**：Client → Docker Daemon → Registry

**Namespace 隔离**（6 种）：

| Namespace | 作用 |
|-----------|------|
| PID | 进程隔离 |
| NET | 网络隔离 |
| MNT | 挂载/文件系统隔离 |
| UTS | 主机名隔离 |
| IPC | 进程间通信隔离 |
| USER | 用户权限隔离 |

Linux API：`clone(CLONE_NEWPID|CLONE_NEWNET)`

**Cgroup**：内核级资源限制（control group），控制一组进程的CPU/内存/IO使用，路径 `/sys/fs/cgroup`

**UnionFS**：将分属不同物理位置的只读目录合并挂载至虚拟文件系统，容器启动后在最顶端附加可写层；相同基础层服务器仅存一次

**镜像分层**：容器 = 只读镜像层 + 可写容器层（所有文件操作均发生于顶部可写层）

**虚拟化优势**：资源利用率提升、运维成本降低、方便升级迁移、安全隔离环境

**虚拟化局限**：资源冗余（每VM跑完整OS）、弹性迟缓（分钟级启动）、交付困难（环境不一致）

## 三、云原生与微服务

### 云原生四要素

| 要素 | 定义 | 核心价值 |
|------|------|---------|
| 容器化 | 应用及依赖打包为容器镜像 | 可移植性、快速部署 |
| 微服务 | 拆分为独立服务，专注单一业务功能 | 独立开发/部署/扩展 |
| 声明式 API | 用户声明期望状态，系统自动实现维护 | 简化运维、自动化管理 |
| 不可变基础设施 | 一旦部署不再修改，更新通过替换 | 环境一致性、可审计性 |

**不可变基础设施**：不SSH登录修改，更新 = 构建新镜像 + 滚动替换（回滚=用旧镜像，可审计=镜像版本化）

**云原生 vs 传统**：

| 维度 | 传统 | 云原生 |
|------|------|--------|
| 架构 | 单体 Monolith | 微服务 |
| 部署单元 | WAR/EAR 包 | 容器镜像→K8s |
| 部署频率 | 每月/季度 | 每天多次 |
| 扩展方式 | 垂直（加CPU/内存） | 水平（加实例） |
| 环境管理 | 手动配置脚本 | 声明式 IaC |
| 故障处理 | 人工排查恢复 | 自动检测恢复 |
| 状态管理 | 有状态 Session | 无状态 Stateless |

**微服务核心特征**：单一职责、独立部署、独立扩展、技术异构、轻量通信、去中心化治理、去中心化数据（Database per Service）、容错设计

**拆分策略**：
1. **按业务领域（DDD）**：基于限界上下文（Bounded Context），如电商→用户/商品/订单/支付/库存服务
2. **按数据边界**：每服务独立DB，服务间不直接访问对方数据库，通过API或事件交换
3. **按变更频率**：变更频率高的功能独立为服务

### 微服务通信

| | REST | gRPC |
|---|---|---|
| 协议 | HTTP/JSON | HTTP/2 + Protobuf |
| 优点 | 简单通用 | 高性能、强类型、双向流 |
| 场景 | 对外 API | 内部服务间调用 |

**异步**：消息队列（Kafka/RabbitMQ），解耦 + 削峰

### 服务发现

**为什么需要**：微服务中实例IP/端口动态变化，随时扩缩容/重启/迁移，硬编码行不通

- **客户端发现**：客户端直接查注册中心获取实例列表 + 本地负载均衡（Eureka+Ribbon）。优点：无额外网络跳转。缺点：客户端需集成发现逻辑
- **服务端发现**：请求→负载均衡器/网关→网关查注册中心（K8s Service+kube-proxy）。优点：客户端逻辑极简，语言无关。缺点：多一跳延迟，网关可能成单点

| 注册中心 | 一致性 | 特点 |
|---------|--------|------|
| etcd | Raft 强一致 | K8s 默认 |
| Consul | Raft | 内置健康检查 |
| ZooKeeper | ZAB 强一致 | 老牌 |
| Nacos | AP/CP 可切 | 阿里，发现+配置 |

### 负载均衡

| 算法 | 原理 | 场景 |
|------|------|------|
| 轮询 | 依次分发 | 性能相同 |
| 加权轮询 | 按权重比例 | 性能不均 |
| 最少连接 | 连接数最少的 | 长连接 |
| 一致性哈希 | 相同请求→相同实例 | 缓存命中 |
| IP哈希 | 按客户端IP | Session亲和 |

L4（TCP/UDP层，基于IP+端口）vs L7（HTTP层，基于URL/Header）

### 熔断器模式（Circuit Breaker）

**问题：级联故障/雪崩**：服务A→B→C，C崩溃→B线程阻塞→线程池耗尽→A同样阻塞

**三状态**：

| 状态 | 说明 | 行为 |
|------|------|------|
| Closed | 正常 | 请求正常转发，统计失败率 |
| Open | 熔断触发 | 所有请求直接返回降级响应 |
| Half-Open | 尝试恢复 | 允许少量请求通过，成功→Closed，失败→Open |

```
Closed --失败率>=阈值--> Open --超时时间到--> Half-Open
  ^                                          |
  +------探测成功------<--------+             |
                                +--探测失败--> Open
```

| 参数 | 说明 | 典型值 |
|------|------|--------|
| 失败率阈值 | 触发熔断的失败比例 | 50% |
| 统计窗口 | 统计失败率的时间窗口 | 10s |
| 最少请求数 | 触发熔断需要的最少请求量 | 20次 |
| 熔断持续时间 | Open 状态持续时间 | 30s |
| 半开允许数 | Half-Open 允许通过的请求数 | 5次 |

**其他容错模式**：重试Retry（指数退避）、超时Timeout、舱壁Bulkhead（独立线程池）、降级Fallback（默认值/缓存）

**降级策略**：返回默认值、返回缓存、功能裁剪（关非核心）、流量排队（秒杀）

### API 网关

统一入口：请求路由、认证鉴权、限流熔断、负载均衡、协议转换（REST→gRPC）、请求聚合、日志监控

### 限流算法

| 算法 | 核心 | 特点 |
|------|------|------|
| 固定窗口 | 窗口内计数 | 边界突刺 |
| 滑动窗口 | 滑动计数 | 更平滑 |
| 令牌桶 | 固定速率生成令牌 | **允许突发** |
| 漏桶 | 固定速率流出 | **严格平滑** |

### Docker Compose

顶级 key：services、networks、volumes、configs、secrets

同一网络容器通过**服务名**直接通信（Docker 内置 DNS）

**服务配置关键选项**：image、build、ports、environment、volumes、depends_on、networks、deploy、healthcheck

## 四、Kubernetes 基础

### 架构：Master-Worker 模型

**Control Plane（Master）**：集群的"大脑"，负责决策
1. **kube-apiserver**：唯一入口，所有组件只和它通信，无状态可水平扩展。职责：认证、授权、准入控制
2. **etcd**：分布式KV数据库，保存集群所有状态，基于Raft协议，通常奇数部署(3/5个)，只有API Server能直接访问
3. **controller-manager**：控制循环(Control Loop)，不断比较"期望状态" vs "实际状态"，逻辑：`if current != desired then fix_it()`
4. **scheduler**：给新Pod找最合适节点。预选(Filtering)排除→优选(Scoring)打分

**Worker Nodes**：集群的"手脚"，负责干活
1. **kubelet**：节点代理人，接收API Server指令，管Pod生命周期，调用CRI启动容器
2. **kube-proxy**：维护网络规则(iptables/IPVS)，实现Service负载均衡和流量转发
3. **Container Runtime**：containerd、CRI-O（Docker已被垫片化）

### YAML 四必填

```yaml
apiVersion  kind  metadata  spec
```

### Namespace

逻辑隔离：default（默认）、kube-system（系统组件）、dev/prod（自定义）

### Pod

**为什么不直接管理容器**：容器间往往需要紧密协作（日志收集、代理），Pod 提供共享环境简化协作

- **共享网络**：Pod内所有容器共用一个IP，容器间通过localhost通信
- **共享存储**：容器间通过挂载同一个Volume交换文件
- **Labels & Selectors**：Service 通过标签选择器找到后端 Pod

**资源管理**：
- **Requests**：调度保底（节点最少要有这么多资源才能调度上去）
- **Limits**：运行上限（超CPU限流，超Memory OOM Kill）

**Pod QoS 驱逐优先级**：
1. **Guaranteed**（头等舱）：req==limit，最后被驱逐
2. **Burstable**（商务舱）：req<limit，资源紧张时可能被驱逐
3. **BestEffort**（经济舱）：未设资源限制，最先被杀

**探针（Probes）**：

| 探针 | 作用 | 失败后果 |
|------|------|---------|
| Liveness | 存活检测（如死锁） | 重启容器 |
| Readiness | 就绪检测（启动中） | 切断流量（从Service移除） |
| Startup | 启动检测（慢启动应用） | 抑制其他探针 |

**生命周期**：Pending（等调度/拉镜像）→ Running → Succeeded/Failed/Unknown（与节点失联）

**Init Containers**：主容器启动前按序执行，全部成功后主容器才启动（初始化配置、等待DB就绪）

### Service 类型

| 类型 | 访问范围 | 端口 |
|------|---------|------|
| ClusterIP | 集群内 | — |
| NodePort | 节点IP:30000-32767 | 外部可访问 |
| LoadBalancer | 云 LB 公网 IP | 外部可访问 |

**为什么需要Service**：Pod是短暂的，重启后IP会变，Service提供VIP屏蔽动态变化

**DNS**：K8s内置CoreDNS，`<service>.<namespace>.svc.cluster.local`

**Ingress**：L7路由（Service只能L4基于IP/Port），基于域名(Host)/路径(Path)转发，节省公网IP（一个IP代理多个服务），支持SSL/TLS终止

### Deployment

核心功能：维持副本数（声明3个就永远保持3个）、滚动更新（先起新后停旧）、版本回滚（一键回到过去）
- **maxSurge**：允许比期望多几个 | **maxUnavailable**：允许比期望少几个
- **HPA（水平自动扩缩容）**：根据CPU/内存利用率自动调整Pod数量
- 回滚：`kubectl rollout undo deployment/web`
- 扩容：`kubectl scale deployment/web --replicas=10`

**kubectl 常用**：`describe`（详情报错）、`logs`（日志）、`exec -it -- sh`（进容器）、`apply -f`（声明式创建）、`get`（查看）、`delete -f`（删除）

## 五、K8s 深入与服务网格

### 调度

**预选（Filtering）** - 排除不合格节点：

| 规则 | 说明 |
|------|------|
| PodFitsResources | 节点剩余资源 >= Pod 的 Request |
| PodFitsHostPorts | 节点端口无冲突 |
| MatchNodeSelector | 节点标签匹配 Pod 的 nodeSelector |
| NoTaintUnlessTolerated | 节点 Taint 需被 Pod Toleration 匹配 |
| CheckNodeMemoryPressure | 节点无内存压力 |

**优选（Scoring）** - 给剩余节点打分：

| 规则 | 说明 |
|------|------|
| LeastRequestedPriority | 优先选剩余资源最多的节点（分散调度） |
| BalancedResourceAllocation | CPU和内存使用率更均衡的得分更高 |
| NodeAffinityPriority | 匹配亲和性规则的得分更高 |

### 亲和性与污点

**亲和性 = Pod主动选择（"我想去哪"）**：

| 机制 | 方向 | 效果 |
|------|------|------|
| Node Affinity | Pod→Node | required（硬约束，必须满足）/ preferred（软约束，优先满足） |
| Pod Affinity | Pod→Pod | 同节点/区域部署（提升通信效率） |
| Pod Anti-Affinity | Pod↔Pod | 不同节点（容灾分散） |

**污点/容忍 = 节点排斥Pod（"谁不能来"）**，Pod可声明Toleration豁免：

| Effect | 说明 |
|--------|------|
| NoSchedule | 不调度新Pod到该节点（已运行不受影响） |
| PreferNoSchedule | 尽量不调度，但不保证 |
| NoExecute | 不调度新Pod，且**驱逐已运行**的不匹配Pod |

典型：GPU 节点 `gpu=true:NoSchedule`（只有需要GPU的Pod才容忍）；Master 默认 `node-role.kubernetes.io/master:NoSchedule`

### ResourceQuota vs LimitRange

| | ResourceQuota | LimitRange |
|---|---|---|
| 范围 | 命名空间总量 | 单个Pod/容器 |
| 功能 | 限制总资源、对象数量 | 设置默认值、范围 |

### StatefulSet vs Deployment

| | Deployment | StatefulSet |
|---|---|---|
| Pod 名 | 随机后缀 | 有序固定（web-0,1,2） |
| 网络标识 | 无 | 稳定 DNS（web-0.svc） |
| 存储 | 重建丢失 | 独立 PVC 保留 |
| 顺序 | 并行 | 有序启停 |
| 场景 | 无状态 Web | 数据库、MQ |

**Headless Service**：`clusterIP: None`，返回 Pod IP 列表

**VolumeClaimTemplates**：StatefulSet 每个 Pod 独立 PVC

### ConfigMap & Secret

- ConfigMap：非敏感，使用方式：环境变量注入 / 卷挂载为文件 / 命令行参数。卷挂载约1分钟热更新，环境变量需重启
- Secret：Base64 编码（非加密），挂载为 tmpfs 不落盘
  - 类型：Opaque（通用）、tls（TLS证书）、dockerconfigjson（Registry认证）、service-account-token

### 存储

**三层架构**：Pod → PVC（存储请求声明：大小、访问模式）→ PV（集群级存储资源）→ 底层存储（云盘/NFS/Ceph）

| 访问模式 | 说明 |
|---------|------|
| RWO | 单节点读写 |
| ROX | 多节点只读 |
| RWX | 多节点读写（需 NFS/CephFS） |

回收策略：Retain（保留）、Delete（删除）

**动态供给**：StorageClass + Provisioner → 自动创建 PV

### 服务网格（Service Mesh）

**定义**：专门处理服务间通信的基础设施层，在每个服务旁部署Sidecar代理，透明处理服务发现/负载均衡/故障恢复/指标采集/安全通信

| 传统SDK | Service Mesh |
|---------|-------------|
| 业务代码嵌入通信逻辑 | 通信下沉基础设施 |
| 语言绑定 | 语言无关 |
| 升级SDK需重部署所有服务 | 升级代理不影响业务 |

**Istio 架构**：

| 组件 | 功能 |
|------|------|
| istiod | 统一控制面（合并Pilot/Citadel/Galley） |

| Envoy | 数据面Sidecar代理，所有流量经过Envoy（L4/L7路由/负载均衡/熔断/重试/超时/TLS/可观测性） |

**mTLS**：双向 TLS，Citadel 自动签发 X.509 证书，应用无感

**Istio 金丝雀发布四阶段**：v1=100%/v2=0%（部署观察）→ v1=90%/v2=10% → v1=50%/v2=50% → v1=0%/v2=100%（全量切换）

## 六、消息队列

**MQ 核心作用**：
- **异步解耦**：发送方无需等待接收方处理，降低系统耦合
- **流量削峰**：缓冲突发流量，保护下游服务不被压垮
- **最终一致性**：通过可靠消息传递达成系统最终一致

**消息模型**：点对点Queue（每条消息只被一个消费者消费）vs 发布/订阅Topic（消息可被多个消费者同时接收）

### 投递语义

| 语义 | 说明 | 场景 |
|------|------|------|
| At Most Once | 可能丢，不重复 | 日志 |
| At Least Once | 不丢，可能重复（需幂等） | 订单 |
| Exactly Once | 不丢不重，实现最复杂 | 金融 |

**消息重复原因**：生产者发送后 Broker 未返回 ACK；消费者消费后返回 ACK 失败

**顺序性**：单分区/单队列内有序；多分区无全局顺序；增加分区→增加并行但牺牲全局顺序

### Kafka

| 组件 | 说明 | 关键特性 |
|------|------|---------|
| Broker | Kafka集群中的服务器节点 | 水平扩展、高可用（副本机制） |
| Topic | 消息的逻辑标识 | 支持多个分区、可配置副本数 |
| Partition | Topic的物理分片 | 每个Partition是append-only log，分区内有序 |
| Offset | Partition中每条记录的唯一递增序号 | 不可变，由Kafka自动维护 |
| Consumer Group | 一组消费者实例 | 组内负载均衡、组间互不影响（独立消费） |

- Topic 的多个 Partition 分布在多个 Broker 中
- 一个 Partition 内部消息有序，一个 Topic 跨 Partition 无序
- 常结合 Flink/Spark Streaming 做实时流处理

### RabbitMQ

基于 AMQP 协议（开放标准，可靠/可扩展/灵活）：Producer → Exchange → Binding → Queue → Consumer

**Exchange 类型**：

| 类型 | 路由方式 | 场景 |
|------|---------|------|
| Direct | Routing Key 精确匹配 | 精确分发 |
| Fanout | 广播所有绑定队列 | 通知 |
| Topic | 模式匹配（`*`一词，`#`多词） | 事件分类 |

Topic 通配符示例：`order.*`（匹配 order.created）、`*.error`（匹配 db.error）、`order.#`（匹配所有 order 开头）

**ACK**：消费者确认 | **持久化**：写入磁盘 | **DLQ**：TTL过期/队列满/被拒→死信队列

**延迟消息**：延迟交换机（Delayed Message Exchange），指定时间后消费

## 七、分布式存储

### CAP 定理

| 特性 | 含义 |
|------|------|
| C 一致性 | 所有节点同一时刻看到相同数据 |
| A 可用性 | 每个请求都收到响应（不保证最新） |
| P 分区容错 | 节点间通信故障时系统仍可运行 |

三者最多满足两个，P在真实环境中无法避免。分区发生时：选C=拒绝服务保一致；选A=继续服务允许旧数据

| 选择 | 分区时行为 | 典型 |
|------|-----------|------|
| CP | 拒绝服务保一致 | ZooKeeper、etcd、HBase |
| AP | 继续服务允许不一致 | Cassandra、DynamoDB |

**PACELC**：分区时选 A/C？正常时选 L(延迟)/C(一致)？

| 系统 | 分区时 | 正常时 |
|------|--------|--------|
| DynamoDB | PA | EL |
| Cassandra | PA | EL |
| HBase | PC | EC |
| MongoDB | PA | EC |

### BASE 理论

BA（基本可用）+ S（软状态，允许短暂不一致）+ E（最终一致性）

| ACID | BASE |
|------|------|
| 强一致 | 最终一致 |
| 银行转账 | 社交动态 |

### 数据分片

**为什么需要**：容量瓶颈（单机磁盘有限）、性能瓶颈（高并发）、可用性风险（单点故障）

| 策略 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 哈希分片 | `node_id = hash(key) % N` | 数据分布均匀 | 节点变化大量迁移(3→4台约75%)，不支持范围查询。代表：Redis Cluster(CRC16%16384) |
| 一致性哈希 | 哈希空间组成虚拟圆环(0~2^32-1)，Key顺时针找最近节点 | 扩缩容只影响 1/N 的数据 | 可能不均匀→虚拟节点解决。代表：Cassandra、DynamoDB |
| 范围分片 | 按 key 值范围划分到不同节点 | 范围查询高效，数据有序存储 | 数据倾斜产生热点。代表：HBase/Spanner/BigTable |

**虚拟节点**：每个物理节点在哈希环上注册100~200个"分身"均匀散落，解决数据不均匀

**向量时钟**：记录每节点写入次数，用于检测并发写入和冲突。一个版本在所有维度上>=另一个→是后继版本；两个版本互不包含→并发冲突！需应用层合并。能精确检测（不是解决）冲突

### 存储类型对比

| | KV | 文档 | 列族 | 图 | NewSQL |
|---|---|---|---|---|---|
| 代表 | Redis | MongoDB | HBase/Cassandra | Neo4j | TiDB/Spanner |
| 一致性 | AP/CP | 可调 | CP/AP | CP | CP |
| 场景 | 缓存 | 内容管理 | 时序/日志 | 社交/知识图谱 | 金融/电商 |

另：时序数据库（InfluxDB/TimescaleDB，AP，监控/IoT）

**列族选型**：有 Hadoop+要强一致→HBase；全球部署+高可用→Cassandra；GCP→Bigtable

| | HBase | Cassandra | Bigtable |
|---|---|---|---|
| 一致性 | 强一致CP | 可调AP | 强一致 |
| 架构 | Master-Slave | P2P去中心化 | 全托管 |

**NewSQL**：SQL + ACID + 水平扩展。Spanner（TrueTime外部一致性）、CockroachDB（兼容PG）、TiDB（兼容MySQL，HTAP）

## 八、分布式文件系统

### 三种存储

| | 块存储 | 文件存储 | 对象存储 |
|---|---|---|---|
| 接口 | SCSI/iSCSI | POSIX/NFS | HTTP REST |
| 修改 | 随机修改 | 随机修改 | 只能整体覆盖 |
| 扩展 | 弱 | 中 | 极强（EB级） |
| 场景 | 数据库/VM磁盘 | 共享文档 | 图片/视频/冷数据 |

### GFS

**设计背景**：搜索引擎PB级网页索引，使用廉价x86商用服务器（故障是常态），高吞吐率比低延迟更重要

**四大假设**：廉价易损节点、大文件为主（GB级）、流式读取+顺序追加、并发追加语义

- **Master**（唯一主节点，管理元数据：目录树/文件→Chunk映射/Chunk位置）+ **ChunkServer**（存储数据，Chunk 64MB，3副本）+ Client

**三大创新**：
1. 单一Master设计：简化架构，避免复杂分布式一致性协议
2. 控制流与数据流分离：数据传输不经Master，避免Master成为网络瓶颈
3. 大Chunk策略（64MB）：极大减少Master的元数据管理压力

**追加写入 Pipeline**：Master指定Primary副本 → Primary定序 → 链式推送 Client→A→B→C（充分利用全双工带宽）
- 一致性妥协：至少一次语义，不保证副本字节级一致

### HDFS

| 组件 | 职责 |
|------|------|
| NameNode | 管理文件系统命名空间和元数据，存储文件→Block映射，全内存运行（1GB内存约管100万Block） |
| DataNode | 存储实际数据Block（默认128MB），每3秒向NameNode发心跳，每个Block 3副本 |
| Secondary NameNode | 定期合并EditLog和FsImage（**不是热备份！**） |

- **计算向数据移动**：传统是数据读入内存计算；HDFS将计算程序调度到数据所在DataNode运行，网络零拷贝
- **设计目标**：超大文件处理（TB/PB级）、流式数据访问（一次写入多次读取）、高容错低成本
- **放弃的特性**：不适合海量小文件、不支持低延迟随机访问、不支持随机修改（仅追加）

### 对象存储

扁平命名空间，数据=对象存于桶（Bucket）。核心要素：Key（唯一标识）、Value（二进制块，最大5TB）、Metadata（自定义标签）

### Ceph

底层 RADOS，上层三接口：
- **RBD**（块设备）：VM 系统盘，秒级快照COW
- **CephFS**（文件系统）：POSIX 兼容
- **RGW**（对象网关）：兼容 S3/Swift API

### 分布式文件系统对比

| | HDFS | Ceph | MinIO | GlusterFS |
|---|---|---|---|---|
| 架构 | 中心化主从 | 去中心化统一 | 轻量对象 | 无中心哈希 |
| 优势 | 计算向数据移动 | 块/文件/对象通吃 | 极致轻量 | 部署简单 |
| 痛点 | 怕小文件 | 运维复杂 | 仅对象接口 | 小文件差 |
| 场景 | 大数据批处理 | 私有云底座 | 云原生数据湖 | NAS平替 |

## 九、并行编程 MapReduce

**为什么需要并行**：单机100MB/s读1TB需2.8小时；分给100台每台10GB→10分钟

**三大并行流派**：

| 流派 | 数据特征 | 操作特征 | 代表技术 |
|------|---------|---------|---------|
| 数据并行 | 不同数据子集 | 相同操作逻辑 | MapReduce/Spark |
| 任务并行 | 相同/不同数据 | 不同操作逻辑 | 多线程 |
| 流水线 | 源源不断流式数据 | 多阶段串联处理 | Flink/Storm |

**Amdahl 定律**：`S(N) = 1/(f + (1-f)/N)`，f=串行比例，N=处理器数量，N→∞ 时上限 = 1/f

### MapReduce 流程

**设计哲学**：2004年Google发表。核心：计算向数据移动（Moving Computation to Data）——不移动庞大数据，把轻量程序代码发送到数据所在节点执行

**角色分工**：Client（提交作业）→ Master/JobTracker/AppMaster（大管家，拆分任务、调度监控）→ Worker/TaskTracker/NodeManager（打工人，执行Map/Reduce代码）

**Map（数据打散与重塑）**：输入`<K1,V1>` → 输出`list<K2,V2>`（过滤、提取、转换）
**Reduce（数据聚合）**：输入`<K2,list(V2)>` → 输出`list<K3,V3>`（求和、求最值、拼接）
- 键值对(Key-Value)是实现分组(Group By)的通用语言，同一种Key必然被送到同一个Reduce节点

```
InputSplit → Map(K1,V1→list<K2,V2>) → Shuffle(按Key分组排序) → Reduce(K2,list<V2>→list<K3,V3>) → Output
```

- **Shuffle**：介于Map和Reduce之间，保证相同Key的中间数据都送到同一个Reduce。流程：Map端溢写(Spill) → 网络拉取(Fetch) → 归并排序(Merge)
- **Combiner**：运行在Map端的"迷你Reduce"，数据离开Map节点前先合并。优化前：("hello",1),("hello",1),("hello",1)→传3条；Combiner后：("hello",3)→只传1条
  - **致命陷阱**：Combiner绝不能改变最终结果。适用Sum/Max（交换律+结合律），不适用Average（Avg(Avg(1,3),5) != Avg(1,3,5)）
- **推测执行**：100个任务99个1分钟完成，1个因硬盘老化跑10分钟→Master在其他空闲机器启动替补，先完成者胜，杀掉另一个。**有副作用的任务（如写数据库）不能开启**

**容错**：Shared-Nothing 无状态计算（失败重跑）、中间结果落盘

**生命周期**：InputSplit(128MB切块) → Map → Shuffle → Reduce → Output(写HDFS)

**WordCount**：map 输出 (word,1) → reduce 按 key 求和

**TopN**：Map 端保留局部 TopN → Reduce 汇总全局 TopN

## 十、Spark

### 设计动机

**MapReduce的痛点**：迭代计算（机器学习需反复迭代）和交互式查询，每次迭代中间结果都要写磁盘再读回来，IO成本巨大

**Spark三大核心思想**：
1. **内存计算**：中间结果尽量保留在内存，减少磁盘IO
2. **DAG执行引擎**：观察全局依赖进行优化，而非MapReduce的两阶段固定模式
3. **统一批流处理**：一套API同时支持批处理(Batch)和流处理(Structured Streaming)

### DAG 执行引擎

将一连串 Transformation 看成一个**有向无环图(DAG)**。依据 **Shuffle 边界（宽依赖处）** 切成多个 Stage，Stage 内部流水执行（无需等待，数据在算子间流动）。好处：系统观察全局依赖，可以做谓词下推、合并操作等全局优化

### 运行架构

- **Cluster Manager**（YARN/Mesos/K8s/Standalone）：集群资源管理，分配Executor容器
- **Worker Node**：物理工作节点
- **Driver Program**：运行 main 函数，创建 SparkSession，解析 Transformation/Action 构建 DAG，当 Action 出现时把 DAG 转换为 Job→Stage→Task 并下发
- **Executor**：长期驻留的JVM进程，接收 Driver 下发 Task 并多线程执行，管理本地 Cache 与 Shuffle 数据。BlockManager模块将**内存和磁盘共同作为存储设备**

### 适用场景

| 场景 | 适合？ | 原因 |
|------|--------|------|
| 海量离线 ETL | 适合 | 并行处理强，生态成熟 |
| 交互式 SQL 分析 | 适合 | DataFrame+Catalyst 性能好 |
| 迭代机器学习 | 适合 | 缓存+迭代计算优势明显 |
| 毫秒级事务/OLTP | 不适合 | Spark不是OLTP数据库 |
| 超低延迟实时控制 | 不适合 | 微批模型不满足毫秒级 |

### RDD（Resilient Distributed Dataset）

Spark 最基础的数据抽象——弹性分布式数据集。**RDD不可变**：每次 Transformation 返回一个全新的 RDD，原 RDD 不变

**五大特性**：

| 特性 | 含义 | 作用 |
|------|------|------|
| Partitions | 分区集合 | 决定并行度与任务划分 |
| Dependencies | 与父RDD的依赖关系 | 决定 Stage 划分与容错恢复 |
| Compute Function | 每个分区的计算逻辑 | 定义转换逻辑 |
| Partitioner | 键值数据如何分区（Hash/Range） | 优化聚合与连接 |
| Preferred Locations | 首选计算位置 | 提高数据本地性（计算向数据移动） |

### 窄依赖 vs 宽依赖

| | 窄依赖 | 宽依赖 |
|---|---|---|
| 关系 | 子分区只依赖少量父分区（1对1或多对1） | 父RDD一个分区被多个子分区依赖 |
| Shuffle | 无，数据不跨节点 | 有，数据需跨节点重分布 |
| 代表 | map, filter, union | reduceByKey, groupByKey, join |
| Stage | 同一 Stage 内流水执行 | **Stage 分界线**（宽依赖处切Stage） |
| 容错 | 只需重算丢失分区 | 需重算父RDD多个分区 |

**Lineage 血缘容错**：Spark 为每个 RDD 记录完整的血缘链（而非复制中间结果），分区丢失时沿链重算该分区。对于代价太高的血缘链（如经过大量Shuffle），用 **Checkpoint** 持久化截断血缘

### Transformation vs Action

| | Transformation | Action |
|---|---|---|
| 返回 | 新 RDD | 结果值 |
| 执行 | 惰性（Lazy） | 触发计算 |
| 代表 | map, filter, flatMap, reduceByKey | collect, count, take, saveAsTextFile |

**惰性执行（Lazy Evaluation）**：Transformation 默认不立即运行，等 Action 出现后统一执行。好处：减少无意义中间结果的产生，给优化器留出**全局优化空间**（例如可以把filter下推到数据源）

### PySpark WordCount 示例

```python
from pyspark.sql import SparkSession
spark = SparkSession.builder.appName("WordCount").master("local[*]").getOrCreate()
sc = spark.sparkContext
lines = sc.textFile("data/words.txt")
words = lines.flatMap(lambda line: line.split())        # Transformation: 窄依赖
pairs = words.map(lambda w: (w.lower(), 1))             # Transformation: 窄依赖
counts = pairs.reduceByKey(lambda a, b: a + b)          # Transformation: 宽依赖(Shuffle)
print(counts.collect())                                  # Action: 触发计算！
spark.stop()
```

### Spark SQL

**DataFrame** = 带 Schema 的分布式表，让用户用 SQL 描述结构化查询

| 操作 | 作用 |
|------|------|
| select | 列选择/表达式 |
| filter/where | 行过滤 |
| groupBy | 分组聚合 |
| orderBy | 排序 |
| join | 表连接 |

**Catalyst 优化器**（4步工作流程）：
1. **Logical Plan Creation**：将SQL/DataFrame操作解析为逻辑计划
2. **Logical Plan Optimization**：谓词下推(Push down filters)、合并操作(Combine operations)
3. **Physical Plan Generation**：选择最优物理执行策略
4. **Code Generation**：生成优化的JVM字节码

**Tungsten 引擎**：Spark 自己的内存管理（绕过JVM GC）+ 堆外内存（off-heap memory）管理 + 全阶段代码生成(Whole-Stage CodeGen)

## 十一、图计算

### 应用场景

- **社交网络分析**：好友推荐、社区发现、影响力分析
- **推荐系统**：协同过滤、商品推荐
- **知识图谱**：实体关系抽取、知识推理
- **金融风控**：欺诈检测、洗钱追踪

### 图数据基本结构

- **顶点(Vertex)**：基本单元，具有唯一ID、可选标签和属性
- **边(Edge)**：表示顶点之间的关系，具有方向性，可包含属性

### 图计算 vs 关系数据库

| 特性 | 图计算 | 关系数据库 |
|------|--------|-----------|
| 数据模型 | 节点+关系 | 表+行+列 |
| 查询方式 | 遍历关系 | SQL JOIN |
| 深度查询 | 高效（O(1)跳转） | 性能急剧下降（多层JOIN笛卡尔积爆炸） |
| 适用场景 | 关系密集型 | 事务处理 |

### NetworkX 四种图类型

| 类型 | 有向 | 多重边 | 典型应用 |
|------|------|--------|---------|
| Graph | 无向 | 否 | 朋友关系 |
| DiGraph | 有向 | 否 | 关注/网页链接 |
| MultiGraph | 无向 | 是 | 航班班次 |
| MultiDiGraph | 有向 | 是 | 交通流量 |

### PageRank

`PR(A) = (1-d)/N + d * Σ(PR(i)/L(i))`

- d = 0.85（阻尼因子）：85%概率继续点链接浏览，15%概率随机跳转
  - d 太低(0.5)→PR趋于均匀；d 太高(0.95)→收敛慢且对噪声敏感
  - 学术引用 d=0.9-0.95；社交网络 d=0.8-0.85；网页搜索 d=0.85
- L(i) = 页面 i 的出链数
- 收敛：新旧差值 < 10^-6 或迭代次数上限(100-500)

**特殊节点**：悬挂节点（无出链）→ PR 均分给所有页面；孤立节点 → 衰减至 0

### Neo4j

专为存储和查询图数据设计的**图数据库**，使用 **Cypher 查询语言**，支持完整的 ACID 事务

```cypher
-- 查询Alice的所有朋友
MATCH (a:Person {name:"Alice"})-[:KNOWS]->(friend) RETURN friend.name, friend.age
-- 朋友的朋友（二度关系），排除已认识的
MATCH (a:Person {name:"Alice"})-[:KNOWS*2]->(fof)
WHERE NOT (a)-[:KNOWS]->(fof) RETURN DISTINCT fof.name AS 推荐好友
-- 创建带属性的节点
CREATE (n:Person {name:"Bob", age:25, city:"成都"})
-- 创建关系
MATCH (a:Person {name:"Alice"}), (b:Person {name:"Bob"})
CREATE (a)-[:KNOWS {since:2020}]->(b)
-- 最短路径查询
MATCH p=shortestPath((a)-[:KNOWS*]-(b)) RETURN p
```

### NetworkX vs Neo4j

| 维度 | NetworkX | Neo4j |
|------|----------|-------|
| 产品类型 | Python库/分析工具 | 图数据库管理系统 |
| 计算模式 | 纯内存计算 | 持久化存储+计算 |
| 数据规模 | 小规模（<10万节点） | 大规模（数十亿节点） |
| 数据持久化 | 无（重启丢失） | 有（ACID事务） |
| 适用场景 | 教学/算法验证/原型开发 | 生产系统/实时查询 |

**决策口诀**：教学/原型 → NetworkX；生产/持久化 → Neo4j；超大规模分布式 → GraphX(Spark)

## 十二、云原生平台

### Helm：K8s 的包管理器

**为什么需要 Helm**：一个真实应用不是一个YAML，而是一组相互关联的 Deployment/Service/ConfigMap/Ingress 等YAML。手工维护多套环境配置时，**配置漂移**会快速累积

**Helm 的作用**：
- **应用打包**：把一组K8s资源组织成 Chart（类比 apt/yum 的 deb/rpm）
- **参数化部署**：通过 values.yaml 适配 dev/test/prod
- **一键部署**：`helm install myapp ./chart -f prod.yaml`
- **版本管理**：Chart 有版本(version)，应用有版本(appVersion)，Release 有历史版本（支持回滚）

**Chart 结构**：

```
myapp/
├── Chart.yaml      # Chart 元信息（名称、版本、依赖）
├── values.yaml     # 默认参数，模板渲染的数据来源
├── charts/         # 存放依赖 Chart
└── templates/      # K8s 资源模板
    ├── deployment.yaml
    ├── service.yaml
    └── ingress.yaml
```

- templates 中用 `{{ .Values.xxx }}` 占位符，渲染后才是最终 K8s YAML
- 同一 Chart 不同 values 部署 dev/test/prod（如 DEV replicas=1, PROD replicas=5+ingress）

### Operator 模式

**为什么需要 Operator**：K8s 能维持 Deployment/Service 等通用资源的期望状态，但**不了解**数据库备份恢复、监控扩缩容等**领域知识**。Operator 把运维经验写成控制器，让系统持续自动收敛

**Operator = CRD + Controller + 领域运维知识**

- **CRD（Custom Resource Definition）**：扩展 K8s API，让用户像操作 Deployment 一样操作业务对象。group+version 组成 API 路径，scope 分 Namespaced/Cluster
- **spec**（用户希望系统达到的状态）/ **status**（控制器观测到并写回的实际状态）分离 = 声明式 API 的关键设计
- **Controller Reconcile Loop**：控制器不断比较期望状态与实际状态 → `if actual != desired then fix()`。每次 Reconcile 都应做到**幂等**（重复执行不破坏系统，不会创建重复资源）

| Operator | 管理对象 | 典型能力 |
|----------|---------|---------|
| Prometheus Operator | Prometheus/ServiceMonitor | 监控自动化管理 |
| MySQL Operator | MySQLCluster/Backup | 数据库生命周期管理 |
| Spark Operator | SparkApplication | Driver/Executor Pod 创建 |
| Cert-Manager | Certificate/Issuer | 证书申请、续期、分发 |

### Spark on K8s

**动机**：云原生环境下不想单独维护 Hadoop/YARN 集群，希望计算任务与其他微服务共享 K8s 统一资源池

- **Driver Pod**：运行 main 函数，创建 SparkContext，向 K8s API Server 请求 Executor Pod，把 Job 切分成 Stage→Task 并下发
- **Executor Pod**：运行 Spark Executor，内部多线程运行多个 Task，使用内存缓存数据，写 Shuffle 临时文件

| 维度 | Spark on YARN | Spark on K8s |
|------|---------------|--------------|
| 生态基础 | Hadoop生态、HDFS、YARN队列 | 容器平台、镜像、Namespace |
| 资源隔离 | YARN 队列与 Container | Namespace、ResourceQuota、Pod |
| 适合场景 | 已有 Hadoop 基础设施 | 云原生数据平台与统一调度 |

### GitOps

**为什么需要 GitOps**：手工 `kubectl apply` 导致线上状态不可追踪，多人协作不知谁改了什么，回滚困难

**核心理念**：
- **Git = 唯一真实来源(Single Source of Truth)**：期望状态以 YAML/Helm Chart/Kustomize 等声明式配置存 Git
- **变更流程**：任何变更先进入 Git（PR审核）→ 控制器自动同步到集群
- **漂移检测**：集群中被手工修改的状态会被检测为 **Drift（配置漂移）**，Sync 操作把差异同步回集群

**ArgoCD**：自动化 GitOps 控制工具，定期监听比较 Git 期望状态和集群实际状态
- 状态一致 → **Synced**
- 存在差异 → **OutOfSync** → 触发 Sync 操作把差异同步到 K8s 集群

**Flux**（Git 原生，为 K8s 持续交付设计），由多个专职控制器组成：

| 控制器 | 职责 |
|--------|------|
| source-controller | 获取 Git/Helm 源，监听仓库变更 |
| kustomize-controller | 应用 Kustomize 配置到集群 |
| helm-controller | 管理 Helm Release 的安装/升级/回滚 |
| notification-controller | 事件通知（Slack/Webhook等） |
