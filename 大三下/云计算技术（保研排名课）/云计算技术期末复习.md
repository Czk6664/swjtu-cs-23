# 云计算技术期末复习

---

## 一、云计算概述

### 1.1 云计算的处理对象：大数据

**什么是大数据？** 海量数据或巨量数据，其规模巨大到无法通过目前主流的计算机系统在合理时间内获取、存储、管理、处理并提炼以帮助使用者决策。

**大数据 4V+1C 特征：**

- **Volume（数据量大）**：PB/EB 级别成为常态
- **Velocity（快速）**：数据产生与处理要求极速响应
- **Variety（多样）**：结构化、半结构化、非结构化混合
- **Value（价值密度低）**：需从海量沙砾中淘金
- **Complexity（复杂度高）**：分析难度呈指数上升

### 1.2 云计算的定义

根据 NIST（美国国家标准与技术研究院）定义：

云计算是一种计算模型，允许无处不在的、便捷的、按需的网络访问，具备共享的可配置计算资源池（包括网络、服务器、存储、应用和服务），资源能够用最小的管理代价或服务提供商的交互实现快速配置和发布。

> "Cloud computing is a model for enabling convenient, on-demand network access to a shared pool of configurable computing resources (e.g., networks, servers, storage, applications, and services) that can be rapidly provisioned and released with minimal management effort or service provider interaction."

### 1.3 云计算的本质特征

1. **按需自服务**：用户可以根据单方面需要，自动配置计算能力（如服务器时间和网络存储），整个过程无需与每个服务提供商进行人工交互。高度自动化的 API 调用是实现按需自服务的基础。

2. **弹性扩展**：能力可以快速、弹性地提供，在某些情况下可以自动横向扩展（Scale-out）或缩减（Scale-in）。对于消费者而言，可供配置的能力看起来是无限的。完美契合流量突发型业务（如电商大促、突发热点事件）。

3. **资源池化**：多租户（multi-tenancy），上万台服务器被融合成一个巨大的计算资源池，供应商的计算资源被池化以服务于多个消费者，互相隔离、互不干扰。

4. **网络访问**：能力可通过标准机制在网络上获取，支持异构客户端。

5. **按量计费**：云系统通过在某种抽象级别（如存储、处理、带宽或活动用户帐户）提供计量能力，自动控制和优化资源使用。经济优势：硬件成本、电价和管理费用全面下降，资源利用率从传统模式的 10%~15% 提升至 80%（5~7倍提升）。

### 1.4 云计算中心选址

- 超大规模带来管理成本显著下降（单管理员可管理超1000台服务器）
- 最大物理开销：电力和制冷成本
- 选址关键：寻找便宜的电力和自然冷源（如 BAT 到贵州山区建立云计算中心）

| 价格 | 地点 | 可能的定价原因 |
|------|------|----------------|
| 3.6美分 | 爱达荷州 | 水力发电，没有长途输送 |
| 10.0美分 | 加州 | 电力在电网上长途输送，湾区的输送线有限，加州不允许煤电 |
| 18.0美分 | 夏威夷 | 发电的能源需要海运到岛上 |

### 1.5 云计算的服务模式

以房屋类比：

- **Local Deployment**：自己盖房子——在本地运行应用，拥有从硬件到应用以及扩缩的所有资源
- **IaaS**：聘请工人盖房子——租用运行应用的硬件，但需负责管理操作系统、运行时、扩缩和所有数据
- **PaaS**：租房自带水电气与家具——自带代码并部署，但将服务器管理和纵向扩容交给云服务提供商
- **SaaS**：拎包入住——支付费用以使用特定用途的完整应用，仅需负责自己的数据

#### IaaS（基础设施即服务）

将多台服务器组成的"云端"服务（内存、I/O、存储、计算能力）作为计量服务提供。

- 优势：消除前期购买硬件设备的资金投入、更好的灾难恢复、专注于开发核心业务
- 典型产品：Amazon EC2（提供可调整大小的计算容量）、Amazon S3（对象存储）

#### PaaS（平台即服务）

将服务器平台或者开发环境作为服务进行提供。

- 优势：减少 OS、数据库、运行环境配置的开销，只需要管理最上层的应用和数据
- 典型产品：Google App Engine、Microsoft Azure

#### SaaS（软件即服务）

通过 Internet 提供软件的模式，用户无需下载软件客户端，而是向提供商租用基于 Web 的软件。

- 优势：可以使用先进的应用程序、只为自己使用的东西付费、免客户端软件使用、轻松增强员工移动性、从任何位置访问应用数据
- 典型产品：文档协同、在线会议、企业OA

#### 三种云交付模型的比较

| 云交付模型 | 服务对象 | 使用方式 | 关键技术 | 用户的控制等级 | 系统实例 |
|-----------|---------|---------|---------|--------------|---------|
| IaaS | 需要硬件资源的用户 | 上传数据、程序代码、环境配置 | 虚拟化技术、分布式海量数据存储等 | 使用和配置 | Amazon EC2、Eucalyptus等 |
| PaaS | 程序开发者 | 上传数据、程序代码 | 云平台技术、数据管理技术等 | 有限的管理 | Google App Engine、Microsoft Azure、Hadoop等 |
| SaaS | 企业和需要软件应用的用户 | 上传数据 | Web服务技术、互联网应用开发技术等 | 完全的管理 | Google Apps、Salesforce CRM等 |

> 注：随着云计算的深化发展，不同云计算解决方案之间相互渗透融合，同一种产品往往横跨两种以上的类型。

### 1.6 云计算的部署模式

| 部署模式 | 优点 | 缺点 | 典型适用场景 |
|---------|------|------|-------------|
| 公有云 | 零初始硬件成本、极致弹性扩展、无需底层运维 | 数据控制权较弱、存在隐私与安全顾虑 | 互联网应用、初创企业、突发流量业务 |
| 社区云 | 多方均摊成本、满足特定行业的定制化与安全合规标准 | 参与方管理协调成本较高、扩展性不及公有云 | 医疗数据联盟、高校科研算力共享、政务云 |
| 私有云 | 最高的安全与隐私、满足严苛合规要求、底层资源完全可控 | 初始采购成本极高、需专门IT团队运维、扩展受限于物理硬件 | 政府机构、大型金融机构、核心机密系统 |
| 混合云 | 兼顾安全与弹性、优化整体IT成本 | 系统架构最复杂、跨云网络互通与数据同步难 | 核心稳态数据留存本地 + 突发流量溢出至公有云 |

### 1.7 云计算的三大基础设施

#### 计算

- **虚拟化技术（Virtualization）**：通过 Hypervisor 层，将一台物理机分成多台拥有独立操作系统的虚拟机。隔离性极强，安全性高，但相对笨重（每个VM都要跑完整的OS）。
- **容器技术（Containers，如 Docker）**：多个容器共享同一个宿主机的操作系统内核，只隔离应用及其依赖库。极致轻量、启动达到秒级/毫秒级，现代云原生架构的基石。

#### 存储

- **分布式存储（Distributed Storage）**：将海量数据分散存储在多台服务器节点上，通过网络将其组合成一个巨大的逻辑磁盘。极高的吞吐量和容错率（多副本机制）。
- **对象存储（Object Storage）**：如 Amazon S3 / 阿里云 OSS。抛弃了传统文件系统的目录树结构，采用扁平化命名空间。数据和元数据打包成一个对象，通过唯一的 URL（API）进行访问。容量几乎无限扩展，适合存储非结构化数据（图片、视频、备份文件）。

#### 网络

- **软件定义网络（SDN）**：将网络的控制面与数据面分离，通过纯软件编程的方式来动态管理和配置网络资源。
- **弹性负载均衡（Load Balancing）**：面对突发海量并发请求，将外部请求均匀分发到多个计算节点上。

## 二、虚拟化技术与 Docker

### 2.1 虚拟化的定义

虚拟化（Virtualization）是一种资源管理技术，是将计算机的各种实体资源（CPU、内存、磁盘空间、网络适配器等），予以抽象、转换后呈现出来并可供分割、组合为一个或多个电脑配置环境。

- 虚拟机：由虚拟化层提供的高效独立的虚拟计算机系统
- 从软件角度来看，虚拟机 = 真实机器

### 2.2 虚拟化带来的优势

- **资源利用率**：资源动态分配和调度
- **运维成本**：自动化开通能力
- **升级迁移**：方便系统的平滑升级与跨硬件迁移
- **测试生产**：安全的隔离环境

### 2.3 硬件虚拟化 vs 软件虚拟化

**软件虚拟化：**
- 通过虚拟机监控器（VMM）捕获并翻译特权指令
- 兼容性好，系统性能开销较大，实现逻辑复杂
- 代表：QEMU、VMware

**硬件虚拟化：**
- 依靠 CPU 等底层硬件架构级的扩展支持，增加一套专门给虚拟机的特权指令通道（Ring-1）
- 无需软件干预，性能极高，和硬件设计绑定
- 代表：Intel VT-x、AMD-v

### 2.4 Hypervisor/VMM

- 职责1：物理硬件资源 → 虚拟资源的逻辑映射
- 职责2：虚拟机的上下文隔离，保障多租户环境安全

#### 寄居虚拟化架构（Hosted Virtualization）

- Hypervisor 作为普通进程运行在 Host OS 之上
- 例如：VMware（个人PC）
- 硬件兼容性好、部署方便，但系统开销大（I/O 请求需经过 Host OS 转发，上下文切换频繁）

#### 裸机虚拟化架构（Bare-metal Virtualization）

- Hypervisor 直接运行于裸机硬件之上，实现从虚拟资源到物理资源的映射
- 例如：KVM（数据中心）
- 省去底层 Host OS 的中间损耗，系统性能最接近物理机，但硬件兼容性要求严格、部署难度大

### 2.5 CPU 虚拟化原理

**怎么解决 CPU 指令的权限冲突？**
- 软件虚拟化：VMM 截获 Ring0 指令并转化
- 硬件虚拟化：在 CPU 芯片直接支撑虚拟化指令

**VT-x 引入了两种操作模式：**
- **根操作模式（Root）**：VMM 运行所处的模式
- **非根操作模式（Non-Root）**：VM 运行所处的模式
- Non-Root 模式也有一套 Ring0-Ring3，Guest OS 可以直接使用这套指令（硬件直接运行）
- 只有当 Guest OS 试图执行影响物理机硬件的指令时，才会将控制权交给 VMM 转换

### 2.6 内存虚拟化原理

**内存地址转换：**
- 物理机：虚拟地址 → 物理地址
- 虚拟机：虚拟地址 → Guest 伪物理地址 → 物理地址

**影子页表（Shadow Page Table，SPT）**：
- Hypervisor 自己维护一个影子页表，记录 Guest 伪物理地址到物理地址的转换
- 拦截、更新、同步所有的内存转换，传递转换后的地址给物理机 CPU
- 局限：两次转换，内存读写缓慢

**扩展页表（Extended Page Table，EPT）**：
- 内存管理单元（MMU）进行两次地址转换
- 硬件查询维护，效率高速度快

### 2.7 虚拟化技术的局限性

- **资源冗余**：每一个虚拟机都必须运行一个完整 Guest OS
- **弹性迟缓**：分钟级的系统启动时间
- **交付困难**：开发、测试与生产环境的底层依赖不一致问题

### 2.8 容器 vs 虚拟机

| | 虚拟机 | 容器 |
|---|---|---|
| OS依赖 | 完整的独立操作系统（Guest OS） | 共享宿主机操作系统内核 |
| 启动速度 | 分钟级（需经历完整的系统引导） | 毫秒/秒级（仅启动一个进程） |
| 空间占用 | GB 级别（包含海量系统文件） | MB 级别（仅包含业务代码与依赖） |
| 性能损耗 | 较大（需通过 Hypervisor 转换） | 极小（原生执行指令） |
| 隔离级别 | 极强（硬件级隔离，高度安全） | 较弱（进程级/Namespace逻辑隔离） |

### 2.9 Docker 架构

**Client/Server 架构：**
- **Docker Client**：build, run
- **Docker Daemon**：守护进程 dockerd
- **Docker Registry**：容器镜像仓库（pull, push, search）

### 2.10 Linux 内核基石

Docker 容器封装了 Linux 内核的 API：

#### Namespace 隔离

Linux 提供的一种内核级别环境隔离的方法。容器内的进程运行的时候看不到宿主机的进程。

| Namespace | 作用 |
|-----------|------|
| PID Namespace | 进程隔离 |
| NET Namespace | 网络隔离 |
| MNT Namespace | 挂载/文件系统隔离 |
| UTS Namespace | 主机名隔离 |
| IPC Namespace | 进程间通信隔离（消息队列IPC） |
| USER Namespace | 用户权限隔离 |

```c
struct nsproxy {
    atomic_t count;
    struct uts_namespace *uts_ns;
    struct ipc_namespace *ipc_ns;
    struct mnt_namespace *mnt_ns;
    struct pid_namespace *pid_ns_for_children;
    struct net           *net_ns;
};
// Linux: clone(CLONE_NEWPID|CLONE_NEWNET)
```

#### Cgroup 资源限制

Linux 提供的一种内核级别资源限制的方法（control group），控制一组进程的资源使用、进程起始、优先级。路径：`/sys/fs/cgroup`

### 2.11 镜像与容器的分层结构

- 容器运行时会在镜像层只读层基础上添加可写层
- 相同基础层（系统环境、语言库...）服务器仅存一次
- 大规模镜像分发：网络和存储成本大幅降低

### 2.12 联合文件系统（UnionFS）

- 将分属不同物理位置的只读目录合并，挂载至一个虚拟文件系统位置（挂载点），实际物理位置是分开的
- 容器启动后，Docker Engine 在最顶端动态附加一层可写层
- 容器生命周期内，所有文件系统操作均发生于顶部可写层

## 三、云原生基础与微服务

### 3.1 云原生的定义（CNCF）

云原生技术使组织能够在公有云、私有云和混合云等现代动态环境中，构建和运行可弹性扩展的应用。云原生的代表技术包括容器、服务网格、微服务、不可变基础设施和声明式API。

- **Cloud**：应用长在云上（按需自服务、弹性扩展、资源池化、网络访问、按量计费）
- **Native**：应用从写代码的第一天起，就是为了适应云环境而设计

### 3.2 云原生的核心要素

| 要素 | 定义 | 核心价值 |
|------|------|---------|
| 容器化 | 应用及其依赖打包为容器镜像，确保环境一致性 | 可移植性、快速部署 |
| 微服务 | 将应用拆分为小型、独立的服务，每个服务专注于单一业务功能 | 独立开发、独立部署、独立扩展 |
| 声明式 API | 用户声明期望状态，系统自动实现和维护 | 简化运维、自动化管理 |
| 不可变基础设施 | 基础设施组件一旦部署不再修改，更新通过替换而非修补 | 环境一致性、可审计性 |

### 3.3 不可变基础设施

| 对比 | 可变基础设施 | 不可变基础设施 |
|------|------------|--------------|
| 更新方式 | SSH 登录服务器手动修改 | 构建新镜像，滚动替换 |
| 环境一致性 | 低（易出现配置漂移） | 高（镜像统一） |
| 回滚 | 困难 | 简单（直接使用旧版本镜像） |
| 可审计性 | 弱 | 强（镜像版本化管理） |

### 3.4 云原生 vs 传统开发模式

| 维度 | 传统开发模式 | 云原生模式 |
|------|------------|-----------|
| 架构 | 单体应用（Monolith） | 微服务架构 |
| 部署单元 | WAR/EAR 包部署到应用服务器 | 容器镜像部署到 K8s |
| 部署频率 | 每月/每季度 | 每天多次 |
| 扩展方式 | 垂直扩展（加 CPU/内存） | 水平扩展（加实例） |
| 环境管理 | 手动配置、脚本 | 声明式配置（IaC） |
| 故障处理 | 人工排查、手动恢复 | 自动检测、自动恢复 |
| 开发流程 | 瀑布式/长周期迭代 | CI/CD、DevOps |
| 基础设施 | 物理机/虚拟机 | 容器/Serverless |
| 状态管理 | 有状态（Session） | 无状态（Stateless） |

### 3.5 微服务的核心特征

| 特征 | 说明 |
|------|------|
| 单一职责 | 每个服务只负责一个明确的业务功能 |
| 独立部署 | 服务可以独立构建、测试和部署，不影响其他服务 |
| 独立扩展 | 根据各服务的负载独立进行水平扩展 |
| 技术异构 | 不同服务可使用不同的编程语言和数据存储 |
| 轻量级通信 | 服务间通过 REST API、gRPC 或消息队列通信 |
| 去中心化治理 | 各团队自主选择技术栈和开发流程 |
| 去中心化数据 | 每个服务拥有自己的数据库（Database per Service） |
| 容错设计 | 服务需要考虑依赖故障的处理（熔断、降级、重试） |

### 3.6 微服务拆分策略

1. **按业务领域拆分（DDD）**：基于领域驱动设计的限界上下文（Bounded Context），每个限界上下文对应一个微服务。例：电商系统 → 用户服务、商品服务、订单服务、支付服务、库存服务。
2. **按数据边界拆分**：每个服务拥有自己的数据库，服务间不直接访问对方数据库，通过API或事件进行数据交换。
3. **按变更频率拆分**：变更频率高的功能独立为服务，稳定的功能保持在一起。

### 3.7 微服务通信方式

#### 同步通信

| 特性 | REST | gRPC |
|------|------|------|
| 协议 | HTTP/HTTPS | HTTP/2 |
| 数据格式 | JSON（主流）、XML | Protocol Buffers（二进制，高效） |
| 设计风格 | 资源导向（GET/POST/PUT/DELETE） | 方法调用导向（RPC） |
| 优点 | 简单、通用、生态成熟 | 高性能、强类型、双向流、多语言代码生成 |
| 缺点 | 文本协议，序列化开销大；缺乏类型安全 | 学习曲线较高，调试不如 REST 直观 |

- **REST**：前端调用后端（对外API），基于 HTTP/JSON，人类易读、简单通用
- **gRPC**：微服务A调用微服务B（对内API），基于 HTTP/2 和 Protocol Buffer（二进制），体积小、传输快

#### 异步通信

消息队列（Message Queue）：通过 Kafka、RabbitMQ 等消息中间件，将生产者发送的消息暂存并异步交付给消费者处理，实现服务间的解耦。具备削峰填谷、保障最终一致性的优势。

### 3.8 服务发现与注册

#### 为什么需要服务发现？

微服务架构中，服务实例的IP地址和端口动态变化，服务可能随时扩缩容、故障重启、迁移到新节点，硬编码地址行不通。

#### 客户端发现（Client-Side Discovery）

- 服务 A 直接查询注册中心，获取服务 B 实例列表，本地负载均衡后直接发起调用
- 代表：Eureka + Ribbon
- 优点：架构简单，无额外网络跳转，延迟低
- 缺点：客户端需集成服务发现与负载均衡逻辑，与语言耦合

#### 服务端发现（Server-Side Discovery）

- 服务 A 将请求发送给负载均衡器/API网关，由网关查询注册中心并完成负载均衡
- 代表：Nginx、Spring Cloud Gateway、Kubernetes Service + kube-proxy
- 优点：客户端逻辑极简，语言无关，负载策略统一维护
- 缺点：多一跳网络延迟，网关成为潜在单点

#### 服务注册中心

| 注册中心 | 一致性模型 | 特点 |
|---------|-----------|------|
| etcd | 强一致（Raft） | K8s 默认使用，键值存储 |
| Consul | 强一致（Raft） | 内置服务发现、健康检查、KV 存储 |
| ZooKeeper | 强一致（ZAB） | 老牌，配置管理 |
| Nacos | AP/CP 可切换 | 阿里开源，服务发现 + 配置管理 |

### 3.9 负载均衡

#### 负载均衡策略

| 算法 | 原理 | 适用场景 |
|------|------|---------|
| 轮询（Round Robin） | 按顺序依次分发到每个实例 | 实例性能相同 |
| 加权轮询（Weighted RR） | 根据实例权重按比例分发 | 实例性能不均 |
| 最少连接（Least Connections） | 分发到当前连接数最少的实例 | 长连接场景 |
| 随机（Random） | 随机选择实例 | 简单场景 |
| 一致性哈希（Consistent Hash） | 相同请求哈希到相同实例 | 缓存命中率优化 |
| IP 哈希 | 按客户端 IP 哈希选择实例 | Session 亲和性 |

#### 负载均衡层次

| 层次 | 技术 | 说明 |
|------|------|------|
| L4负载均衡 | TCP/UDP层 | 基于IP+端口转发，性能高，只基于IP和端口 |
| L7负载均衡 | HTTP层 | 基于URL路径、Header等路由，功能更丰富灵活 |

### 3.10 熔断器模式（Circuit Breaker）

#### 问题：级联故障（雪崩效应）

服务A调用服务B，服务B调用服务C。如果服务C崩溃 → 服务B等待C响应 → 线程阻塞 → 线程池耗尽 → 服务A等待B响应 → 同样阻塞。

#### 熔断器三种状态

| 状态 | 说明 | 行为 |
|------|------|------|
| 关闭（Closed） | 正常状态 | 所有请求正常转发；统计失败率 |
| 打开（Open） | 熔断触发 | 所有请求直接返回降级响应；不调用下游 |
| 半开（Half-Open） | 尝试恢复 | 允许少量请求通过；成功则关闭熔断，失败则继续打开 |

#### 状态转换

1. **Closed → Open**：调用失败率达到预设阈值时，熔断器立即切换到 Open 状态
2. **Open → Half-Open**：经过一段超时时间后，自动进入 Half-Open 状态
3. **Half-Open → Closed/Open**：探测请求成功则恢复到 Closed；失败则回到 Open

#### 关键参数

| 参数 | 说明 | 典型值 |
|------|------|--------|
| 失败率阈值 | 触发熔断的失败比例 | 50% |
| 统计窗口 | 统计失败率的时间窗口 | 10秒 |
| 最少请求数 | 触发熔断需要的最少请求量 | 20次 |
| 熔断持续时间 | Open状态持续时间 | 30秒 |
| 半开允许请求数 | Half-Open状态允许通过的请求数 | 5次 |

### 3.11 其他容错模式

- **重试（Retry）**：短暂故障时自动重试（配合指数退避）
- **超时（Timeout）**：设置调用超时上限，防止长时间阻塞
- **舱壁（Bulkhead）**：资源隔离，不同服务使用独立的线程池/连接池
- **降级（Fallback）**：熔断触发后返回默认值或缓存数据

### 3.12 限流与降级策略

#### 限流算法

| 算法 | 原理 | 特点 |
|------|------|------|
| 固定窗口计数器 | 时间窗口内计数，超过阈值拒绝 | 简单，但有窗口边界突刺问题 |
| 滑动窗口计数器 | 滑动时间窗口，平滑限流 | 更平滑，实现稍复杂 |
| 令牌桶（Token Bucket） | 固定速率生成令牌，请求消耗令牌 | 允许突发流量（桶满时） |
| 漏桶（Leaky Bucket） | 请求进入桶，以固定速率流出 | 严格平滑流量 |

#### 降级策略

| 策略 | 说明 | 示例 |
|------|------|------|
| 返回默认值 | 返回预设的默认响应 | 推荐服务降级 → 返回热门商品 |
| 返回缓存 | 返回上次成功的缓存数据 | 用户画像服务降级 → 返回缓存画像 |
| 功能裁剪 | 关闭非核心功能 | 高峰期关闭评论、推荐功能 |
| 流量排队 | 请求排队等待处理 | 秒杀场景排队机制 |

### 3.13 API 网关

API 网关是微服务架构中的统一入口，负责接收所有客户端请求。

| 功能 | 说明 |
|------|------|
| 请求路由 | 根据URL路径将请求路由到对应微服务 |
| 认证鉴权 | 统一的身份验证和权限校验 |
| 限流熔断 | 保护后端服务免受过载 |
| 负载均衡 | 将请求分发到多个服务实例 |
| 协议转换 | 外部REST → 内部gRPC |
| 请求聚合 | 将多个微服务的响应聚合为一个 |
| 日志监控 | 统一的请求日志和指标采集 |

### 3.14 Docker Compose

Docker Compose 是一个用于定义和运行多容器 Docker 应用的工具，使用 YAML 文件描述应用的服务、网络和卷。

#### 核心结构

| 顶级key | 说明 |
|---------|------|
| services | 定义应用包含的服务（容器） |
| networks | 定义自定义网络 |
| volumes | 定义持久化卷 |
| configs | 定义配置文件 |
| secrets | 定义敏感信息 |

#### 服务配置选项

| 选项 | 说明 | 示例 |
|------|------|------|
| image | 使用已有镜像 | `image: nginx:alpine` |
| build | 从Dockerfile构建 | `build: ./api` |
| ports | 端口映射 | `ports: ["8080:80"]` |
| environment | 环境变量 | `environment: [DB_HOST=db]` |
| volumes | 数据卷挂载 | `volumes: [./data:/app/data]` |
| depends_on | 服务依赖关系 | `depends_on: [db, redis]` |
| networks | 加入的网络 | `networks: [frontend, backend]` |
| deploy | 部署配置 | 副本数、资源限制 |
| healthcheck | 健康检查 | 命令、间隔、超时 |

#### 网络与服务发现

- Compose 会自动创建一个默认网络（项目名_default）
- 同一网络中的容器可以通过服务名直接通信（Docker内置DNS）
- 例：userservice 容器可以通过 `userdb:5432` 访问数据库

## 四、Kubernetes 基础

### 4.1 整体架构：Master-Worker 模型

- **Control Plane（Master）**：集群的"大脑"，负责决策（调度、管理、API响应）
- **Worker Nodes**：集群的"手脚"，负责干活（运行容器负载）

### 4.2 Master 节点核心组件

1. **kube-apiserver（入口/大脑）**：唯一入口，所有组件都只和它通信。无状态，可水平扩展。职责：认证、授权、准入控制、API 注册。

2. **etcd（记忆/存储）**：分布式键值数据库，保存集群所有状态数据。高可用，基于 Raft 协议，通常奇数部署（3或5个）。只有 API Server 能直接访问 etcd。

3. **kube-controller-manager（决策者）**：控制循环（Control Loop），不断比较"期望状态" vs "实际状态"。内置控制器：节点控制器、副本控制器、Service控制器等。逻辑：`if current != desired then fix_it()`

4. **kube-scheduler（调度器）**：给新创建的 Pod 找一个最合适的节点。两步走：
   - 预选（Filtering）：排除资源不足的节点
   - 优选（Scoring）：给剩余节点打分（亲和性、负载均衡）

### 4.3 Worker 节点核心组件

1. **kubelet（节点管家）**：每个节点的代理人，接收 API Server 的指令，管理 Pod 生命周期，调用 CRI（容器运行时接口）启动容器。

2. **kube-proxy（网络代理）**：维护节点上的网络规则（iptables/IPVS），实现 Service 的负载均衡和流量转发。

3. **Container Runtime（运行时）**：真正运行容器的软件：containerd、CRI-O（Docker 已被垫片化）。

### 4.4 声明式 API 与 YAML 结构

一切皆对象，K8s 通过 YAML 文件描述期望状态（Desired State）。

**YAML 四大金刚（必填字段）：**

```yaml
apiVersion: v1        # API 版本
kind: Pod             # 资源类型
metadata:             # 元数据 (名称、标签)
  name: my-pod
  labels:
    app: web
spec:                 # 规格 (最关键！)
  containers: ...     # 用户期望的具体配置
```

### 4.5 Namespace：逻辑隔离

虚拟集群：在同一个物理集群中，逻辑上划分出的独立空间。作用：资源隔离、权限控制、避免命名冲突。

| 名称 | 用途 |
|------|------|
| default | 默认工作区 |
| kube-system | K8s 系统组件（切勿随意修改） |
| dev / prod | 用户自定义：开发/生产环境 |

### 4.6 Pod

#### 为什么不直接管理容器？

容器之间往往需要紧密协作（如日志收集、代理），Pod 提供共享环境简化协作。

**Pod 的共享机制：**
1. **共享网络（Network Namespace）**：Pod 内所有容器共用一个 IP，容器间通过 localhost 通信
2. **共享存储（Shared Volume）**：容器间可以通过挂载同一个 Volume 交换文件

#### Pod YAML 关键配置

```yaml
spec:
  containers:
  - name: web
    image: nginx:1.25
    ports:
    - containerPort: 80
    resources:
      requests:
        cpu: "250m"      # 调度依据（保底资源）
        memory: "64Mi"
      limits:
        cpu: "500m"      # 运行上限
        memory: "128Mi"
```

- **Requests**：节点最少要有这么多资源，Pod 才能调度上去
- **Limits**：容器用超了会被限流（CPU）或杀掉（Memory OOM）

#### Pod 的生命周期

1. **Pending**：等待调度或拉取镜像
2. **Running**：容器已启动
3. **Succeeded/Failed**：任务结束或异常退出
4. **Unknown**：与节点失联

**Init Containers**：在主容器启动之前执行。用途：初始化配置、等待数据库就绪。必须按序、成功执行完，主容器才会启动。

#### 探针（Probes）：健康检查机制

| 探针类型 | 作用 | 失败后果 |
|---------|------|---------|
| Liveness | 存活检测（比如死锁） | 重启容器 |
| Readiness | 就绪检测（比如启动中） | 切断流量（从 Service 移除） |
| Startup | 启动检测（针对慢启动应用） | 抑制其他探针 |

#### Pod QoS 等级

1. **Guaranteed（头等舱）**：request == limit，最后被驱逐，最稳定
2. **Burstable（商务舱）**：request < limit，资源紧张时可能被驱逐
3. **BestEffort（经济舱）**：未设置资源限制，节点缺资源时第一个被杀掉

### 4.7 Service

#### 为什么需要 Service？

Pod 是短暂的，重启后 IP 会变。Service 提供一个 VIP（虚拟IP），屏蔽后端的动态变化。

**核心机制：Labels & Selectors**，Service 通过标签选择器找到后端 Pod。

#### Service 的三种常用类型

1. **ClusterIP（默认）**：仅集群内访问。适用于数据库、内部微服务。
2. **NodePort**：在每个 Node 上开一个端口（30000-32767）。外部访问：`NodeIP:NodePort`。
3. **LoadBalancer**：申请云厂商的硬件负载均衡器。外部访问：LB 公网 IP。

#### Service 发现机制：DNS

K8s 集群内置 CoreDNS。域名格式：`<service>.<namespace>.svc.cluster.local`

### 4.8 Ingress：七层路由入口

- Service（L4）：只能基于 IP/Port 转发
- Ingress（L7）：可以基于域名（Host）和路径（Path）转发
- 优势：节省公网 IP（一个 IP 代理多个服务），支持 SSL/TLS 终止

### 4.9 Deployment：无状态应用管家

**核心功能：**
1. 维持副本数：声明 3 个，就永远保持 3 个
2. 滚动更新：平滑升级，不中断服务
3. 版本回滚：一键回到过去

#### 滚动更新（Rolling Update）

"先起新，后停旧"，逐步替换，确保服务始终可用。

- **maxSurge**：允许比期望多几个？
- **maxUnavailable**：允许比期望少几个？

#### 版本回滚与扩缩容

```bash
# 回滚到上一个版本
kubectl rollout undo deployment/web
# 手动扩容到 10 个副本
kubectl scale deployment/web --replicas=10
```

#### HPA：水平自动扩缩容

根据 CPU/内存利用率，自动调整 Pod 数量。

### 4.10 kubectl 常用命令速查

**调试（Debug）：**
- `kubectl describe pod <name>`：查看详情/报错原因（最常用）
- `kubectl logs <name>`：查看容器日志
- `kubectl exec -it <name> -- sh`：进入容器内部

**增删改查（CRUD）：**
- `kubectl apply -f xx.yaml`：声明式创建/更新（推荐）
- `kubectl get pods/svc/deploy`：查看资源
- `kubectl delete -f xx.yaml`：删除资源

## 五、Kubernetes 深入与服务网格

### 5.1 调度器原理：预选与优选

调度（Scheduling）是指将未绑定节点的 Pod 分配到合适 Worker 节点的过程。

#### 预选常见规则

| 规则 | 说明 |
|------|------|
| PodFitsResources | 节点剩余资源 ≥ Pod 的 Request |
| PodFitsHostPorts | 节点端口无冲突 |
| MatchNodeSelector | 节点标签匹配 Pod 的 nodeSelector |
| NoTaintUnlessTolerated | 节点 Taint 需被 Pod Toleration 匹配 |
| CheckNodeMemoryPressure | 节点无内存压力 |

#### 优选常见规则

| 规则 | 说明 |
|------|------|
| LeastRequestedPriority | 优先选择剩余资源最多的节点（分散调度） |
| BalancedResourceAllocation | CPU和内存使用率更均衡的节点得分更高 |
| NodeAffinityPriority | 匹配亲和性规则的节点得分更高 |
| InterPodAffinityPriority | 满足Pod亲和性的节点得分更高 |

### 5.2 节点亲和性（Node Affinity）

| 模式 | 说明 | 效果 |
|------|------|------|
| requiredDuringSchedulingIgnoredDuringExecution | 硬约束——必须满足 | 不满足则Pod无法调度 |
| preferredDuringSchedulingIgnoredDuringExecution | 软约束——优先满足 | 不满足仍可调度到其他节点 |

**Pod 亲和性（Pod Affinity）**：声明希望与具有特定标签的其他 Pod 调度到同一节点/区域，提升通信效率。

**Pod 反亲和性（Pod Anti-Affinity）**：声明不希望与特定 Pod 在同一节点/区域，用于容灾。

### 5.3 污点与容忍（Taints & Tolerations）

- 亲和性 = Pod 主动选择节点（"我想去哪"）
- 污点/容忍 = 节点排斥 Pod（"谁不能来"），Pod 可声明豁免

| Effect | 说明 |
|--------|------|
| NoSchedule | 不调度新Pod到该节点（已运行的Pod不受影响） |
| PreferNoSchedule | 尽量不调度，但不保证 |
| NoExecute | 不调度新Pod，且驱逐已运行的不匹配Pod |

典型场景：
- GPU节点：Taint 为 `gpu=true:NoSchedule`，只有需要GPU的Pod才容忍该Taint
- Master节点：默认 Taint `node-role.kubernetes.io/master:NoSchedule`

### 5.4 ResourceQuota 与 LimitRange

| 对比 | ResourceQuota | LimitRange |
|------|--------------|------------|
| 作用范围 | 命名空间总量 | 单个Pod/容器 |
| 功能 | 限制总资源、对象数量 | 设置默认值、范围 |

### 5.5 StatefulSet：有状态应用管理

| 特性 | Deployment | StatefulSet |
|------|-----------|-------------|
| Pod名称 | 随机后缀（web-7d9f8c-xk2l3） | 有序固定（web-0, web-1, web-2） |
| 网络标识 | 无稳定标识 | 稳定的DNS名称（web-0.web-svc） |
| 存储 | Pod重建后存储丢失 | 每个Pod绑定独立的PVC，重建后保留 |
| 启动/停止顺序 | 并行 | 有序（0→1→2启动，2→1→0停止） |
| 适用场景 | 无状态应用（Web API） | 有状态应用（数据库、消息队列） |

**Headless Service**：`clusterIP: None`，不分配 IP，直接返回后端 Pod 的 IP 列表，配合 StatefulSet 生成稳定的 DNS 记录。

**VolumeClaimTemplates**：StatefulSet 需要每个 Pod 有自己独立的 PVC。

### 5.6 ConfigMap 与 Secret

#### ConfigMap：非敏感配置

以键值对形式存储，实现配置与应用代码解耦。

| 使用方式 | 说明 |
|---------|------|
| 环境变量注入 | envFrom 或单个 valueFrom |
| 卷挂载为文件 | 将ConfigMap挂载为目录中的文件 |
| 命令行参数 | 通过环境变量传递给命令 |

热更新：环境变量方式需重启Pod；卷挂载方式约1分钟自动更新。

#### Secret：敏感信息管理

数据以 Base64 编码存储（注意：非加密，需配合 etcd 加密使用）。

| 类型 | 用途 |
|------|------|
| Opaque | 通用密钥（默认类型） |
| kubernetes.io/tls | TLS证书 |
| kubernetes.io/dockerconfigjson | Docker Registry认证信息 |
| kubernetes.io/service-account-token | ServiceAccount Token |

Secret 挂载为 tmpfs（内存卷），不会写入节点磁盘。

### 5.7 K8s 存储架构

**三层架构**：Pod → PVC（存储请求）→ PV（存储资源）→ 底层存储（云盘/NFS/Ceph）

| 概念 | 说明 |
|------|------|
| PV（PersistentVolume） | 集群级别的存储资源，由管理员预先创建或动态供给 |
| PVC（PersistentVolumeClaim） | Pod对存储的请求声明（大小、访问模式） |
| StorageClass | 定义存储的类型和供给策略，支持动态创建PV |

**访问模式：**

| 模式 | 缩写 | 说明 |
|------|------|------|
| ReadWriteOnce | RWO | 单节点读写（最常用） |
| ReadOnlyMany | ROX | 多节点只读 |
| ReadWriteMany | RWX | 多节点读写（需NFS/CephFS等共享存储） |

**回收策略：**

| 策略 | 说明 |
|------|------|
| Retain | PVC删除后PV保留（手动回收） |
| Delete | PVC删除后PV和底层存储一并删除 |

**动态供给（Dynamic Provisioning）**：StorageClass 定义存储的类型和供给者（Provisioner），当 PVC 请求匹配某个 StorageClass 时，自动创建对应的 PV。

### 5.8 服务网格（Service Mesh）

#### 定义

服务网格是一个专门用于处理服务间通信的基础设施层。它通过在每个服务旁部署一个轻量级网络代理（Sidecar），以透明的方式处理服务发现、负载均衡、故障恢复、指标采集和安全通信。

| 传统SDK方式 | Service Mesh |
|------------|-------------|
| 业务代码中嵌入通信逻辑 | 通信逻辑下沉到基础设施 |
| 语言绑定 | 语言无关（Sidecar代理） |
| 升级SDK需要修改并重新部署所有服务 | 升级代理不影响业务代码 |
| 每个服务单独实现熔断/限流 | 统一的策略管理 |

#### Istio 架构

| 组件 | 功能 |
|------|------|
| istiod | 统一的控制面（合并了Pilot/Citadel/Galley） |
| Pilot | 服务发现、流量管理规则下发 |
| Citadel | 证书管理、mTLS加密 |
| Galley | 配置验证和分发 |
| Envoy | 数据面代理（Sidecar），所有流量经过Envoy |

#### Sidecar 代理（Envoy）

Envoy 是高性能 L4/L7 代理，具备 L7路由、负载均衡、熔断、重试、超时、TLS、可观测性等能力。

#### Istio 安全：mTLS

mTLS（Mutual TLS）是双向 TLS 认证。Istio Citadel 为每个服务自动签发 X.509 证书，Envoy 自动使用证书建立 mTLS 连接，应用代码无需任何修改。

#### 金丝雀发布（Canary Release）

渐进式发布策略，先将少量流量导向新版本，观察无异常后逐步扩大。

| 策略 | 原理 | 风险 | 回滚速度 |
|------|------|------|---------|
| 滚动更新 | 逐步替换旧Pod | 中等 | 慢 |
| 蓝绿部署 | 两套完整环境切换 | 低 | 快 |
| 金丝雀发布 | 按比例分流 | 最低 | 最快 |
| A/B测试 | 按条件分流 | 低 | 快 |

## 六、消息队列与事件驱动架构

### 6.1 消息队列的概念与作用

消息队列（Message Queue，MQ）是一种应用间通过消息进行异步通信的中间件。

核心作用：
- **异步解耦**：发送方无需等待接收方处理，降低系统耦合
- **流量削峰**：缓冲突发流量，保护下游服务不被压垮
- **最终一致性**：通过可靠消息传递，达成系统最终一致的状态

### 6.2 消息模型

- **点对点（Queue）**：每条消息只被一个消费者消费
- **发布/订阅（Topic）**：消息可被多个消费者同时接收

### 6.3 消息投递语义

| 投递语义 | 适用场景 | 优点 | 缺点 |
|---------|---------|------|------|
| At Most Once | 性能要求高、对消息丢失不敏感（如日志收集） | 高效，处理过程简单 | 可能会丢失消息 |
| At Least Once | 数据完整性要求较高（如订单支付） | 不会丢失消息 | 可能会导致消息重复（需幂等性） |
| Exactly Once | 高价值交易、金融支付 | 完美的消息传递保证 | 实现复杂，性能开销大 |

**导致消息重复的情况：**
- 生产者发送消息后，Broker 保存成功，但没有成功返回 ACK
- 消费者消费消息后，给 Broker 返回 ACK 失败，导致同一条消息再次发送

### 6.4 消息顺序性保证

- **单分区保证**：在同一分区内，消息是有序的（Kafka、Redis Stream）
- **单队列保证**：在同一队列中，消息具有 FIFO
- **多分区/多队列**：无法保证全局顺序，只保证分区/队列内顺序
- 增加分区数量可增加并行性，也会牺牲全局顺序性

### 6.5 Kafka

#### 基本架构组件

| 组件 | 说明 | 关键特性 |
|------|------|---------|
| Broker | Kafka 集群中的服务器节点 | 水平扩展、高可用（副本机制） |
| Topic | 消息的逻辑标识 | 支持多个分区、可配置副本数 |
| Partition | Topic 的物理分片 | 分区内消息有序、分区间可并行 |
| Consumer Group | 一组消费者实例 | 组内负载均衡、组间互不影响 |

#### Partition 分区

- Topic 被分成多个 Partition 分区
- 每个 Partition 都是一个单独的 log 文件，每条记录以追加（append）的形式写入
- Kafka 把 Topic 的多个 Partition 分布在多个 Broker 中

#### Offset

- Partition 中的每条记录都会被分配一个唯一的序号（Offset，偏移量）
- Offset 是递增的、不可变的数字，由 Kafka 自动维护
- 一个 Partition 内部消息有序，一个 Topic 跨 Partition 是无序的

#### Kafka 的流处理应用

Kafka 常用于实时流处理，结合 Apache Flink 或 Spark Streaming 进一步处理和分析。

### 6.6 RabbitMQ

#### AMQP 协议基础

AMQP（Advanced Message Queuing Protocol）是消息队列中的开放标准协议。关键特性：可靠性、可扩展性、灵活性。

#### 核心概念

| 概念 | 说明 |
|------|------|
| Exchange | 负责接收消息并将其路由到适当的队列 |
| Queue | 存储消息，消费者从中获取消息进行处理 |
| Binding | 将Exchange与Queue绑定的规则 |
| Routing Key | 消息的路由关键字 |

#### Exchange 类型

**Direct Exchange**：Routing Key 与 Binding Key 完全匹配，适合精确分类投递。

**Fanout Exchange**：忽略 Routing Key，把消息广播发送到所有绑定队列，适合系统公告、配置更新通知。

**Topic Exchange**：Routing Key 与 Binding Key 按模式匹配。通配符：`*` 匹配一个单词，`#` 匹配零个或多个单词。适合事件分类分发。

| 绑定键 | 含义 |
|--------|------|
| `order.*` | 匹配 order.created、order.paid |
| `*.error` | 匹配 db.error、app.error |
| `order.#` | 匹配所有 order 开头的主题 |

#### 消息确认机制（ACK）

消费者处理完消息后发送 ACK 给 RabbitMQ，确保消息不会丢失。

#### 消息持久化

- 持久化消息会同时写入磁盘和内存
- 非持久化消息在内存不够用时写入磁盘（一般重启后就没有了）

#### 死信队列（DLQ）与延迟消息

**死信队列**：当消息无法被正常消费时，消息将被转移到的专门队列。

死信发生的常见原因：
- 消息 TTL 过期
- 队列长度达到最大值
- 消息被拒绝

**延迟消息**：通过设置消息的延迟时间，消息会在指定的时间后再被消费。实现方式：延迟交换机（Delayed Message Exchange）。

## 七、分布式存储系统

### 7.1 CAP 定理

| 特性 | 含义 |
|------|------|
| 一致性（C） | 所有节点同一时刻看到相同数据 |
| 可用性（A） | 每个请求都收到响应（不保证是最新数据） |
| 分区容错（P） | 节点间通信故障时系统仍可运行 |

**核心结论**：分布式系统中，C、A、P 三者最多同时满足两个。

网络故障（P）在真实环境中无法避免。分区发生时：
- 选 C（一致性）：拒绝响应，等节点联通后再服务 → 牺牲可用性
- 选 A（可用性）：继续服务，可能返回旧数据 → 牺牲一致性

| 选择 | 含义 | 典型系统 |
|------|------|---------|
| CP | 网络分区时拒绝服务，确保数据一致 | ZooKeeper、etcd、HBase |
| AP | 网络分区时继续响应，允许短暂不一致 | Cassandra、DynamoDB |
| CA | 理论上不存在（仅适用于单机场景） | MySQL/PostgreSQL（单节点） |

#### PACELC 模型

发生网络分区（P）时 → 选可用（A）还是一致（C）？正常运行（E=Else）时 → 选低延迟（L）还是强一致（C）？

| 系统 | 分区时 | 正常时 |
|------|--------|--------|
| DynamoDB | PA（优先可用） | EL（低延迟优先） |
| Cassandra | PA | EL |
| HBase | PC（优先一致） | EC（一致性优先） |
| MongoDB | PA | EC |

### 7.2 BASE 理论

BASE 是对 CAP 中 AP 路线的进一步阐述。核心思想：放弃强一致性，换取高可用和高性能。

| 缩写 | 全称 | 含义 |
|------|------|------|
| BA | Basically Available | 允许部分功能降级，但系统整体可用 |
| S | Soft State | 数据不需要时刻一致，允许副本间短暂不同步 |
| E | Eventually Consistent | 停止写入后，经过一段时间所有副本数据趋于一致 |

#### ACID vs BASE

| 维度 | ACID | BASE |
|------|------|------|
| 一致性 | 强一致性 | 最终一致性 |
| 可用性 | 可能降低 | 高可用 |
| 适用场景 | 银行转账、订单支付 | 社交动态、商品库存展示 |
| 代表系统 | MySQL、PostgreSQL | DynamoDB、Cassandra |

### 7.3 数据分片策略

#### 为什么需要数据分片？

- 容量瓶颈：单机磁盘有限，无法应对 PB 级数据
- 性能瓶颈：单机无法撑住高并发
- 可用性风险：单点故障

#### 哈希分片（Hash Sharding）

核心公式：`node_id = hash(key) % N`

- 优点：数据分布均匀，负载均衡好
- 缺点：节点数变化时大量数据需迁移（3台→4台，约75%数据需迁移）；不支持范围查询
- 代表：Redis Cluster（CRC16 % 16384）

#### 一致性哈希（Consistent Hashing）

- 设计目标：解决传统哈希节点增减时大量数据迁移的问题
- 核心原理：哈希空间组成虚拟圆环（0 ~ 2^32-1），节点和 Key 均映射到环上，Key 顺时针找最近节点存入
- 节点增减优势：扩/缩容只影响 1/N 的数据

| 对比 | 传统哈希 | 一致性哈希 |
|------|---------|-----------|
| 增删节点 | 几乎所有数据迁移（~91%） | 只影响相邻节点（~9%） |
| 查询路由 | 直接计算 hash(key)%N | 顺时针找最近节点 |

**虚拟节点（Virtual Nodes）**：每个物理节点在哈希环上注册多个"分身"，均匀散落在环的各处。实践中通常每个物理节点对应 100~200 个虚拟节点。代表系统：Cassandra、DynamoDB。

#### 范围分片（Range Sharding）

- 原理：按 Key 的值范围将数据划分到不同节点
- 优点：范围查询高效，数据有序存储
- 缺点：数据倾斜时产生热点
- 代表：HBase、Spanner、BigTable

### 7.4 向量时钟（Vector Clock）

向量时钟记录每个节点的写入次数，用于检测并发写入和冲突。

- 如果一个版本在所有维度上都不小于另一个，并且至少一维更大，就说明它"包含"另一个，是后继版本
- 两个版本互不包含（并发写入）→ 冲突！需应用层合并
- 向量时钟能精确检测（不是解决）并发写入，冲突合并需交由应用层处理

### 7.5 分布式存储全景图

| 类别 | 代表系统 | 数据模型 | 一致性 | 典型场景 |
|------|---------|---------|--------|---------|
| KV 存储 | Redis, DynamoDB | Key-Value | AP/CP | 缓存、会话、配置 |
| 文档存储 | MongoDB | JSON 文档 | 可调 | 内容管理、用户画像 |
| 列族存储 | HBase, Cassandra | Column Family | CP/AP | 时序、日志、大数据 |
| 图数据库 | Neo4j, JanusGraph | 图（节点+边） | CP | 社交网络、知识图谱 |
| NewSQL | TiDB, Spanner | 关系表 | CP | 金融、电商核心业务 |
| 时序数据库 | InfluxDB, TimescaleDB | 时间序列 | AP | 监控、IoT |

### 7.6 列族存储对比

| 维度 | HBase | Cassandra | Google Bigtable |
|------|-------|-----------|----------------|
| 一致性 | 强一致（CP） | 可调一致性（AP） | 强一致 |
| 架构 | Master-Slave | P2P 去中心化 | 全托管 |
| 适用场景 | 大数据分析+随机读写 | 高写入+全球分布 | GCP 大数据 |

选型口诀：已有 Hadoop 生态、要强一致 → HBase；全球部署、要高可用 → Cassandra；用 GCP → Cloud Bigtable。

### 7.7 NewSQL

兼备 SQL 的关系型模型与 ACID 事务，同时具备 NoSQL 的水平扩展能力。

代表产品：
- **Google Spanner**：全球分布式 SQL，TrueTime 保证外部一致性
- **CockroachDB**：开源 NewSQL，兼容 PostgreSQL
- **TiDB**：国产 NewSQL，MySQL 兼容，HTAP 混合负载

## 八、分布式文件系统

### 8.1 三种存储类型

| 维度 | 块存储 | 文件存储 | 对象存储 |
|------|--------|---------|---------|
| 抽象层级 | 最低（裸盘） | 中（树状目录） | 最高（扁平桶） |
| 访问接口 | SCSI/iSCSI | POSIX/NFS/SMB | HTTP REST API |
| 性能表现 | 极低延迟、高 IOPS | 较高吞吐、中等延迟 | 超高吞吐、延迟较高 |
| 扩展能力 | 较弱 | 中等 | 极强（轻松扩展至 EB 级） |
| 修改方式 | 支持随机修改 | 支持随机修改 | 只能整体覆盖替换 |
| 适用场景 | 数据库、虚拟机系统盘 | 多机共享日志、办公文档 | 海量图片/视频、冷数据归档 |

选型建议：跑系统与数据库选块存储，多机共享读写选文件存储，海量多媒体与静态资源选对象存储。

### 8.2 Google File System（GFS）

#### 设计背景

- 搜索引擎需要存储 PB 级网页索引数据
- 使用廉价 x86 商用服务器（组件故障是常态）
- 大文件为主（GB级），追加写入为主，随机修改极少
- 高吞吐率比低延迟更重要

#### 四大核心假设

1. 系统由大量廉价易损节点组成
2. 系统主要存储大文件（数百万个100MB以上的对象）
3. 读写模式固定（大规模流式读取、顺序追加写入）
4. 并发追加语义

#### GFS 架构

- **Master（控制流）**：唯一的主节点，管理元数据（目录树、文件到Chunk的映射、Chunk位置）
- **ChunkServer（数据流）**：存储实际数据块（Chunk），每个Chunk默认64MB，通常3副本
- **Client**：向Master询问元数据，然后直接与ChunkServer进行数据交互

#### 关键创新点

1. **单一Master设计**：简化架构，避免复杂的分布式一致性协议
2. **控制流与数据流分离**：数据传输不经过Master，避免Master成为网络瓶颈
3. **大Chunk策略（64MB）**：极大减少Master的元数据管理压力

#### 追加写入流程（Pipeline 机制）

1. 授权主副本：Master 在3个副本中指定一个为 Primary
2. 数据链式推送：Client → 最近副本A → B → C（充分利用全双工带宽）
3. 执行写入顺序：Primary 定好顺序后通知所有 Secondary 副本按相同顺序落盘

一致性妥协：GFS 采用至少一次语义，不保证副本字节级完全一致。

### 8.3 HDFS（Hadoop Distributed File System）

#### 概述

HDFS 是 Apache Hadoop 大数据生态的底层基石，设计深度借鉴了 GFS 论文，用 Java 实现。

| 设计目标 | 放弃的特性 |
|---------|-----------|
| 超大文件处理（TB/PB 级） | 不适合海量小文件存储 |
| 流式数据访问（一次写入，多次读取） | 不支持低延迟数据随机访问 |
| 高容错与低成本 | 强一致性随机修改（仅支持追加） |
| 计算向数据移动 | 计算与存储完全分离架构 |

#### 计算向数据移动

传统架构将数据读入内存计算；HDFS 配合 MapReduce/Spark，将计算程序调度到数据所在的 DataNode 上运行，实现网络零拷贝。

#### 架构组件

| 组件 | 职责 |
|------|------|
| NameNode | 管理文件系统命名空间和元数据；存储文件→Block 映射。全内存运行，1GB内存约管理100万个Block |
| DataNode | 存储实际数据 Block（默认128MB）；每3秒向 NameNode 发送心跳 |
| Secondary NameNode | 定期合并 EditLog 和 FsImage（不是热备份！） |
| Block | 数据块，默认 128MB，每个 Block 3 副本 |

### 8.4 对象存储

采用扁平的命名空间（无目录层级），数据以对象（Object）为单位存储在桶（Bucket）中。

核心组成要素：
- **Key**：全局唯一标识符
- **Value**：不透明二进制块，最大可达5TB
- **Metadata**：与数据紧密绑定，可自定义标签

### 8.5 Ceph：统一存储架构

底层构建 RADOS（可靠自主分布式对象存储），上层提供三种接口：

- **RBD（块设备）**：将 RADOS 映射成 Linux 块设备，支持秒级快照和克隆（COW机制），常用于虚拟机系统盘
- **CephFS（文件系统）**：兼容 POSIX 的文件系统，MDS 集群采用动态子树分区策略
- **RGW（对象网关）**：原生支持 AWS S3 和 OpenStack Swift 双重 API 规范

### 8.6 分布式存储全景对比

| 对比维度 | HDFS | Ceph | MinIO | GlusterFS |
|---------|------|------|-------|-----------|
| 架构流派 | 中心化主从 | 去中心化统一 | 轻量级对象 | 无中心哈希 |
| 核心优势 | 计算向数据移动 | 块/文件/对象通吃 | 极致轻量、超高吞吐 | 部署极其简单 |
| 痛点 | 极度害怕海量小文件 | 学习曲线陡、运维灾难 | 仅支持对象接口 | 小文件性能严重下滑 |
| 适用场景 | 大数据批处理 | IaaS 私有云底座 | 云原生 AI 数据湖 | 传统 NAS 平替 |

## 九、并行编程模型

### 9.1 并行计算基础

#### 为什么需要并行计算？

单机硬盘 100MB/s 读 1TB 需要 2.8 小时；1TB 分给 100 台，每台 10GB，数小时缩短为 10 分钟。

#### 三大流派

- **数据并行**：不同数据子集，相同操作逻辑
- **任务并行**：相同/不同数据，不同操作逻辑
- **流水线**：源源不断的流式数据，多阶段串联处理

#### Amdahl 定律

加速比 `S(N) = 1 / (f + (1-f)/N)`（f=串行部分比例，N=处理器数量）

即便 N→∞，加速比上限 = 1/f

### 9.2 MapReduce

#### 设计哲学

2004年 Google 发表。核心思想：计算向数据移动（Moving Computation to Data）——不移动庞大的数据，而是把轻量的程序代码发送到数据所在的节点执行。

#### Map 与 Reduce

**Map 函数（数据打散与重塑）**：
- 输入：键值对 `<K1, V1>`
- 输出：零个或多个中间键值对 `list(<K2, V2>)`
- 动作：过滤、提取、转换

**Reduce 函数（数据聚合）**：
- 输入：中间键和它的值集合 `<K2, list(V2)>`
- 输出：最终结果 `list(<K3, V3>)`
- 动作：求和、求最值、拼接

同一种 Key 必然被送到同一个 Reduce 节点。

#### Shuffle

介于 Map 和 Reduce 之间的过程，保证所有 Key 相同的中间数据都能被送到同一个 Reduce 任务中去。

流程：Map端溢写（Spill）→ 网络拉取（Fetch）→ 归并排序（Merge）

#### Combiner

运行在 Map 端的"迷你 Reduce"，在数据离开 Map 节点前先合并一次，减少网络传输。

- 适用：Sum（求和）、Max（最大值）—— 满足交换律和结合律
- 不适用：Average（平均值）

#### 整体执行生命周期

1. **InputSplit**：1TB文件按128MB切块
2. **Map阶段**：每个分片启动一个Map Task执行
3. **Shuffle阶段**：数据按规则在集群中大迁徙
4. **Reduce阶段**：接收合并后的数据执行聚合
5. **Output阶段**：最终结果写入HDFS

#### 容错机制

- **无状态计算（Shared-Nothing）**：Map 和 Reduce 互不干扰，失败了重跑就行
- **中间结果落盘**：Map 的结果写入本地磁盘

#### 推测执行（Speculative Execution）

当 Master 发现某个 Task 进度远低于平均水平时，在其他空闲机器上启动一个相同的"替补任务"，哪个先跑完就用哪个的结果。

注意：涉及写数据库等有副作用的任务不能开启推测执行。

#### 典型应用

**WordCount：**

```python
def map_function(document):
    for word in document.split():
        emit(word, 1)

def reduce_function(word, counts_list):
    total = sum(counts_list)
    emit(word, total)
```

**排序与 Top N：**
- Map端：每个节点只保留局部TopN，大幅减少Shuffle传输量
- Reduce端：汇总所有局部冠军，选出全局TopN

## 十、Spark 大数据处理

### 10.1 Spark 的设计动机

MapReduce 对迭代优化任务（机器学习、交互式查询），中间结果反复落盘会非常慢。

Spark 核心思想：
- 尽量把中间结果保留在内存，减少磁盘 I/O
- DAG 执行引擎
- 统一批处理与流处理

### 10.2 DAG 执行引擎

Spark 把一连串 Transformation 看成一个有向无环图（DAG）。依据 Shuffle 边界，把 DAG 切成多个 Stage，Stage 内部尽量流水执行。好处：系统可以观察全局依赖。

### 10.3 Spark 适用场景

| 场景 | 是否适合 | 原因 |
|------|---------|------|
| 海量离线 ETL | 适合 | 并行处理强，生态成熟 |
| 交互式 SQL 分析 | 适合 | DataFrame + Catalyst 性能较好 |
| 迭代机器学习 | 适合 | 缓存与迭代计算优势明显 |
| 毫秒级事务处理 | 不适合 | Spark 不是 OLTP 数据库 |
| 超低延迟实时控制 | 通常不适合 | 微批模型不满足毫秒级要求 |

### 10.4 Spark 运行架构

- **Cluster Manager**：集群资源管理器
- **Worker Node**：运行作业任务的工作节点
- **Driver**：每个应用的任务控制节点
- **Executor**：每个工作节点上负责具体任务的执行进程

Executor 的优点：
- 利用多线程执行任务，减少启动开销
- BlockManager 存储模块将内存和磁盘共同作为存储设备

#### Driver Program

运行 main 函数，创建 SparkSession，解析 Transformation/Action，当 Action 出现时把逻辑转换成 Job/Stage/Task。

#### Executor

长期驻留的进程，负责接收 Driver 下发的 Task 并实际执行，管理本地 Cache 与 Shuffle 数据。

### 10.5 RDD（Resilient Distributed Dataset）

RDD 是 Spark 最基础的数据抽象。

**五大特性：**

| 特性 | 含义 | 作用 |
|------|------|------|
| Partitions | 分区集合 | 决定并行度与任务划分 |
| Dependencies | 与父 RDD 的依赖 | 决定 Stage 与容错恢复 |
| Compute Function | 每个分区如何计算 | 定义转换逻辑 |
| Partitioner | 键值数据如何分区 | 优化聚合与连接 |
| Preferred Locations | 首选位置 | 提高数据本地性 |

#### Dependency

- **窄依赖**：子分区只依赖少量父分区，适合流水执行，如 map、filter
- **宽依赖**：父 RDD 的一个分区对应一个子 RDD 的多个分区，可能产生 Shuffle，如 reduceByKey、join、groupByKey

Spark 根据依赖关系切分 Stage 并进行容错恢复。

#### 血缘追踪（Lineage）与容错

Spark 为 RDD 记录 Lineage（血缘），而不是对每个中间结果都进行复制。一旦某个分区丢失，沿着血缘链重新计算该分区。对于代价太高的数据，通过 Checkpoint 持久化。

### 10.6 Transformation 与 Action

| 类别 | 代表操作 | 特点 |
|------|---------|------|
| Transformation | map、filter、flatMap、reduceByKey | 返回新 RDD，惰性执行 |
| Action | collect、count、take、saveAsTextFile | 触发真正计算 |

**惰性执行（Lazy Evaluation）**：Transformation 默认不会立即运行，等 Action 出现后统一执行。好处：减少无意义中间结果，给优化器留出全局优化空间。

### 10.7 PySpark 示例

```python
# WordCount
from pyspark.sql import SparkSession
spark = SparkSession.builder.appName("RDDWordCount").master("local[*]").getOrCreate()
sc = spark.sparkContext
lines = sc.textFile("data/words.txt")
words = lines.flatMap(lambda line: line.split())
pairs = words.map(lambda w: (w.lower(), 1))
counts = pairs.reduceByKey(lambda a, b: a + b)
print(counts.collect())
spark.stop()
```

### 10.8 DataFrame 与 Spark SQL

DataFrame = 带 Schema 的分布式表，让用户用 SQL 描述结构化查询。

| 操作 | 作用 |
|------|------|
| select | 列选择/表达式 |
| filter/where | 行过滤 |
| groupBy | 分组聚合 |
| orderBy | 排序 |
| join | 表连接 |

### 10.9 Catalyst 查询优化器

工作流程：
1. Logical Plan Creation
2. Logical Plan Optimization（Push down filters、Combine operations）
3. Physical Plan Generation
4. Code Generation

## 十一、大规模图计算

### 11.1 图计算的典型应用场景

- 社交网络分析（好友推荐、社区发现、影响力分析）
- 推荐系统（协同过滤、商品推荐）
- 知识图谱（实体关系抽取、知识推理）
- 金融风控（欺诈检测、洗钱追踪）

### 11.2 图数据的基本结构

- **顶点（Vertex）**：基本单元，具有唯一ID、可选标签和属性
- **边（Edge）**：表示顶点之间的关系，具有方向性，可包含属性

### 11.3 图计算 vs 关系数据库

| 特性 | 图计算 | 关系数据库 |
|------|--------|-----------|
| 数据模型 | 节点+关系 | 表+行+列 |
| 查询方式 | 遍历关系 | SQL JOIN |
| 深度查询 | 高效 | 性能急剧下降 |
| 适用场景 | 关系密集型 | 事务处理 |

### 11.4 NetworkX

纯 Python 图计算库，轻量，适合教学和原型验证。

| 图类型 | 边是否有向 | 是否允许多重边 | 典型应用 |
|--------|-----------|--------------|---------|
| Graph | 无向 | 否 | 朋友关系 |
| DiGraph | 有向 | 否 | 关注关系、网页链接 |
| MultiGraph | 无向 | 是 | 航班班次 |
| MultiDiGraph | 有向 | 是 | 交通流量 |

### 11.5 PageRank 算法

#### 迭代计算公式

`PR(A) = (1-d)/N + d * (PR(B)/L(B) + PR(C)/L(C) + ...)`

- PR(A)：页面A的PageRank值
- d：阻尼因子，通常取0.85（85%概率继续点击链接，15%概率随机跳转）
- N：总页面数
- L(B)：页面B的链出数量

#### 收敛条件

- 差值阈值判断：新旧PR差值绝对值最大值小于阈值（10^-6 / 10^-8）
- 迭代次数上限：100~500次

#### 特殊节点处理

- 悬挂节点（无出链）：PR 值均分至所有页面
- 孤立节点（无任何连接）：PR 迭代后衰减至 0

### 11.6 Neo4j

专为存储和查询图数据设计的数据库，使用 Cypher 查询语言，支持完整的 ACID 事务。

#### Cypher 查询语言基础

```cypher
-- 查询Alice的所有朋友
MATCH (a:Person {name:"Alice"})-[:KNOWS]->(friend)
RETURN friend.name, friend.age

-- 朋友的朋友（二度关系）
MATCH (a:Person {name:"Alice"})-[:KNOWS*2]->(fof)
WHERE NOT (a)-[:KNOWS]->(fof)
RETURN DISTINCT fof.name AS 推荐好友

-- 创建带标签的节点
CREATE (n:Person {name:"Bob", age:25, city:"成都"})

-- 创建关系
MATCH (a:Person {name:"Alice"}), (b:Person {name:"Bob"})
CREATE (a)-[:KNOWS {since:2020}]->(b)

-- 最短路径查询
MATCH p=shortestPath((a)-[:KNOWS*]-(b))
RETURN p
```

### 11.7 NetworkX vs Neo4j

| 维度 | NetworkX | Neo4j |
|------|----------|-------|
| 产品类型 | Python库/分析工具 | 图数据库管理系统 |
| 计算模式 | 内存计算 | 持久化存储+计算 |
| 数据规模 | 小规模（<10万节点） | 大规模（数十亿节点） |
| 数据持久化 | 无（重启丢失） | 有（ACID事务） |
| 适用场景 | 算法验证、原型开发 | 生产系统、实时查询 |

决策口诀：教学/原型 → NetworkX；生产/持久化 → Neo4j；超大规模 → GraphX

## 十二、云原生平台

### 12.1 Helm：Kubernetes 的包管理器

#### 为什么需要 Helm？

一个真实应用通常不是一个 YAML，而是一组相互关联的 YAML。手工维护多套环境配置时，配置漂移会快速累积。

**Helm 的作用：**
- 应用打包：把一组 Kubernetes 资源组织成 Chart
- 参数化部署：通过 values.yaml 适配 dev/test/prod
- 一键部署：`helm install myapp ./chart -f prod.yaml`
- 版本管理：Chart 有版本，Release 也有历史版本

#### Chart 结构

```
myapp/
├── Chart.yaml      # Chart 元信息（名称、版本、依赖）
├── values.yaml     # 默认参数，模板渲染的数据来源
├── charts/         # 存放依赖 Chart
└── templates/      # Kubernetes 资源模板
    ├── deployment.yaml
    ├── service.yaml
    └── ingress.yaml
```

templates 中使用 `{{ .Values.xxx }}` 占位符，渲染后才是 Kubernetes 资源。同一个 Chart 通过不同 values 文件可部署到 dev/test/prod。

### 12.2 Operator 模式

#### 为什么需要 Operator？

Kubernetes 能维持通用资源的期望状态，但不了解数据库、监控等领域知识。Operator 把运维经验写成控制器，让系统持续自动收敛。

**Operator = CRD + Controller + 领域运维知识**

#### CRD（Custom Resource Definition）

用于扩展 Kubernetes API。用户像操作 Deployment 一样操作业务对象。

- **spec**：用户希望系统达到的状态
- **status**：控制器观测到并写回的实际状态
- spec/status 分离是声明式 API 的关键设计

#### Controller：Reconcile Loop

控制器不断比较期望状态与实际状态，发现差异后执行动作修正系统。每次 Reconcile 都应尽量做到幂等。

#### 常见 Operator 实例

| Operator | 管理对象 | 典型能力 |
|----------|---------|---------|
| Prometheus Operator | Prometheus/ServiceMonitor | 监控系统的自动化管理 |
| MySQL Operator | MySQLCluster/Backup | 数据库生命周期管理 |
| Spark Operator | SparkApplication | Driver/Executor Pod 创建 |
| Cert-Manager | Certificate/Issuer | 证书申请、续期和分发 |

### 12.3 Spark on Kubernetes

- **Driver Pod**：运行 main 函数，创建 SparkContext，向 K8s 请求 Executor Pod，把 Job 切分成 Stage 和 Task
- **Executor Pod**：运行 Spark Executor，内部可用多线程运行多个 Task，使用内存缓存数据

| | Spark on YARN | Spark on Kubernetes |
|---|---|---|
| 生态基础 | Hadoop 生态、HDFS、YARN 队列 | 容器平台、镜像、Namespace |
| 资源隔离 | YARN 队列与 Container | Namespace、ResourceQuota、Pod |
| 适合场景 | 已有 Hadoop 基础设施 | 云原生数据平台与统一调度 |

### 12.4 GitOps

#### 核心理念

- Git 作为唯一的真实来源
- 声明式配置：期望状态以 YAML/Helm Chart/Kustomize 等形式保存在 Git 中
- 任何变更先进入 Git，再由控制器同步到集群
- 集群中被手工修改的状态会被检测为 Drift

#### ArgoCD

自动化控制工具，定期监听比较 Git 期望状态和集群实际状态。状态一致为 Synced，存在差异为 OutOfSync。Sync 操作把差异同步到 Kubernetes 集群。

#### Flux

GitOps 自动化控制工具，由多个控制器组成：
- source-controller：获取 Git/Helm 源
- kustomize-controller：应用 Kustomize 配置
- helm-controller：管理 Helm Release
- notification-controller：事件通知
