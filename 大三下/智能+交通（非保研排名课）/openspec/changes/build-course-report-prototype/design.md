## 背景

当前仓库按“大作业1 / 大作业2 / 大作业3 / 课程设计”组织，课程报告网页尚未正式搭建，但根目录已经存在一份偏 Airtable 风格的 `design.md`，可以作为课程网站的视觉规范来源。课程报告主题聚焦“大小模型协同的智能交通管理决策系统（Demo 版）”，需要在一个轻量、可离线展示的网页中同时承载研究背景、系统架构、已完成成果、预警诱导流程与后续扩展方向。

当前约束包括：
- `课程设计/` 目录适合先从静态原型起步；
- 汇报场景优先考虑本地打开、答辩展示和后续增量扩展；
- 已完成的大作业 1 和大作业 2 需要在页面中形成成果映射，但当前不要求接入真实推理链路；
- 视觉风格需要尽量贴合根目录设计稿中的白底、深蓝文本、蓝色强调和卡片化布局。

## 目标 / 非目标

**目标：**
- 在 `课程设计/` 中实现一个可直接打开的课程报告网站原型。
- 将课程主题拆解为清晰的叙事模块，包括项目定位、协同架构、能力展示、成果挂接和演示流程。
- 使用统一的样式变量、卡片组件和响应式布局，保证后续扩展时无需重做页面结构。
- 提供少量前端交互，用于切换系统流程、预警场景或核心能力状态，增强 Demo 感。

**非目标：**
- 本次变更不接入后端、数据库或实时交通数据。
- 不实现真实模型推理、视频识别或 Isaac 仿真执行，仅提供原型占位和流程表达。
- 不追求完整产品化路由体系，优先单页展示和低成本部署。

## 设计决策

### 1. 第一阶段采用静态单页网站

选用 `index.html + styles.css + script.js` 的纯静态结构，而不是一开始就引入 React 或 Vue。

原因：
- 课程展示更看重快速可用和本地可运行；
- 当前内容量有限，静态页面足以表达主要信息；
- 便于后续再迁移到框架化前端。

备选方案：
- React 单页应用：更利于组件化，但初始化成本更高；
- PPT 式长图页面：制作更快，但扩展性和交互表达较弱。

### 2. 页面结构以“课程汇报叙事流”为主

页面将按“项目总览 -> 协同架构 -> 已完成成果 -> 决策闭环 -> Demo 计划 -> 路线图”组织，而不是按技术模块拆分导航。

原因：
- 更符合课堂汇报和答辩讲解的顺序；
- 更容易把大作业 1 和大作业 2 自然纳入最终系统主线。

备选方案：
- 按作业 1/2/3 拆栏目：对应关系清晰，但系统整体性较弱；
- 按技术组件拆栏目：技术表达更细，但不利于快速建立全局理解。

### 3. 使用设计 Token 统一视觉风格

在 CSS 中定义 `--theme_*` 变量，将根目录 `design.md` 中的主色、边框、阴影和圆角语义转化为课程网站自己的组件层。

原因：
- 能继承已有设计方向；
- 便于后续统一调整颜色、间距和组件风格。

备选方案：
- 直接写死样式：实现更快，但后期维护成本高；
- 完整照搬 Airtable 官网：容易失真，也不适合课程展示。

### 4. 用轻交互增强演示感

原型将加入少量轻量交互，例如场景切换、协同阶段切换或预警等级展示，而不引入复杂数据链路。

原因：
- 让答辩演示更像“系统在运行”；
- 保持开发成本可控，不被真实数据接入阻塞。

备选方案：
- 完全静态展示：最简单，但感染力不足；
- 模拟复杂数据大屏：工作量过大，且偏离课程汇报重点。

## 风险 / 权衡

- [风险] 页面内容偏概念化，缺少真实数据支撑时说服力不足 -> 预留实验截图、图表和指标插槽，便于后续补充。
- [风险] 静态单页后续扩展到多页面时可能需要重构 -> 通过模块化 section、卡片和 Token 设计降低迁移成本。
- [风险] 设计稿偏企业官网风格，直接照搬会削弱交通领域感 -> 通过系统架构图、态势卡片和预警术语强化专业性。
- [风险] 本地直接打开时资源路径可能出错 -> 使用纯相对路径和无构建依赖，保证双击即可访问。

## 迁移计划

1. 在 `课程设计/` 中创建静态页面文件和基础资源结构。
2. 先完成单页原型和轻交互脚本，确保可离线打开。
3. 后续按需把大作业 1 和大作业 2 的截图、指标和结果图嵌入到对应模块。
4. 如果后续需要在线部署，再平滑迁移到框架化工程或静态托管平台。

回滚策略：
- 删除 `课程设计/` 中新增静态文件即可恢复到变更前状态；
- OpenSpec 文档保留，作为后续重建原型的设计依据。
