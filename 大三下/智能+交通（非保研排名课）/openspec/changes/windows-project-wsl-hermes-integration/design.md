## 背景

当前项目主体运行在 Windows 工作区 `D:\大三下\智能交通` 中，前端和后端也都已经基于 Windows 环境跑通。但 Hermes Agent 官方明确要求通过 WSL2 运行，因此无法像普通 Python 依赖一样直接接入当前 Windows 运行时。如果整个项目整体迁移到 WSL，会打乱现有已经可用的前后端环境，所以更现实的方案是保留“Windows 主项目”，同时把 Hermes 作为 WSL 内部的专用任务执行层接入。

这意味着系统需要同时处理两套路径和运行环境：
- Windows 路径，例如 `D:\大三下\智能交通`
- WSL 路径，例如 `/mnt/d/大三下/智能交通`

同时又要保证 Hermes 依然满足项目约束：
- 只在当前项目工作区内运行；
- 只读写当前项目目录下的模板、状态目录和产物目录；
- 由 Windows 后端统一调度；
- 对前端和主业务 API 来说仍保持一个统一的任务系统体验。

## 目标 / 非目标

**目标：**
- 为当前 Windows 项目建立一套可复用的 WSL Hermes 接入方案。
- 支持后端通过 `wsl.exe` 调用 WSL 中安装的 Hermes。
- 提供 Windows 路径到 WSL 路径的稳定映射规则。
- 强制 Hermes 运行目录固定到当前项目在 WSL 中的对应路径。
- 让报表、播报稿和每日总结任务能通过 WSL Hermes 执行并把产物写回当前项目目录。
- 补充 Windows + WSL 联合运行所需的环境检查、启动说明和错误提示。

**非目标：**
- 不把整个项目整体迁移到 WSL 开发环境。
- 不要求 Windows 本机原生安装 Hermes。
- 不在本次变更中引入 Docker、远程 Linux 服务器或云端 Hermes 部署。
- 不改变主业务链路仍由 Windows 后端控制的基本架构。

## 设计决策

### 1. 采用“Windows 主控 + WSL Hermes 执行”的双环境结构

Windows 继续承载主项目目录、前端、后端和主任务状态；Hermes 只在 WSL 中运行，并由 Windows 后端通过 `wsl.exe` 调用。

原因：
- 保留现有可运行环境，迁移成本最低；
- 符合 Hermes 官方对 WSL 的要求；
- 可以在不动主系统的情况下把 Hermes 接进来。

备选方案：
- 整个项目迁移到 WSL：环境更统一，但会影响当前开发节奏；
- 不使用 Hermes：会失去自动化任务能力；
- 尝试原生 Windows 跑 Hermes：与官方支持范围不一致，风险高。

### 2. 路径统一通过“Windows -> WSL 映射器”转换

后端需要一个明确的路径转换层，把 Windows 路径转换为 WSL 路径。例如：
- `D:\大三下\智能交通` -> `/mnt/d/大三下/智能交通`

这个映射层将负责：
- 项目根目录映射；
- `.task_state`、模板目录和输出目录映射；
- 给 Hermes 提供正确的工作目录和文件参数。

原因：
- 路径映射是跨环境接入的核心问题；
- 集中处理比在各处手写路径拼接更稳。

### 3. Hermes 通过 `wsl.exe` 子进程方式调用

Windows 后端不直接嵌入 Hermes 运行时，而是通过 `wsl.exe` 启动一个明确的 WSL 命令，例如在指定发行版中切换到项目目录并调用 `hermes`。

原因：
- 兼容当前 Windows Python 后端；
- 易于实现、易于记录 stdout/stderr 和退出码；
- 便于后续做超时控制和错误分类。

备选方案：
- HTTP 方式调用 WSL 内的 Hermes 服务：可行但复杂度更高；
- 在 WSL 中跑额外网关再由 Windows 调：目前没有必要。

### 4. 工作区约束通过“固定工作目录 + 固定产物目录”保证

每一次 Hermes 调用都必须：
- 指向当前项目在 WSL 中的映射目录；
- 使用当前项目内的模板和状态文件；
- 把生成结果写回当前项目目录中。

原因：
- 满足“只在当前工作区运行”的要求；
- 避免读写用户其他 WSL 目录；
- 方便前后端继续按原有目录读取任务产物。

### 5. 按任务类型初始化 WSL 内资源

不同任务类型在执行前分别准备自己的资源：
- `report`：报表模板、输入摘要、输出文件路径
- `voice`：播报稿模板、摘要文本、输出文件路径
- `daily-summary`：汇总上下文、日期范围、输出文件路径

原因：
- 保持任务边界清晰；
- 便于后续单独调试和扩展；
- 不要求一次性准备所有 Hermes 能力。

## 风险 / 权衡

- [风险] 用户机器未安装 WSL2 或未配置 Linux 发行版 -> 在启动预检中显式检查 `wsl.exe` 和目标发行版。
- [风险] Windows 路径映射到 WSL 时处理不一致 -> 把路径映射逻辑集中封装并添加测试。
- [风险] WSL 中的 Hermes 未安装或不可执行 -> 增加独立的 Hermes 健康检查和明确报错。
- [风险] 产物写回路径错误导致前端不可见 -> 固定产物目录并由后端统一生成绝对路径。
- [风险] WSL 子进程调用超时或挂起 -> 为 `wsl.exe` 调用设置超时和失败兜底。

## 迁移计划

1. 增加 Windows -> WSL 的 Hermes 配置项，包括发行版、WSL 根路径和项目映射规则。
2. 实现路径映射和 WSL 预检逻辑。
3. 实现通过 `wsl.exe` 调用 Hermes 的执行适配器。
4. 为 `report`、`voice` 和 `daily-summary` 三类任务增加资源初始化与产物回写机制。
5. 更新任务 API 和前端任务中心，展示 WSL Hermes 的执行状态和错误信息。
6. 更新启动文档和排错文档，确保用户能在 Windows + WSL2 环境下运行。

回滚策略：
- 保持 `HERMES_ENABLED=false` 时系统仍可回退到本地兜底逻辑。
- 如果 WSL Hermes 接入不稳定，可只保留配置与预检代码，暂停真实调用。
