## 背景

当前项目已经完成两部分关键能力：
- `大作业1/` 中的交通流预测研究与实验结果；
- `大作业2/` 中的交通标志检测与目标识别实验工程；
- `课程设计/` 中的课程报告网站原型。

当前问题是，这三部分仍然是分离的：前端只有静态展示，后端尚未建立，模型没有统一调用入口，也缺少一个任务系统来处理报表、语音播报和总结类工作。用户希望把系统升级成“真实可用的完整系统”，并进一步部署 Hermes Agent，承担表格生成、语音播报、每日总结等辅助任务。

这是一次典型的跨模块系统升级，涉及：
- 前端从静态页面升级为应用；
- 后端从无到有；
- 模型推理由独立脚本升级为服务化入口；
- 引入 Agent 和后台任务；
- 补齐后续可部署、可维护、可扩展的系统结构。

## 目标 / 非目标

**目标：**
- 搭建一个可实际运行的智能交通管理决策系统 Demo，而不只是展示页。
- 打通“输入数据 -> 预测/识别 -> 决策研判 -> 输出预警/诱导/报表”的业务链路。
- 为前端提供统一 API，使用户可以查看结果、触发任务、下载表格和收听播报。
- 将 Hermes Agent 作为后台任务与运营助手接入系统，处理日报、表格导出、语音播报和定时总结。
- 为后续接入大作业 3 的具身执行层预留扩展接口。

**非目标：**
- 本次不要求一次性把所有模型训练代码重构为生产级云原生系统。
- 不在当前阶段实现高并发、多租户或复杂权限体系。
- 不把 Hermes Agent 作为核心实时推理链路的唯一依赖，避免主流程被外部 Agent 阻塞。
- 不承诺当前阶段完成 Isaac 仿真与具身控制集成，仅预留接口位置。

## 设计决策

### 1. 采用“四层架构”

系统采用“前端应用 + Python 后端 + 模型编排层 + Agent 任务层”的四层结构。

原因：
- 前端负责交互和展示；
- 后端负责业务 API 和数据组织；
- 模型编排层负责串联预测、识别和决策；
- Hermes Agent 负责异步任务和运营辅助。

备选方案：
- 单体脚本 + 页面直接调模型：实现快，但不可维护；
- 前后端全部用 JS/TS：技术统一，但现有模型资产主要在 Python，迁移成本高。

### 2. 后端优先采用 Python Web API

建议使用 FastAPI 作为后端主框架。

原因：
- 现有模型代码和实验资产主要基于 Python；
- FastAPI 容易封装推理接口、文件上传下载和后台任务；
- 类型定义和接口文档能力更适合后续联调。

备选方案：
- Flask：更轻，但类型约束和自动文档能力较弱；
- Node.js：语言统一，但模型服务桥接成本更高。

### 3. 模型调用通过统一编排接口暴露

后端向前端暴露统一的业务接口，例如：
- `/api/analyze-scene`
- `/api/predict-traffic`
- `/api/generate-briefing`
- `/api/tasks/*`

后端内部再决定调用哪些模块：
- 大作业 1 负责流量预测；
- 大作业 2 负责目标识别；
- 大模型决策模块负责态势总结、预警生成和诱导文案输出。

原因：
- 避免前端与多个模型细节耦合；
- 便于后续替换模型或增加缓存。

### 4. Hermes Agent 只负责异步任务和运营辅助

Hermes Agent 适合承担：
- 日报和阶段总结生成；
- 结构化结果转为 Excel / Markdown / Word 风格报表；
- 触发语音播报或生成播报文本；
- 定时任务、提醒和后台辅助工作。

不建议让 Hermes 直接接管实时主链路中的每一次预测或识别请求。

原因：
- 主链路应由后端显式控制，更稳定、更可监控、更可测试；
- Hermes 更适合做“智能执行器”，不适合作为核心推理总控。

### 5. 任务系统采用“后端任务队列 + Hermes 工作流触发”

建议引入轻量任务基础设施，由后端负责排队、状态跟踪、超时和历史记录，再根据任务类型触发 Hermes。

原因：
- 任务队列更适合处理状态、重试和可观测性；
- Hermes 更适合作为任务执行器，而不是通用任务数据库。

### 6. 前端升级为框架化应用

现有 `课程设计/` 原型将迁移到框架化前端，优先使用 React 生态。

原因：
- 便于承载分析入口、任务面板、结果区和导出功能；
- 更适合状态管理和 API 调用；
- 也更利于后续演示和扩展。

## 风险 / 权衡

- [风险] 模型代码原本偏实验脚本，服务化后稳定性不足 -> 先封装最小可用推理入口，逐步抽象。
- [风险] 大模型输出不稳定 -> 强制采用结构化输入输出格式，并在后端做校验和兜底。
- [风险] Hermes 接入方式选错会导致耦合过深 -> 把 Hermes 放在异步任务层，通过明确接口边界接入。
- [风险] 前后端、模型和 Agent 同时推进工作量较大 -> 分阶段交付，先打通主链路，再补报表、播报和日报。
- [风险] 语音播报依赖第三方 TTS 或本地模型 -> 先定义统一接口，首版先支持文本播报结果和可替换的 TTS Provider。

## 迁移计划

1. 保留现有 `课程设计/` 原型作为信息架构和视觉参考。
2. 新建框架化前端应用目录，并迁移现有页面内容为组件。
3. 新建 Python 后端服务，优先实现健康检查、场景分析、结果查询和任务接口。
4. 对大作业 1 和大作业 2 分别封装最小可调用入口，并提供统一编排服务。
5. 接入大模型决策接口，先输出结构化 JSON，再逐步生成自然语言摘要。
6. 增加后台任务和 Hermes Agent 接入，实现报表、播报和日报等异步任务。
7. 最后补齐部署配置、日志、环境变量模板和基础监控。

回滚策略：
- 若新系统不稳定，可继续保留现有 `课程设计/` 静态页面独立展示；
- 后端与任务系统独立部署，不影响已完成的大作业代码和实验结果；
- Hermes 集成为可选能力，不作为系统最小可运行条件。

## 开放问题

- 大模型决策层最终优先接哪类模型：本地模型、OpenAI 兼容接口，还是其他平台？
- Hermes 最终通过 CLI、HTTP 服务还是 MCP 协作模式接入？
- 语音播报首版采用浏览器 Web Speech、云端 TTS 还是本地 TTS？
- 首版数据输入是静态图片 / 文件上传，还是接入视频流与时序数据？
