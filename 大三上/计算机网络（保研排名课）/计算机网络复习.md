### 电路交换

（比特流直达终点）

- 优点
  1. 通信时延小
  2. 有序传输
  3. 没有冲突
  4. 适用范围广
  5. 实时性强
  6. 控制简单
- 缺点
  1. 建立连接时间长
  2. 线路独占，使用效率低
  3. 灵活性差
  4. 难以规格化

### 报文交换

- 优点
  1. 无需建立连接
  2. 动态分配线路
  3. 提高线路可靠性
  4. 提高线路利用率
  5. 提供多目标服务
- 缺点
  1. 引起了转发时延
  2. 需要较大存储缓存空间
  3. 需要传输额外的信息量

### 分组交换

- 优点
  1. 无需建立连接
  2. 线路利用率高
  3. 简化了存储管理
  4. 加速传输
  5. 减少出错概率和重发数据量
- 缺点
  1. 引起了转发时延
  2. 需要传输额外的信息量
  3. 对于数据报服务，存在失序、丢失或重复分组的问题；对于虚电路服务，存在呼叫建立、数据传输和虚电路释放三个过程

## 计算机网络性能指标

### 比特

计算机中**数据量的单位**，也是信息论中信息量的单位。一个比特就是二进制数字中的一个 1 或 0。

#### 常用数据量单位

- 8 bit = 1 Byte
- KB = 2¹⁰ B
- MB = K·KB = 2¹⁰·2¹⁰ B = 2²⁰ B
- GB = K·MB = 2¹⁰·2²⁰ B = 2³⁰ B
- TB = K·GB = 2¹⁰·2³⁰ B = 2⁴⁰ B

### 速率

连接在计算机网络上的主机在数字信道上传送比特的速率，也称为**比特率或数据率**。

#### 常用数据率单位

- bit/s（b/s，bps）

- kb/s = 10³ b/s（bps）

- Mb/s = k·kb/s = 10³·10³ b/s = 10⁶ b/s（bps）

- Gb/s = k·Mb/s = 10³·10⁶ b/s = 10⁹ b/s（bps）

- Tb/s = k·Gb/s = 10³·10⁹ b/s = 10¹² b/s（bps）

  

### 带宽

在计算机网络中，带宽用于描述**通信线路**的数据传输能力，具体指：单位时间内，从网络中某一点到另一点能够通过的**最高数据率**。

#### 带宽的单位

与数据率单位一致



### 吞吐量

指**单位时间内**，通过某一网络、信道或接口的实际数据量。

#### 吞吐量的作用

是对现实网络的**实际传输能力的测量指标**，用于明确网络实际可承载的数据量。



### 网络时延的组成

网络时延是数据从发送端到接收端的总延迟，包含 3 类核心时延：

1. **发送时延**

   计算方式：分组长度 ÷ 发送速率

   说明：由发送设备的速率（比如网卡、接口的速率）决定，是把数据 “推” 进信道需要的时间。

2. **传播时延**

   计算方式：信道长度 ÷ 电磁波传播速率

   说明：由信道介质的传播速率决定（自由空间：每秒 3×10⁸米；铜线：每秒 2.3×10⁸米；光纤：每秒 2.0×10⁸米），是信号在信道里 “传输” 的时间。

3. **处理时延**

   说明：由路由器等网络设备的转发处理耗时决定，通常没有固定计算方式，是设备解析、转发数据的时间。

短距离发送时延占主导，长距离传播时延占主导



### 时延带宽积的定义

时延带宽积是**传播时延**与**带宽**的乘积，可理解为：把网络线路比作管道，带宽是管道的横截面积，传播时延是管道的长度，时延带宽积就是管道的 “容积”。

#### 核心含义

1. 当发送端连续发送数据时，在第一个比特即将到达接收端的时刻，发送端已经发送了 “时延带宽积” 数量的比特。
2. 时延带宽积也被称为 “以比特为单位的链路长度”，它体现了链路在传播数据时，同时承载的最大比特数。



### 往返时间（RTT）的定义

RTT 是指数据从发送端发出，到接收端响应并返回至发送端的**双向交互总时间**，是衡量网络双向通信效率的关键指标。



## 网络体系结构分层

通信双方（H1、H2）的网络协议栈分为 4 层，数据按 “应用层→运输层→网际层→网络接口层” 的顺序封装，经路由器（R）转发后，在接收端反向解封装：

- **应用层**：提供具体服务（如 HTTP、SMTP、DNS）；
- **运输层**：负责端到端传输（TCP 可靠、UDP 快速）；
- **网际层**：实现跨网络的分组转发（核心是 IP 协议）；
- **网络接口层**：适配物理网络的传输规则。

### 2. IP 协议的核心定位

IP 协议是网络互联的 “核心枢纽”，体现为两大特性：

- **IP over everything**：IP 可适配任意网络接口（如以太网、无线等），实现不同物理网络的互联；
- **Everything over IP**：所有应用层服务（HTTP、SMTP 等）、运输层协议（TCP、UDP），都以 IP 为基础传输，是网络服务的 “通用载体”。

### 一、基本调制方法（将数字信号转换为模拟信号）

| 调制类型   | 核心原理                                                     | 特点                                     |
| ---------- | ------------------------------------------------------------ | ---------------------------------------- |
| 调幅（AM） | 通过 “有无载波输出” 表示数字信号（如 1 对应有载波、0 对应无载波） | 实现简单，但抗干扰性弱                   |
| 调频（FM） | 通过 “不同频率的载波” 表示数字信号（如 1 对应频率 f2、0 对应频率 f1） | 抗干扰性优于调幅，常用于广播、无线通信   |
| 调相（PM） | 通过 “载波的不同初始相位” 表示数字信号（如 1 对应 180° 相位、0 对应 0° 相位） | 抗干扰性强，是现代通信的常用基础调制方式 |

### 二、混合调制：正交振幅调制（QAM）

以 QAM-16 为例，其核心特点是**结合调幅与调相**：

1. 采用 12 种相位 + 每种相位 1~2 种振幅，共生成 16 种不同的码元；
2. 每个码元对应 4 个比特（如 “0000” 对应某一相位 + 振幅组合），大幅提升传输效率；
3. 码元采用格雷码映射，相邻码元仅 1 个比特不同，可降低传输错误的影响。



### 一、奈氏准则的核心结论

在理想信道条件下，为避免码间串扰，码元传输速率存在上限：

| 信道类型     | 最高码元传输速率公式 | 说明              |
| ------------ | -------------------- | ----------------- |
| 理想低通信道 | 2W Baud（码元 / 秒） | W为信道带宽（Hz） |
| 理想带通信道 | W Baud（码元 / 秒）  | W为信道带宽（Hz） |

### 二、码元传输速率与比特率的关系

码元传输速率（波特率）与信息传输速率（比特率）的换算：

1. 当 1 个码元携带n比特信息时，**比特率 = 波特率 × n**；
2. 若 1 个码元仅携带 1 比特（如二进制码元），则比特率与波特率数值相等。



### 一、香农公式与参数定义

公式：\(c = W \times \log_2(1 + \frac{S}{N})\)其中各参数含义：



| 参数            | 定义与单位                                                   |
| --------------- | :----------------------------------------------------------- |
| c               | 信道极限信息传输速率，单位为比特 / 秒（b/s）                 |
| W               | 信道带宽，单位为赫兹（Hz）                                   |
| S               | 信道内信号的平均功率                                         |
| N               | 信道内高斯噪声的功率                                         |
| \(\frac{S}{N}\) | 信噪比（无量纲），通常用分贝（dB）表示：\(\text{信噪比(dB)} = 10 \times \log_{10}(\frac{S}{N})\) |

### 二、核心结论与实际限制

1. **影响因素**：信道带宽W或信噪比\(\frac{S}{N}\)越大，极限传输速率c越高；
2. **实际差距**：实际信道的传输速率会低于该极限值，因为香农公式未考虑脉冲干扰、信号衰减 / 失真等实际损伤。

# 3.数据链路层

- **链路（Link）**：仅指 “从一个节点到相邻节点的一段物理线路”，是纯粹的硬件连接（无协议）。
- **数据链路（Data Link）**：在链路基础上，增加了 “实现通信协议的硬件 + 软件”，是能完成数据传输的逻辑连接。
- **数据链路层的传输单位**：以 “帧” 为基本单元处理数据。

### 一、数据链路层的三个核心问题

1. 封装成帧

   将网络层的分组（IP 数据报）加上帧头、帧尾，形成 “帧”（数据链路层的传输单位），实现数据的边界划分。

2. 差错检测

   通过帧尾的 FCS（帧检验序列），检测传输过程中是否出现比特错误（如误码），但不负责纠错。

3. 可靠传输

   确保帧无差错、按序、不丢失地传输（常见于面向连接的链路，如 PPP 的可靠模式）。

### 1. 封装成帧

- **定义**：数据链路层给上层（网络层）的协议数据单元添加帧头、帧尾，形成 “帧”（数据链路层的传输单元）。
- 帧头 / 帧尾的作用
  - 包含控制信息（如地址、校验码等）；
  - 实现 “帧定界”：通过特定标识（如图中的`01111110`）区分不同帧的起始与结束。

### 2. 透明传输

- **定义**：数据链路层对上层传输的数据无限制，上层数据仿佛 “直接传输”，不受数据链路层规则影响。
- 实现方式
  - 面向字节的链路：用 “字节填充”（在特定字节前插入转义字节）避免数据与帧定界标识混淆；
  - 面向比特的链路：用 “比特填充”（在连续 5 个 “1” 后插入 “0”）解决类似问题（如图中数据部分的`11111`后插入 “0”）。

###  最大传送单元（MTU）的定义与作用

- **定义**：每种数据链路层协议都会规定帧数据部分的**长度上限**，即 MTU。
- **作用**：平衡 “传输效率” 与 “差错控制、链路复用” 的需求，是数据链路层的关键参数之一（例如以太网的 MTU 通常为 1500 字节）。



### 1. 差错检验基本概念

- **比特差错**：实际链路中，传输的比特（1/0）可能发生翻转（如 1 变 0、0 变 1），这是传输过程中的常见误差。
- **误码率（BER）**：衡量链路可靠性的指标，即传输错误的比特数与总传输比特数的比值（值越小，链路越可靠）。

### 2. 差错检测的实现：帧检验序列（FCS）

以以太网 V2 的 MAC 帧为例，其帧尾包含**4 字节的 FCS 字段**，作用是：

- 发送方：根据帧的有效数据（目的地址、源地址、类型、数据载荷），通过特定算法（如 CRC 循环冗余校验）计算出 FCS 值，附加到帧尾；
- 接收方：对收到的帧重新计算 FCS，若与帧尾的 FCS 不一致，则判定帧存在比特差错，通常会直接丢弃该帧。

### . 奇偶校验的原理

- 操作方式

  ：在待传输数据后添加 1 位 “校验位”，使整个数据（含校验位）中 “1” 的个数满足：

  - 奇校验：“1” 的个数为奇数；
  - 偶校验：“1” 的个数为偶数。

- **检测逻辑**：接收方统计 “1” 的个数，若与约定的奇偶性不符，则判定数据出错。

### 2. 奇偶校验的局限性

仅能检测**奇数位的比特差错**，无法检测**偶数位的比特差错**（此时 “1” 的奇偶性不变）。例如：

- 1 位误码：奇偶性改变，可检出；
- 2 位误码：奇偶性不变，无法检出。

### 1. CRC 的基本流程

CRC 的实现基于**收发双方约定的生成多项式 G (x)**，分为三步：

1. **发送方处理**：将待传输数据左移（位数等于生成多项式的最高次数），再与生成多项式进行 “模 2 除法”，得到的余数即为**冗余码**，附加到数据后一起传输；
2. **接收方处理**：将收到的 “数据 + 冗余码” 与生成多项式做 “模 2 除法”，若余数为 0，则判定数据无差错；若余数非 0，则判定数据存在误码。

### 2. 核心特点

- **检测能力强**：可检测出所有单比特错误、多数多比特错误，以及突发错误（错误比特连续出现的情况），检测效率远高于奇偶校验；
- **开销可控**：冗余码的长度由生成多项式的最高次数决定（例如常用的 CRC-32 生成多项式对应 4 字节冗余码），开销相对较小。

### 步骤 1：构造被除数

生成多项式 \(G(x)=x^3+x^2+1\) 的最高次数是 3，因此将待发送信息`101001`后添加 3 个 0，得到被除数：`101001000`。

### 步骤 2：构造除数

生成多项式的系数对应比特串（\(x^3\)对应 1、\(x^2\)对应 1、\(x^0\)对应 1，中间\(x^1\)项系数为 0），因此除数为：`1101`。

### 步骤 3：模 2 除法计算余数

模 2 除法的核心是 “异或运算”（相同为 0，不同为 1），计算过程：

- 用除数`1101`与被除数的前 4 位`1010`异或，得到结果后依次下移一位，重复异或操作；
- 最终得到的余数为`001`（位数与生成多项式最高次数一致，不足则补前导 0）。

### 最终结果

待发送信息附加冗余码后，实际传输的数据为：`101001001`。



### 1. 差错检测与可靠传输的关系

差错检测技术（如 CRC）仅能让接收方识别 “有误码的帧”，但这不是可靠传输 —— 可靠传输需要确保 “发送端发送的内容，接收端完整、无差错地收到”。

### 2. 数据链路层的两种服务类型

| 服务类型       | 核心特点                                                     |
| -------------- | ------------------------------------------------------------ |
| 不可靠传输服务 | 仅丢弃有误码的帧，不做其他处理（例如以太网的数据链路层提供的就是不可靠服务） |
| 可靠传输服务   | 通过重传、确认等机制，保证接收端收到与发送端完全一致的数据   |

### 1. 传输差错的类型

比特差错（1/0 翻转）只是传输差错的一种，从网络体系结构看，完整的传输差错还包括：

- **分组丢失**：分组在传输过程中因链路故障、拥塞等原因未到达接收端；
- **分组失序**：分组到达接收端的顺序与发送顺序不一致（例如多路径传输导致）；
- **分组重复**：同一分组被多次传输到接收端（例如重传机制误触发）

### 1. 停等协议核心逻辑

发送方每发送一个分组后，需 “停止发送并等待” 接收方的反馈（确认 / 否认），再决定后续操作。

### 2. 停等协议关键机制

| 机制        | 作用与实现                                                   |
| ----------- | ------------------------------------------------------------ |
| 确认（ACK） | 接收方收到无差错的分组后，发送 ACK 告知发送方 “可发送下一个分组”。 |
| 否认（NAK） | 接收方收到有误码的分组后，发送 NAK 告知发送方 “需重传该分组”。 |
| 超时重传    | 发送方发送分组后启动超时计时器，若超时未收到反馈，则重传该分组（解决分组丢失问题）；重传时间通常设为略大于往返时间。 |
| 分组序号    | 用 1 个比特（0/1）给分组编号，避免重传导致的分组重复（停止 - 等待协议中只需区分 “当前分组” 与 “重传分组”）。 |

### 1. 关键参数定义

- \(T_D\)：发送方发送一个数据分组的时间（发送时延）；
- \(T_A\)：接收方发送一个确认分组的时间（发送时延，通常远小于\(T_D\)，可忽略）；
- RTT：往返时间（数据分组从发送方到接收方的传播时延 + 确认分组从接收方到发送方的传播时延）。

### 1. 回退n帧GBN 的核心参数

- **分组编号**：采用`n`比特编号（课件中`n=3`，编号 0~7）。
- **发送窗口（Wₜ）**：取值范围为`1 < Wₜ ≤ 2ⁿ-1`（课件中`Wₜ=5`），超过此范围会导致接收方无法区分新、旧数据分组。
- **接收窗口（Wᵣ）**：固定为`1`，即接收方仅按序接收数据。

### 2. 关键机制

- **累积确认**：接收方无需逐个确认分组，仅对**按序到达的最后一个分组**发送确认（`ACKn`表示序号`n`及之前的分组均已正确接收）。
- **出错重传**：若某分组出错（如课件中 5 号分组误码），其后续已正确到达的分组会被 “牵连丢弃”，发送方需重传该出错分组及之后的所有分组（即 “回退 N 帧”）。

### 3. 发送方与接收方规则

| 角色   | 规则                                                         |
| ------ | ------------------------------------------------------------ |
| 发送方 | 可连续发送发送窗口内的分组；超时 / 收到重复确认时，重传未确认的所有分组。 |
| 接收方 | 仅接收窗口内的分组，按序滑动窗口；未按序的分组丢弃，并重复确认最近正确接收的分组。 |

### 4. 超出窗口范围的问题

若发送窗口`Wₜ > 2ⁿ-1`（如课件中`Wₜ=8`），接收方会无法区分新、旧分组（如重传的 0~7 号分组与新的 0 号分组编号重复），导致数据错误。

### 5. 协议定位

- GBN 是**连续 ARQ 协议**：基于 “流水线传输”（发送方无需等待确认即可连续发帧），通过 “发送窗口” 限制连续发送的分组数量，平衡传输效率与可靠性。
- GBN 属于**滑动窗口协议**：工作过程中，发送窗口（控制可发送的分组范围）和接收窗口（控制可接收的分组范围）会随确认 / 接收进度向前滑动。



### 1. 选择重传协议核心规则

- **分组编号**：采用 3 比特编号，序号范围为 0-7。

- 窗口尺寸限制

  ：

  - 发送窗口尺寸 \(W_T\) 需满足 \(1 < W_T \leq 2^{n-1}\)（n 为编号比特数，此处 \(n=3\)，故 \(W_T \leq 4\)）；
  - 接收窗口尺寸 \(W_R\) 需满足 \(1 < W_R \leq W_T\)。

- **错误示例**：若将 \(W_T、W_R\) 设为 5（超过上限），会导致接收方无法正确识别重复分组，引发协议失效。

### 2. 与其他协议的关联

- 当 \(W_T=1\) 时，SR 退化为**停止 - 等待协议（SW）**；
- 当 \(W_R=1\) 时，SR 退化为**回退 N 帧协议（GBN）**。



### 一、PPP协议定位与组成

PPP 是数据链路层广泛使用的点对点协议，核心由三部分构成：

1. **封装方法**：将网络层数据报封装成 PPP 帧；
2. **链路控制协议（LCP）**：负责建立、配置、测试数据链路连接；
3. **网络控制协议（NCPs）**：每套 NCP 对应一种网络层协议（如 IP、IPX），用于配置网络层参数。

### 二、PPP 帧格式

PPP 帧的结构及各字段作用：

| 字段              | 长度       | 作用                                                         |
| ----------------- | ---------- | ------------------------------------------------------------ |
| 标志（F）         | 1 字节     | 帧定界符，取值`0x7E`                                         |
| 地址（A）         | 1 字节     | 固定为`0xFF`（预留，无实际作用）                             |
| 控制（C）         | 1 字节     | 固定为`0x03`（预留，无实际作用）                             |
| 协议（P）         | 2 字节     | 标识数据部分的协议（如`0x0021`对应 IP 数据报，`0xC021`对应 LCP 分组） |
| 数据部分          | ≤1500 字节 | 网络层数据或控制分组                                         |
| 帧检验序列（FCS） | 2 字节     | 基于 CRC-CCITT 算法的校验位，用于差错检测                    |

### 三、透明传输机制

为避免数据部分出现帧定界符`0x7E`导致帧识别错误，PPP 采用两种填充方法：

1. 面向字节的异步链路（字节填充法）
   - 发送方：将`0x7E`替换为`0x7D 0x5E`，`0x7D`替换为`0x7D 0x5D`，ASCII 控制字符前插入`0x7D`并加`0x20`；
   - 接收方：反向转换恢复原始数据。
2. 面向比特的同步链路（比特填充法）
   - 发送方：扫描数据部分，每出现 5 个连续的 “1”，插入 1 个 “0”；
   - 接收方：扫描数据部分，每出现 5 个连续的 “1”，删除后续的 “0”。

### 四、差错检测

PPP 通过 FCS 字段（基于 CRC-CCITT 算法）实现差错检测：

- 接收方对帧（除首尾标志字段外）进行 CRC 校验，校验失败则丢弃该帧；
- 注意：PPP**不提供可靠传输服务**（不重传错误帧）。

### 五、工作状态流程

PPP 的链路建立与终止分为 5 个状态：

1. **静止**：物理层未连接；
2. **建立**：检测到载波，通过 LCP 协商链路参数（如最大帧长、鉴别协议）；
3. **鉴别**：使用 PAP（口令鉴别）或 CHAP（挑战握手鉴别）验证身份；
4. **网络**：通过 NCP 配置网络层参数（如 IPCP 分配 IP 地址）；
5. **打开**：链路就绪，可传输数据；
6. **终止**：链路故障或收到终止请求，返回静止状态。



### 一、MAC媒体接入控制的核心作用

MAC 用于解决**共享信道**中多站点的资源占用冲突问题（如图中多设备同时发送数据会产生 “碰撞”），确保多个站点有序使用传输介质。

### 二、MAC 的分类及特点

MAC 分为**静态划分信道**和**动态接入控制**两类：

#### 1. 静态划分信道

预先固定分配信道资源，适用于物理层（而非数据链路层），特点是灵活性差、突发数据传输的信道利用率低，具体方式包括：

- **频分多址**：按频率划分信道；
- **时分多址**：按时间片划分信道；
- **码分多址**：按编码序列划分信道（如 CDMA）。

#### 2. 动态接入控制

按需分配信道资源，适用于数据链路层，分为两类：

- 受控接入

  （已被淘汰）：

  - 集中控制：主站轮询各站点，存在单点故障风险；
  - 分散控制：通过令牌（如令牌环网）传递发送权，有序但效率较低。

- 随机接入

  - 所有站点竞争信道，可能发生碰撞（如以太网的 CSMA/CD）；
  - 需解决 “避免冲突” 和 “冲突后恢复” 问题，是共享式以太网的核心机制。

### 一、信道复用的核心概念

复用是通过一条物理线路同时传输多路信号，以充分利用传输介质的带宽（当介质容量大于单信道总通信量时适用）。

### 二、4 种复用技术的特点与应用

#### 1. 频分复用（FDM）

- **原理**：将物理信道的总带宽划分为多个子频带，每个用户占用一个子频带并行通信（子频带间需保留隔离频带避免干扰）。
- **特点**：所有用户同时占用不同频带，适用于模拟信号传输。
- **应用**：传统广播电视、调频广播等。

#### 2. 时分复用（TDM）

- **原理**：将时间划分为等长的 “时分复用帧”，每个用户占用帧内固定的时间间隙传输数据。
- **特点**：用户按时间顺序轮流占用信道，适用于数字信号传输；但存在 “空闲时间间隙” 的资源浪费问题。
- **应用**：早期电话交换网、传统数字通信系统。

#### 3. 波分复用（WDM）

- **原理**：本质是光信号的频分复用，将不同波长的光载波信号复用到同一条光纤中传输。
- **特点**：利用光纤的高带宽特性，可大幅提升传输容量（如图中每路 2.5Gb/s，多路复用后总容量达 20Gb/s）。
- **应用**：光纤通信骨干网（如长途光缆传输）。

#### 4. 码分复用（CDM，常称码分多址 CDMA）

- **核心特点**：所有用户可在**同一时间、同一频带**通信，通过 “独特码型（码片序列）” 区分不同用户，抗干扰能力强。

- 原理

  - 每个用户被分配唯一的*m*位码片序列（通常*m=64/128*）；
  - 发送比特 1 时，发送自身码片序列；发送比特 0 时，发送码片序列的反码；
  - 码片序列需满足 “相互正交（规格化内积为 0）”，以避免用户间干扰。

- 接收机制

  ：接收方通过计算 “叠加信号与目标用户码片序列的内积” 判断数据：

  - 结果为 1→发送比特 1；
  - 结果为 - 1→发送比特 0；
  - 结果为 0→未发送。

- **应用**：移动通信（如 3G 网络）、军事通信（信号隐蔽性强）。

### 三、复用与多址的区别

- **复用**：静态划分信道资源，子信道独立占用介质的部分资源；
- **多址**：动态分配信道给用户，适用于用户临时性占用信道的场景（如移动通信）。



### 一、CSMA/CD协议核心机制

CSMA/CD 的核心是 “先听后说、边说边听、冲突即停、随机重发”，由三部分组成：

1. **多址接入（MA）**：多个站点共享总线，竞争信道使用权；

2. **载波监听（CS）**：发送前检测总线是否空闲，空闲则等待 96 比特时间后发送；

3. 碰撞检测（CD）

   ：发送时持续检测总线，若发现碰撞：

   - 立即停止发送；
   - 发送 32/48 比特的 “强化碰撞信号”，确保所有站点检测到冲突；
   - 等待随机时间后重发。

### 二、关键概念

#### 1. 争用期（碰撞窗口）

- 定义：以太网端到端往返传播时延（\(2\tau\)），是检测碰撞的最长时间；
- 规则：若争用期内未检测到碰撞，可确定发送成功；
- 示例：10Mb/s 以太网的争用期为 512 比特时间（51.2μs），对应总线长度不超过 2500m（受信号衰减限制）。

#### 2. 帧长限制

- **最小帧长**：64 字节（512 比特），确保发送方在帧发送完成前能检测到碰撞；若数据不足，需填充字节至 64 字节；
- **最大帧长**：以太网 V2 帧为 1518 字节（数据载荷≤1500 字节），带 VLAN 标记的 802.1Q 帧为 1522 字节；过长帧会导致总线长期被占用，降低信道利用率。

#### 3. 截断二进制指数退避算法

用于确定碰撞后的重发等待时间，规则为：

- 退避时间 = 争用期 × 随机数r；
- 随机数r从集合\(\{0,1,...,2^k-1\}\)中选取，其中\(k=\text{Min}[重传次数, 10]\)；
- 重传次数≤10 时，k随重传次数增加；重传 16 次仍失败则丢弃帧并上报。

### 三、协议特点

- 适用于半双工共享总线网络（如传统以太网）；
- 信道利用率随主机数量、总线长度增加而降低；
- 是共享式以太网的基础，现代交换式以太网已无需 CSMA/CD（全双工通信）。



### 1. CSMA/CD 协议的核心流程

- 帧发送流程

  （第一张图）：

  - 先将数据 “封装成帧”，初始化重传次数`c=0`；
  - 通过 “载波监听” 检测信道：若空闲 96 比特时间，则发送帧；
  - 发送中 “碰撞检测”：若碰撞，发送干扰信号，重传次数`c+1`；若`c=15`则放弃；否则通过截断二进制指数算法计算退避时间后重传；若未碰撞且发送完成则结束。

- 帧接收流程

  （第二张图）：

  - 监听信道，若信道活跃则接收帧；
  - 接收后校验：帧长过短（小于最短帧长）、地址不匹配、CRC 校验错误，均丢弃该帧；否则接收成功。

### 2. CSMA/CD 的核心概念

- 争用期（碰撞窗口）

  发送帧的主机最多经过 “端到端往返传播时延（2τ）”，即可检测到碰撞；以太网规定争用期为 512 比特时间（10Mbps 以太网中为 51.2μs）。

- 最小帧长

  最小帧长 = 争用期 × 数据传输速率（如 10Mbps 以太网的最小帧长为 512bit=64 字节），确保发送方在帧发送完成前能检测到碰撞。

### 3. 真题解析（2009、2010 年题）

- 2009 年题

  最小帧长与最远站点距离的关系为：

  ```
  最小帧长 = (2d / 信号传播速度) × 传输速率
  ```

  。当最小帧长减少 800bit 时，代入

  ```
  传输速率=1Gbps
  ```

  ```
  信号传播速度=200000km/s
  ```

  ，计算得距离减少 80m（选 D）。

- 2010 年题

  - 最短碰撞检测时间：两主机同时发送，信号在中点碰撞后传回，耗时为**单程传播时延**：`2km / 200000km/s = 10μs`；
  - 最长碰撞检测时间：信号传播到对端时碰撞，需等待碰撞信号传回，耗时为**往返传播时延（争用期）**：`2×10μs=20μs`。

### 4. 协议的应用与现状

CSMA/CD 曾用于总线型 / 双绞线以太网，但**现代以太网基于交换机和全双工连接**，无碰撞风险，因此不再使用该协议。



### 一、MAC 地址的基础定义

MAC 地址是数据链路层的设备标识，核心特征：

- **存储位置**：固化在网卡的 EEPROM 中，又称 “硬件地址”；
- **标识对象**：是网络接口（而非设备）的唯一标识（一台设备多个网卡则对应多个 MAC 地址）；
- **层归属**：虽被称为 “物理地址”，但属于数据链路层，并非物理层。

### 二、MAC 地址的格式（EUI-48 标准）

由 6 字节（48 比特）组成，结构为：

| 字段                  | 长度      | 分配方                  |
| --------------------- | --------- | ----------------------- |
| 组织唯一标识符（OUI） | 前 3 字节 | IEEE 注册管理机构       |
| 网络接口标识符        | 后 3 字节 | 获得 OUI 的厂商自行分配 |

同时，**第一字节的低 2 位定义地址类型**：

| 第一字节 b1 位 | 第一字节 b0 位 | 地址类型         | 说明                                 |
| -------------- | -------------- | ---------------- | ------------------------------------ |
| 0              | 0              | 全球管理单播地址 | 厂商固化的默认地址，唯一标识单个接口 |
| 0              | 1              | 全球管理多播地址 | 用于特定功能的多播组                 |
| 1              | 0              | 本地管理单播地址 | 管理员手动分配，覆盖全球管理地址     |
| 1              | 1              | 本地管理多播地址 | 用户配置的自定义多播组               |



- 特殊情况：48 比特全为 1 时，为**广播地址（FF-FF-FF-FF-FF-FF）**，表示同一网络内所有接口。

### 三、MAC 地址的发送顺序

- 字节顺序：从 “第一字节” 到 “第六字节” 依次发送；
- 字节内比特顺序：从 “b0 位” 到 “b7 位” 依次发送。

### 四、MAC 地址的通信场景

1. 单播
   - 帧的目的 MAC 为某接口的单播地址，仅该接口接收（如主机 B 给主机 C 发送单播帧，仅 C 接收）。
2. 多播
   - 帧的目的 MAC 为多播地址，仅加入该多播组的接口接收（如主机 A 发送多播帧，仅 B、C 接收）。
3. 广播
   - 帧的目的 MAC 为广播地址（FF-FF-FF-FF-FF-FF），同一网络内所有接口均接收。

### 一、核心内容总结

内容围绕 “集线器与交换机的功能、冲突域 / 广播域、工作层级” 展开，通过拓扑图和对比表清晰区分两者的差异。

### 二、关键概念解析

1. **冲突域（碰撞域）**
   - 集线器：所有连接设备共享同一带宽，属于**同一个冲突域**（多设备同时通信会产生冲突，需依赖 CSMA/CD 协议）；若多个集线器级联，冲突域会进一步扩大。
   - 交换机：每个接口对应**独立的冲突域**，多对设备可同时通信，无冲突（无需 CSMA/CD）。
2. **广播域**
   - 集线器：所有连接设备属于**同一个广播域**，广播帧会被转发到所有端口。
   - 交换机：默认所有接口属于**同一个广播域**（可通过 VLAN 隔离），但单播帧仅转发到目标 MAC 对应的端口。

### 三、集线器与交换机的核心差异（表格对比）

| 维度     | 集线器（HUB）           | 交换机（SWITCH）              |
| -------- | ----------------------- | ----------------------------- |
| 工作层级 | OSI 物理层              | OSI 数据链路层（含物理层）    |
| 转发依据 | 无（仅放大、广播信号）  | 基于 MAC 地址（依赖帧交换表） |
| 冲突域   | 所有端口共享 1 个冲突域 | 每个端口是独立冲突域          |
| 通信方式 | 半双工（需 CSMA/CD）    | 全双工（无冲突）              |
| 带宽利用 | 共享带宽（总带宽固定）  | 独享带宽（各端口带宽独立）    |

### 四、实际应用

- 集线器因性能限制已被淘汰，仅用于早期简单网络；
- 交换机是当前局域网的核心设备，支持多设备并行通信，且可通过 VLAN、存储转发 / 直通交换等方式优化网络。

以下是 “以太网交换机自学习与转发” 的核心知识点整理：

### 一、交换机基础特性

1. **工作层级**：数据链路层（含物理层）。
2. **核心功能**：根据**MAC 地址（物理地址）** 转发帧，依赖内部的 “帧交换表”。
3. **即插即用性**：上电时帧交换表为空，通过 “自学习算法” 动态建立表项。

### 二、自学习流程

收到帧后，**登记帧的 “源 MAC 地址” 与 “进入交换机的接口号”**，并写入帧交换表。

### 三、帧转发规则

根据 “目的 MAC 地址” 和帧交换表，分 3 种情况：

1. **明确转发**：表中存在目的 MAC 对应的接口，仅转发到该接口（支持单播、多播、广播）。
2. **盲目转发（泛洪）**：表中无目的 MAC 记录，转发到除入接口外的所有接口。
3. **明确丢弃**：表中记录目的 MAC 对应的接口是入接口，直接丢弃（避免环路）。

### 四、帧交换表的时效性

表中每条记录有**有效时间**，到期自动删除，原因包括：

- 交换机接口更换连接的主机；
- 主机更换网卡（MAC 地址变更）。

### 五、典型考题要点

1. 交换机转发决策的依据是**目的物理地址（MAC 地址）**（对应 2009 年题）。
2. 数据帧转发时，若表中无目的 MAC 记录，会执行**泛洪转发**（对应 2014 年题）。

这是计算机网络中 ** 以太网交换机生成树协议（STP）** 的知识点内容，核心是解决冗余链路带来的网络环路问题，以下是结构化整理：

### 一、背景：冗余链路的矛盾

1. **目的**：添加冗余链路是为了提高以太网的可靠性（避免单链路故障导致网络中断）。

2. 问题

   ：冗余链路会形成

   网络环路

   ，引发三类问题：

   - **广播风暴**：大量广播帧在环路中循环，耗尽网络资源，导致正常数据无法转发；
   - **重复广播帧**：主机收到大量重复帧，消耗主机资源；
   - **帧交换表震荡**：交换机的 MAC 地址 - 接口映射不断变化，无法稳定转发数据。

### 二、生成树协议（STP）的作用

STP 的核心是在保留冗余链路的同时，**通过逻辑上阻塞部分端口，构建无环的树形拓扑**，实现 “可靠 + 无环” 的网络。

### 三、STP 的核心特性

1. **自动计算**：无论交换机物理连接如何，自动构建逻辑上无环的树形拓扑；
2. **连通性保障**：生成的树形拓扑需覆盖整个网络，确保所有设备互通；
3. **动态更新**：当网络拓扑（如链路故障、新增设备）变化时，自动重新计算生成树。

### 1. 背景：交换式以太网的问题

- 以太网交换机工作在数据链路层（含物理层），传统交换式以太网中所有站点属于**同一个广播域**。
- 随着网络规模扩大，广播域过大带来弊端：
  - 广播风暴（大量广播占用带宽）
  - 管理维护难度提升
  - 安全风险增加
- 网络中存在大量广播信息（如 ARP、RIP、DHCP 协议均依赖广播）。

### 2. VLAN 的作用与定义

- 传统分割广播域的方式是用路由器，但成本较高；**VLAN 技术是更经济的替代方案**。
- VLAN（虚拟局域网）：将局域网设备划分成**与物理位置无关的逻辑组**的技术，逻辑组内设备具有共同需求。

### 3. 图示说明

图中展示了 VLAN 的逻辑分组效果：不同物理位置（如不同楼层、不同网段）的设备，可被划分到同一 VLAN（如 VLAN1），同一 VLAN 内的设备能接收彼此的广播，而不同 VLAN（如 VLAN2）的设备则被隔离。

### 补充：VLAN 的核心价值

- 缩小广播域，减少广播风暴影响；
- 提升网络安全性（不同 VLAN 默认隔离）；
- 简化网络管理（按业务需求而非物理位置分组）。

### 一、IEEE 802.1Q 帧（VLAN 帧的基础）

1. 帧格式扩展

   ：

   - 在传统以太网 MAC 帧中插入**4 字节 VLAN 标记**，使帧长度从 1518 字节扩展到 1522 字节。

2. VLAN 标识符（VID）

   ：

   - VLAN 标记的后 12 比特为 VID，用于标识帧所属 VLAN；
   - VID 取值范围是 0~4095，但 0 和 4095 为保留值，**有效范围是 1~4094**。

3. 处理主体

   ：

   - 802.1Q 帧由交换机处理（而非用户主机）：交换机接收普通以太网帧时 “打标签”，转发时可能 “去标签”。

### 二、交换机端口类型及机制

交换机端口分为 3 类，核心是**Access 端口**和**Trunk 端口**：

#### 1. Access 端口（连接用户终端）

- **特性**：仅属于 1 个 VLAN，默认 PVID（端口 VLAN ID）为 1（华为称 PVID，思科称 Native VLAN）。

- 收发逻辑

  ：

  - 接收：仅收未打标签的帧，按端口 PVID 打标签；
  - 发送：仅转发 VID 与端口 PVID 一致的帧，并去标签。

- **示例效果**：同一 VLAN 的终端（如 VLAN2 的 A、B）广播帧仅在本 VLAN 内转发，与其他 VLAN（如 VLAN3）隔离。

#### 2. Trunk 端口（连接交换机 / 路由器）

- **特性**：可属于多个 VLAN，默认 PVID 为 1。

- 收发逻辑

  ：

  - 接收：未打标签的帧按 PVID 打标签；已打标签的帧直接保留标签；
  - 发送：VID 与 PVID 一致的帧 “去标签” 转发，否则直接带标签转发。

- **作用**：实现多 VLAN 数据在交换机间的透传（如 VLAN1、VLAN2 的帧可通过 Trunk 端口在交换机 1 和 2 之间传输）。

# 第四章网络层

### 一、两种服务的核心定义与特征

#### 1. 面向连接的虚电路服务

- **核心逻辑**：由网络保证通信可靠性，需先建立 “虚电路（VC）” 连接。
- 传输过程
  - 连接建立阶段使用目的主机地址，后续分组仅携带 “虚电路编号”（每段链路的编号独立）；
  - 所有分组沿已建立的虚电路传输，能保证无差错、按序、不丢失 / 重复到达；
  - 通信结束后需释放虚电路。
- **典型应用**：早期广域网（如 X.25、帧中继 FR、ATM）。

#### 2. 无连接的数据报服务

- **核心逻辑**：由用户主机（而非网络）保证可靠性，无需建立连接。
- 传输过程
  - 每个分组需携带目的主机的完整地址；
  - 分组可沿不同路径传输，可能出现误码、丢失、重复、失序；
  - 网络核心（路由器）仅做 “尽最大努力交付”，结构简单、成本低。
- **典型应用**：因特网（TCP/IP 协议栈的网际层采用此服务）。

### 二、两种服务的对比（表格总结）

| 对比方面     | 虚电路服务                     | 数据报服务             |
| ------------ | ------------------------------ | ---------------------- |
| 可靠通信责任 | 由网络保证                     | 由用户主机保证         |
| 连接建立     | 必须建立虚电路                 | 无需建立连接           |
| 终点地址使用 | 仅连接阶段用，分组带虚电路编号 | 每个分组带完整目的地址 |
| 分组转发路径 | 同一路由                       | 可走不同路由           |
| 节点故障影响 | 故障节点的虚电路全部失效       | 可能丢失分组、路由变化 |
| 分组到达顺序 | 按发送顺序到达                 | 不一定按顺序到达       |
| 服务质量保证 | 易实现（提前分配资源）         | 很难实现               |

### 三、补充说明

因特网（TCP/IP）选择数据报服务的核心原因：牺牲网络层的可靠性，换取核心设备的简单性、灵活性，将复杂的可靠传输逻辑（如差错重传、排序）交给 ** 运输层（如 TCP 协议）** 实现。

### 一、IPv4 地址的基础定义

- **本质**：给因特网中主机 / 路由器的每个接口分配的**32 比特全球唯一标识符**，是 TCP/IP 体系的核心概念。
- **分配机构**：由 ICANN（互联网名称与数字分配机构）统一分配，我国用户需向 APNIC（亚太网络信息中心）申请（需付费）。
- **地址枯竭**：2011 年 IPv4 地址已全部分配完毕，我国 2014-2015 年停止新分配，转而推进 IPv6 部署。

### 二、IPv4 地址的表示方法（点分十进制）

32 比特的二进制地址不便使用，因此采用**点分十进制表示法**，步骤为：

1. 将 32 比特的二进制地址按每 8 位（1 字节）分组；
2. 每组转换为十进制数；
3. 用 “.” 连接各组十进制数。

**示例**：

- 32 比特二进制：`00001010 11110000 00001111 10101010`
- 每组十进制：`10`、`240`、`15`、`170`
- 点分十进制形式：`10.240.15.170`

### 三、IPv4 地址的编址阶段

IPv4 的编址方法经历了三个历史阶段：

1. **分类编址（1981）**：将地址分为 A、B、C、D、E 类，按固定位数划分网络号与主机号；
2. **划分子网（1985）**：在分类编址基础上，将主机号部分划分为子网号与主机号，提升地址利用率；
3. **无分类编址（1993）**：采用 CIDR（无类别域间路由），用 “前缀长度” 灵活划分网络与主机部分，是当前主流编址方式。

### 一、IPv4 分类编址的类型与结构

IPv4 地址按首位二进制位分为 5 类，仅 A/B/C 类用于分配主机 / 路由器接口，结构及参数如下：

| 地址类别 | 首位标识 | 网络号长度 | 主机号长度 | 可指派网络数                | 每个网络最大主机数    |
| -------- | -------- | ---------- | ---------- | --------------------------- | --------------------- |
| A 类     | `0`      | 8 位       | 24 位      | \(2^7-2=126\)               | \(2^{24}-2=16777214\) |
| B 类     | `10`     | 16 位      | 16 位      | \(2^{14}=16384\)            | \(2^{16}-2=65534\)    |
| C 类     | `110`    | 24 位      | 8 位       | \(2^{21}=2097152\)          | \(2^8-2=254\)         |
| D 类     | `1110`   | -          | -          | 多播地址（无网络 / 主机号） | -                     |
| E 类     | `1111`   | -          | -          | 保留地址（未使用）          | -                     |

### 二、地址分配的限制规则

以下地址**不能分配给主机 / 路由器接口**：

1. 网络号为 “0” 或 “127”（A 类，0 为保留、127 为环回测试）；
2. 主机号为 “全 0”（网络地址，标识整个网络）；
3. 主机号为 “全 1”（广播地址，用于本网段广播）。

### 三、特殊 IPv4 地址的用途

| 地址形式          | 作用                       | 源地址 / 目的地址可用性 |
| ----------------- | -------------------------- | ----------------------- |
| `0.0.0.0`         | 本网络上的本主机（DHCP）   | 仅作源地址              |
| `127.x.x.x`       | 本地环回测试               | 可作源 / 目的地址       |
| `255.255.255.255` | 本网段广播（路由器不转发） | 仅作目的地址            |

### 四、地址分配的实践原则

根据网络的主机数量选择地址类别：

- 主机数多（如 65534 台）→ 选 A 类地址；
- 主机数中等（如 254 台）→ 选 B 类地址；
- 主机数少（如 16/24 台）→ 选 C 类地址；
- 不同网络需分配不同的网络号。

### 一、划分子网的核心逻辑

划分子网是从**分类地址的主机号部分借位作为子网号**，以此在一个网络号下拆分出多个子网，解决地址浪费问题。其核心工具是**子网掩码**：



- 子网掩码为 32 比特，用**连续的 “1” 对应网络号 + 子网号**，**连续的 “0” 对应主机号**；
- 将 IP 地址与子网掩码做**逻辑与运算**，可得到子网的网络地址。

### 二、默认子网掩码（未划分子网时）

不同分类地址的默认子网掩码（无子网号，“1” 仅对应网络号）：



| 地址类别 | 默认子网掩码（二进制）                | 点分十进制形式  |
| -------- | ------------------------------------- | --------------- |
| A 类     | `11111111 00000000 00000000 00000000` | `255.0.0.0`     |
| B 类     | `11111111 11111111 00000000 00000000` | `255.255.0.0`   |
| C 类     | `11111111 11111111 11111111 00000000` | `255.255.255.0` |

### 三、划分子网的实例（以 C 类地址为例）

已知网络地址`218.75.230.0`，子网掩码`255.255.255.128`（借 1 位主机号作子网号）：



1. **子网数量**：\(2^1=2\)个子网；

2. 子网 1（子网号 0）

   ：

   - 网络地址：`218.75.230.0`；
   - 可分配地址：`218.75.230.1 ~ 218.75.230.126`；
   - 广播地址：`218.75.230.127`；

3. 子网 2（子网号 1）

   ：

   - 网络地址：`218.75.230.128`；
   - 可分配地址：`218.75.230.129 ~ 218.75.230.254`；
   - 广播地址：`218.75.230.255`。

### 四、划分子网的价值与信息获取

- **避免的弊端**：无需申请新网络号，减少路由表条目，降低地址浪费；
- **已知 IP + 子网掩码可获取的信息**：子网数量、每个子网的地址范围、网络地址 / 广播地址。

### 一、CIDR 的背景与核心价值

划分子网仍无法解决 C 类地址浪费、IPv4 地址枯竭的问题，因此 IETF 在 1993 年推出**无分类域间路由（CIDR）**：



- 消除传统 A/B/C 类地址及划分子网的概念；
- 更高效分配 IPv4 地址空间，支撑因特网在 IPv6 普及前的规模增长。

### 二、CIDR 的表示方法（斜线记法）

用 “`IP地址/前缀长度`” 表示，其中**前缀长度**是网络前缀的比特数（替代子网掩码）：



- 示例：

  ```
  128.14.35.7/20
  ```

  - 网络前缀：20 比特；
  - 主机号：\(32-20=12\)比特；

- CIDR 将**网络前缀相同的连续 IP 地址**组成 “CIDR 地址块”，通过任意一个地址可确定地址块的全部信息（最小 / 最大地址、地址数量等）。

### 三、CIDR 的关键技术：路由聚合（构造超网）

通过**提取多个地址块的共同前缀**，将多条路由记录合并为一条，减少路由表条目：

- 示例：将

  ```
  172.1.4.0/25
  ```

  、

  ```
  172.1.4.128/25
  ```

  、

  ```
  172.1.5.0/24
  ```

  等地址块聚合

  - 提取共同前缀（22 比特）：`172.1.000001`；
  - 聚合后地址块：`172.1.4.0/22`。

### 四、CIDR 的路由匹配规则：最长前缀匹配

- 网络前缀越长，地址块越小，路由越具体；
- 路由器转发分组时，优先选择**网络前缀最长**的路由（保证转发到最精确的目标网络）。

### 一、FLSM 与 VLSM 的核心区别

| 方案类型             | 核心特点                                     | 地址利用效率         |
| -------------------- | -------------------------------------------- | -------------------- |
| 定长子网掩码（FLSM） | 使用同一子网掩码划分子网，每个子网地址数相同 | 低（易造成地址浪费） |
| 变长子网掩码（VLSM） | 使用不同子网掩码划分子网，按需分配地址数     | 高（减少地址浪费）   |

### 二、VLSM 的应用实例（以地址块`218.75.230.0/24`为例）

1. **需求分析**：5 个网络的地址需求不同（如 N2 需 28 个地址、N1 需 9 个地址）；

2. 地址块选择

   ：

   - 按需求大小分配对应前缀的地址块（大需求用短前缀，小需求用长前缀）：
     - N2（28 个地址）→ `/27`（32 个地址）；
     - N1/N3/N4（9/15/13 个地址）→ `/28`（16 个地址）；
     - N5（4 个地址）→ `/30`（4 个地址）；

3. **分配规则**：地址块起点需为 “块大小的整数倍”（如`/27`块起点为`0`、`32`等）。

### 三、VLSM 的优势

通过灵活选择子网掩码，实现 “按需分配地址”，大幅降低 IPv4 地址的浪费，是实际网络规划中常用的方案。

### 一、核心原理：IP 数据报发送 / 转发规则

1. **主机判断交付方式**
   - 用**自身 IP 与子网掩码 “与运算” 得到自身网络地址**，再用**目的主机 IP 与自身子网掩码 “与运算” 得到目的网络地址**。
   - 若两个网络地址**相同**：直接交付（同一网络内通过交换机转发）。
   - 若两个网络地址**不同**：间接交付（发给默认网关，由路由器转发）。
2. **路由器转发规则**
   - 先检查 IP 数据报首部是否出错，出错则丢弃并通告源主机。
   - 再根据目的地址查路由表，找到匹配条目则转发到下一跳；找不到则丢弃并通告源主机。
3. **广播地址与广播风暴**
   - 本网络广播地址：主机位全 1（如 192.168.0.127，对应子网掩码 255.255.255.128）；受限广播地址：255.255.255.255。
   - 路由器**不转发广播包**，可隔离广播域（抑制广播风暴）；中继器、集线器、网桥无法隔离广播域。

### 二、案例（拓扑：主机 A/B/C/S1、路由器 R、主机 D/E/F/S2）

以 ** 主机 A（192.168.0.1/255.255.255.128）发送数据到主机 D（192.168.0.129/255.255.255.128）** 为例：

1. 主机 A 计算自身网络地址：`192.168.0.1 & 255.255.255.128 = 192.168.0.0`。
2. 主机 A 计算目的网络地址：`192.168.0.129 & 255.255.255.128 = 192.168.0.128`。
3. 两个网络地址不同，属于间接交付：主机 A 将数据发给默认网关（交换机 S1→路由器 R）。
4. 路由器 R 查路由表：目的网络 192.168.0.128 对应接口 1，转发到 S2，最终送达主机 D。

### 1. 静态路由的基础配置

- 普通静态路由

  ：

  

  路由器通过手动配置 “目的网络 + 下一跳” 的条目，实现不同网段的通信（如 R1 配置到 192.168.2.0/24 的静态路由，下一跳指向 R2 的 10.0.0.2）。

- 默认路由

  ：

  

  以

  ```
  0.0.0.0/0
  ```

  表示 “所有未匹配的网络”，作为 “兜底” 路由（如 R1 配置默认路由，下一跳指向 R2，可替代多个具体网段的静态路由）。

- 特定主机路由

  ：

  

  以

  ```
  /32
  ```

  掩码匹配单个主机（如 R1 配置到 192.168.2.1/32 的路由，精准指向特定设备）。

### 2. 路由环路的产生场景

路由环路是指数据包在路由器之间循环转发、无法到达目标的问题，常见触发原因包括：



- 配置错误

  ：

  

  路由器的下一跳指向错误（如 R2 将 192.168.1.0/24 的下一跳配置为 R3 的 10.0.1.2，而 R3 又将该网段的下一跳指向 R2，形成 R2-R3 的循环）。

- 路由聚合不当

  ：

  

  聚合了不存在的网络（如 R2 聚合 192.168.0.0/22，包含实际不存在的 192.168.0.0/24 和 192.168.3.0/24，导致这些网段的数据包在 R1-R2 间循环）。

- 网络故障

  ：

  

  原直连链路故障后，路由器未及时更新路由表（如 R1 到 192.168.2.0/24 的直连链路故障，却仍将数据包转发给 R2，而 R2 又转发回 R1）。

### 3. 路由环路的解决 / 缓解手段

- TTL 字段

  ：

  

  IP 数据包的 “生存时间（TTL）” 每经过一个路由器减 1，当 TTL 为 0 时数据包被丢弃，避免无限循环。

- 黑洞路由

  ：

  

  对不存在的网络配置下一跳为

  ```
  null0
  ```

  （空接口），直接丢弃目标为这些网络的数据包（如 R2 对 192.168.0.0/24 和 192.168.3.0/24 配置黑洞路由）。

### 一、静态路由与动态路由的对比

| 类型     | 特点                                                         | 适用场景   |
| -------- | ------------------------------------------------------------ | ---------- |
| 静态路由 | 人工配置（含普通静态路由、默认路由、特定主机路由等），简单开销小，但无法自适应网络变化 | 小规模网络 |
| 动态路由 | 路由器通过协议自动获取路由信息，复杂度高、开销大，但能自适应网络状态变化 | 大规模网络 |

### 二、因特网路由选择协议的核心特点

因特网的路由协议具备 3 个关键特性：



1. **自适应**：动态调整路由，适配网络拓扑 / 流量变化；
2. **分布式**：路由器之间相互交换路由信息，共同维护网络可达性；
3. **分层次**：将网络划分为多个**自治系统（AS）**，自治系统内部用**内部网关协议（IGP）**，自治系统之间用**外部网关协议（EGP）**。

### 三、常见路由选择协议分类

路由协议分为 “内部网关协议（IGP）” 和 “外部网关协议（EGP）” 两类：



- IGP（自治系统内使用）

  ：

  - 基于 “距离向量”：RIP（早期协议）、IGRP（已被 EIGRP 替代）、EIGRP（思科私有，混合距离向量 + 链路状态）；
  - 基于 “链路状态”：OSPF（广泛使用）、IS-IS（ISP 骨干网常用）；

- **EGP（自治系统间使用）**：BGP（因特网中自治系统之间的核心协议）。

### 四、路由器的基本结构与工作逻辑

路由器由 “路由选择部分” 和 “分组转发部分” 组成：

1. 路由选择部分
   - 由 “路由选择处理机” 运行路由协议，维护**路由表**（记录 “目的网络→下一跳” 的映射）；
2. 分组转发部分
   - 输入端口接收数据包，经 “网络层” 解析后，通过 “交换结构” 传递到 “分组处理模块”；
   - 分组处理模块依据**转发表**（由路由表优化而来，用于快速查找），将数据包转发到输出端口，最终通过物理层发送。

（注：路由表用于 “计算最优路由”，转发表用于 “快速转发数据包”，二者逻辑关联但功能不同）

### 五、路由器的分组转发流程

数据包在路由器中的转发步骤：

1. 输入端口：物理层→链路层→网络层，解析数据包的目的地址；
2. 分组处理：查询转发表，确定输出端口；
3. 输出端口：网络层→链路层→物理层，发送数据包。

（输入 / 输出端口均设有缓冲区，用于缓解流量拥塞）

### 一、RIP 的基本定义与核心规则

RIP 是早期的内部网关协议（IGP），基于 “距离向量” 算法，核心规则包括：



1. **度量单位**：用 “跳数” 衡量路由距离（直连网络跳数 = 1，每经过 1 个路由器跳数 + 1）；
2. **最大跳数**：路径最多包含 15 个路由器，跳数 = 16 表示 “网络不可达”，因此仅适用于小型网络。

### 二、RIP 的路由选择逻辑

- **最优路由标准**：选择 “跳数最少” 的路径；
- **负载均衡**：若到同一网络的多条路由跳数相等，可进行 “等价负载均衡”（如 R1 到 R6 的两条路径跳数均为 2，可同时使用）。

### 三、RIP 的工作过程

1. **初始化**：路由器仅知道自身直连网络的跳数（=1）；
2. **信息交换**：仅与**相邻路由器**周期性（如每 30 秒）交换完整路由表；
3. **收敛**：多次交换后，每个路由器掌握自治系统内所有网络的 “最短跳数 + 下一跳”，称为 “收敛”。

### 四、RIP 的路由条目更新规则

当收到相邻路由器的路由信息时，按以下逻辑更新：



| 场景                       | 处理方式       |
| -------------------------- | -------------- |
| 相同下一跳，收到新信息     | 直接更新       |
| 发现新网络                 | 添加路由条目   |
| 不同下一跳，新路由跳数更少 | 更新为更优路由 |
| 不同下一跳，跳数相等       | 等价负载均衡   |
| 不同下一跳，新路由跳数更多 | 不更新         |

### 五、RIP 的典型问题：“坏消息传播得慢”

当网络故障（如 N1 不可达）时，RIP 会出现 “路由环路”：



1. R1 检测到 N1 故障，将其跳数设为 16（不可达）；
2. R2 仍向 R1 发送 “N1 跳数 = 2” 的旧信息，导致 R1 误将 N1 的下一跳改为 R2，跳数 = 3；
3. R1 再向 R2 发送 “N1 跳数 = 3” 的信息，R2 更新为跳数 = 4，循环往复，直到跳数增至 16 才会终止（耗时数分钟）。

### 六、RIP 问题的缓解手段

为减少路由环路，RIP 采用以下措施：



1. **限制最大跳数**：跳数 = 16 表示不可达，避免无限循环；
2. **触发更新**：路由表变化时立即发送更新，而非等待周期；
3. **水平分割**：路由器不向 “学习到路由的接口” 反向发送该路由信息。

  ：假设 R1、R2、R3 采用 RIP 协议交换路由信息，且均已收敛。若 R3 检测到网络 201.1.2.0/25 不可达，并向 R2 通告一次新的距离矢量，则 R2 更新后，其到达该网络的距离是（）

  

  A. 2

  

  B. 3

  

  C. 16

  

  D. 17

- **答案**：B

- 解析

  ：

  1. 收敛后，R1 到 201.1.2.0/25 的跳数为 2（下一跳 R3），R2 到该网络的跳数为 2（下一跳 R3）；
  2. R3 检测到网络不可达，将其跳数设为 16 并通告 R2；
  3. R2 收到 R3 的信息后，会尝试通过 R1 转发该网络的数据包，因此跳数更新为 “R1 到该网络的跳数（2）+1”=3。

### 一、OSPF 的基本定义与核心特点

OSPF 是为解决 RIP 的缺陷（如路由环路、规模限制）而设计的内部网关协议，核心特点包括：



1. **开放与算法**：“开放” 指协议公开发布，“最短路径优先” 基于 Dijkstra 的 SPF 算法；
2. **链路状态协议**：以 “链路状态（邻居关系 + 链路代价）” 为基础，而非 RIP 的 “距离向量”；
3. **优势**：无路由环路、支持大规模网络、更新效率高、收敛速度快；
4. **链路代价**：由网络管理员定义（可代表带宽、时延等），例如思科设备中代价 = 100Mbps / 链路带宽（结果 < 1 记为 1，小数舍去）。

### 二、OSPF 的邻居关系建立

OSPF 通过**Hello 分组**建立与维护邻居关系：



- Hello 分组封装在 IP 数据报中，目标地址为组播地址 224.0.0.5；
- 发送周期为 10 秒，若 40 秒未收到邻居的 Hello 分组，则判定邻居不可达；
- 路由器维护 “邻居表”，记录邻居 ID、接口及 “死亡倒计时”。

### 三、OSPF 的链路状态同步过程

1. **生成 LSA**：每个路由器生成**链路状态通告（LSA）**，包含直连网络、邻居的链路状态信息；
2. **洪泛 LSU**：LSA 封装在 ** 链路状态更新分组（LSU）** 中，通过 “洪泛法”（向所有邻居转发，除接收接口）发送；
3. **同步 LSDB**：每个路由器维护**链路状态数据库（LSDB）**，存储所有 LSA；通过洪泛 LSU，最终所有路由器的 LSDB 保持一致。

### 四、OSPF 的路由计算

路由器基于一致的 LSDB，通过 **SPF 算法（Dijkstra 算法）** 计算到其他路由器的最短路径，构建自身路由表：



- LSDB 可转化为 “带权有向图”，以自身为根节点，计算到各节点的最短路径。

### 五、OSPF 的分组类型

OSPF 包含 5 种核心分组：



| 分组类型                | 功能                           |
| ----------------------- | ------------------------------ |
| 问候（Hello）分组       | 发现、维护邻居关系             |
| 数据库描述分组          | 向邻居发送自身 LSDB 的摘要信息 |
| 链路状态请求分组        | 向邻居请求特定 LSA 的详细信息  |
| 链路状态更新分组（LSU） | 洪泛发送 LSA，同步全网链路状态 |
| 链路状态确认分组        | 确认收到 LSU，保证可靠性       |

### 六、OSPF 的多点接入网络优化

在多点接入网络（如以太网）中，OSPF 通过 ** 选举指定路由器（DR）和备用指定路由器（BDR）** 减少邻居关系数量：



- 非 DR/BDR 仅与 DR/BDR 建立邻居关系；
- 非 DR/BDR 之间通过 DR/BDR 交换信息，大幅降低邻居关系数量（从\(n(n-1)/2\)减少为\(2(n-2)+1\)）。

### 七、OSPF 的区域划分

为支持超大规模网络，OSPF 将自治系统（AS）划分为多个**区域（Area）**：



- **区域内路由器（IR）**：仅属于一个区域的路由器；
- **区域边界路由器（ABR）**：连接多个区域的路由器；
- **主干路由器（BBR）**：属于主干区域（Area 0.0.0.0）的路由器；
- **自治系统边界路由器（ASBR）**：连接其他自治系统的路由器；
- 规则：所有区域必须连接到主干区域，区域间路由通过 ABR 转发。



OSPF 是目前主流的内部网关协议，其链路状态机制和区域划分使其适用于中大型网络。

### 一、BGP 的核心定位与设计逻辑

BGP 是**自治系统（AS）之间的外部网关协议（EGP）**，其设计逻辑源于自治系统间路由的特殊性：



1. **度量不统一**：不同自治系统的路由 “代价”（距离、带宽等）定义不同，无法用单一度量选最优路由；
2. **策略优先**：自治系统间路由需考虑政治、经济、安全等策略（如避免经过特定 AS）；
3. **目标**：不求 “最优路由”，只求 “可达且较优、无环路” 的路由。

### 二、BGP 的工作机制

1. **BGP 发言人**：每个自治系统需选择至少一个路由器作为 “BGP 发言人”，负责与其他 AS 的 BGP 发言人交互；

2. **会话建立**：不同 AS 的 BGP 发言人通过 **TCP 连接（端口 179）** 建立会话，保证传输可靠性；

3. 路由信息交换

   ：

   - 交换 “网络可达性信息”（即到达目标网络需经过的 AS 序列，称为 “路径向量”）；
   - 各 BGP 发言人基于策略，从收到的路由中选择较优路径，构建无环路的 AS 连通图。

### 三、BGP 的报文类型

BGP-4 包含 4 种核心报文：



| 报文类型             | 功能                                                      |
| -------------------- | --------------------------------------------------------- |
| OPEN（打开）         | 与相邻 BGP 发言人建立连接，初始化通信                     |
| UPDATE（更新）       | 通告新路由、撤销过时路由                                  |
| KEEPALIVE（保活）    | 周期性（通常 30 秒）验证邻居连通性，维持 TCP 会话         |
| NOTIFICATION（通知） | 发送错误信息（如报文格式错误），出现错误时会关闭 BGP 会话 |

### 四、BGP 的协议封装

不同路由协议的封装方式不同：



- RIP：封装在 **UDP（端口 520）** 中，再封装到 IP；
- OSPF：直接封装在 **IP（协议号 89）** 中；
- BGP：封装在 **TCP（端口 179）** 中，再封装到 IP（利用 TCP 保证可靠性）。

### 一、IPv4 首部的整体结构

IPv4 数据报首部分为 “固定部分（20 字节）” 和 “可变部分（0~40 字节）”：



- 固定部分：包含必选字段，是所有 IPv4 数据报都具备的；
- 可变部分：包含可选字段 + 填充字段，用于扩展功能（实际很少使用）。

### 二、固定部分核心字段解析

#### 1. 版本

- 占 4 比特，标识 IP 协议版本（IPv4 对应值为 4），通信双方版本必须一致。

#### 2. 首部长度

- 占 4 比特，以 “4 字节” 为单位表示首部总长度：
  - 最小值为 5（对应 20 字节固定部分）；
  - 最大值为 15（对应 20 字节固定部分 + 40 字节可变部分）。

#### 3. 区分服务

- 占 8 比特，旧称 “服务类型”，用于提供差异化服务质量（QoS），一般场景下不使用。

#### 4. 总长度

- 占 16 比特，以 “字节” 为单位表示数据报总长度（首部 + 数据载荷），最大值为 65535 字节。
- 示例：若首部长度 = 20 字节、总长度 = 1020 字节，则数据载荷长度 = 1020-20=1000 字节。

#### 5. 标识、标志、片偏移（分片相关）

这三个字段共同实现**IP 数据报分片**（当数据报长度超过链路的 MTU 时，需拆分后传输）：



- **标识**：占 16 比特，同一数据报的所有分片标识相同，用于重组时识别归属；

- 标志

  ：占 3 比特，包含：

  - DF 位（1 = 不允许分片，0 = 允许分片）；
  - MF 位（1 = 后面还有分片，0 = 最后一个分片）；

- **片偏移**：占 13 比特，以 “8 字节” 为单位表示分片数据在原数据报中的偏移位置，用于重组时排序。

- 示例：3800 字节数据载荷（+20 字节首部）需分片（MTU=1420 字节），会拆分为 3 个分片，片偏移分别为 0、1400/8、2800/8。

#### 6. 生存时间（TTL）

- 占 8 比特，每经过一个路由器减 1，当 TTL=0 时数据报被丢弃，用于防止路由环路导致数据报无限循环。

#### 7. 协议

- 占 8 比特，标识数据载荷对应的上层协议，常见值：

  | 协议 | ICMP | IGMP | TCP  | UDP  | IPv6 | OSPF |
  | ---- | ---- | ---- | ---- | ---- | ---- | ---- |
  | 值   | 1    | 2    | 6    | 17   | 41   | 89   |

### 三、可变部分字段

- **可选字段**：长度 1~40 字节，支持排错、安全等扩展功能，实际很少使用；
- **填充字段**：用全 0 填充，确保首部长度为 4 字节的整数倍。

·

IPv4数据报首部由**固定部分（20字节）**和**可变部分（最多40字节）**组成，总长度最大为60字节。



#### **1. 固定部分 (20字节)**

这部分包含所有必需的字段，其结构如下：



- **版本 (Version, 4位)**: 指明IP协议版本。对于IPv4，此值为`4`。
- **首部长度 (IHL, 4位)**: 以“4字节”为单位，表示整个首部的长度。最小值为`5`（即20字节），最大值为`15`（即60字节）。
- **区分服务 (Differentiated Services, 8位)**: 用于指定数据包的服务质量（QoS）。现在通常被称为“DSCP”和“ECN”字段。
- **总长度 (Total Length, 16位)**: 以“字节”为单位，表示整个IP数据报（首部+数据载荷）的总长度。最大值为`65535`字节。
- **标识 (Identification, 16位)**: 用于唯一标识一个数据报的所有分片。同一个原始数据报的所有分片具有相同的标识值。
- **标志 (Flags, 3位)**:
  - **DF (Don't Fragment)**: `1`表示不允许分片；`0`表示允许分片。
  - **MF (More Fragments)**: `1`表示后面还有分片；`0`表示这是最后一个分片。
  - **保留位**: 必须为`0`。
- **片偏移 (Fragment Offset, 13位)**: 以“8字节”为单位，指示该分片的数据在原始数据报中的起始位置。
- **生存时间 (TTL, 8位)**: 也称为“跳数”。路由器每转发一次数据报，TTL值减`1`。当TTL值减为`0`时，数据报被丢弃。其作用是**防止数据报在网络中永久循环**。
- **协议 (Protocol, 8位)**: 指明数据报的数据部分封装的是哪种上层协议的数据单元。
  - 常见值：ICMP (`1`)、IGMP (`2`)、TCP (`6`)、UDP (`17`)、IPv6 (`41`)、OSPF (`89`)。
- **首部检验和 (Header Checksum, 16位)**: 用于检测IP首部在传输过程中是否出错。由于TTL、标志、片偏移等字段在经过路由器时会变化，因此每经过一个路由器都需要重新计算此校验和。在IPv6中，为了提高效率，已取消了首部校验和。
- **源IP地址 (Source IP Address, 32位)**: 发送方主机的IP地址。
- **目的IP地址 (Destination IP Address, 32位)**: 接收方主机的IP地址。



#### **2. 可变部分 (最多40字节)**

这部分是可选的，用于支持排错、测量及安全等措施。实际应用中很少使用。

### **关键概念与示例**

#### **【举例】对IPv4数据报进行分片**

- **场景**: 一个总长度为`3800 + 20 = 3820`字节的数据报需要被分片。
- **过程**:
  1. 首先分成三个主要分片：`首部1` (0-1399), `首部2` (1400-2799), `首部3` (2800-3799)。
  2. 其中，`首部2`又被进一步细分为两个子分片：`首部2-1` (1400-2199) 和 `首部2-2` (2200-2799)。
- **分片字段值**:
  - **原始数据报**: `MF=0`, `DF=0`, `片偏移=0`。
  - **分片2的分片1**: `MF=1` (后面还有分片), `DF=0`, `片偏移=1400/8=175`。
  - **分片2的分片2**: `MF=1` (后面还有分片), `DF=0`, `片偏移=2200/8=275`。
  - **分片3**: `MF=0` (这是最后一个分片), `DF=0`, `片偏移=2800/8=350`。



#### **【举例】生存时间TTL的作用 —— 防止路由环路**

- **问题**: 当网络中存在路由环路（如R1和R2互相将对方设为下一跳）时，数据报可能无限循环。
- **解决方案**: TTL机制。
  - 数据报从N1发出，经过R1、R2、R1...。
  - 每经过一个路由器，TTL值减`1`。
  - 当TTL值最终减到`0`时，当前路由器会丢弃该数据报，并向源主机发送一个ICMP超时消息。
  - 这样就有效避免了数据报在网络中永久兜圈。



#### **【举例】协议字段的应用**

- 当**协议字段值为1时，表明IP数据报的数据部分封装的是一个ICMP报文**。

### ✅ **第一张图：IP分片问题（2018年题47）**

#### 背景信息：

- 网络拓扑：销售部（MTU=1500B）→ 路由器F0/F1 → 技术部（MTU=800B）
- 主机 `192.168.1.1` 发送一个总长度为 **1500B** 的IP分组，首部20B，载荷1480B
- 经过路由器时，需通过 F1 接口转发，该接口 MTU = 800B

#### 关键知识点：

1. **最大传输单元（MTU）限制**
   - 当IP数据报大于链路MTU时，必须**分片**
   - 分片后每个分片的总长度 ≤ MTU
2. **分片原则：尽可能大但不超过MTU**
   - 每个分片包含20B首部 + 数据部分
   - 所以每个分片最大数据载荷 = 800 - 20 = **780B**
3. **片偏移（Fragment Offset）**
   - 单位是 **8字节**（即64位），所以必须是整数
   - 第一个分片偏移 = 0
   - 第二个分片偏移 = 780 / 8 = **97.5** ❌ 不合法！

> ⚠️ 错误方案：尝试把第一个分片设为780B数据 → 偏移=97.5 → 非整数 → **不允许！**

✅ 正确做法：

- 第一个分片：776B数据（因为776 ÷ 8 = 97，整数）
- 第二个分片：剩余704B数据
- 片偏移分别为：
  - 分片1: 0
  - 分片2: 776 / 8 = **97**

#### 结论：

- 最大IP分片封装数据：**776字节**
- 至少需要分 **2个分片**
- 片偏移量分别是：**0 和 97**

### ✅ **第五张图：IPv4首部字段详解**

这是对IPv4首部各字段的全面解释，非常系统：

| 字段                      | 说明                                                         |
| ------------------------- | ------------------------------------------------------------ |
| **版本**                  | 4比特，表示IPv4                                              |
| **首部长度**              | 4比特，单位为4字节，最小5（20字节），最大15（60字节）        |
| **区分服务（DS）**        | 原DSCP，用于QoS                                              |
| **总长度**                | 16比特，最大65535字节（含首部+数据）                         |
| **标识**                  | 16比特，用于同一数据报的所有分片共享                         |
| **标志**                  | 3比特： - DF: 不分片 - MF: 更多分片（0表示最后） - 保留位：0 |
| **片偏移**                | 13比特，单位为8字节，指示当前分片在原数据报中的位置          |
| **生存时间（TTL）**       | 8比特，每经过一跳减1，防止无限循环                           |
| **协议**                  | 8比特，表示上层协议（如TCP=6, UDP=17）                       |
| **首部校验和**            | 16比特，仅检查首部，每次修改都要重算                         |
| **源IP地址 / 目的IP地址** | 各32比特                                                     |

## 🧠 核心知识点总结

### 1. **IP分片规则**

- 分片发生在**MTU较小的链路上**
- 每个分片都有独立的IP首部
- **片偏移必须是8字节的整数倍**
- 最后一个分片的MF位为0
- 分片后，重组由**最终接收端完成**

### 2. **IP首部关键字段作用**

| 字段   | 功能                           |
| ------ | ------------------------------ |
| TTL    | 控制数据报寿命，防环路         |
| 校验和 | 检查首部是否损坏               |
| 片偏移 | 指示分片在原始报文中的位置     |
| 标志   | 控制是否分片及是否还有后续分片 |

### 3. **路由器转发行为**

- TTL减1
- 重算首部校验和
- 若超过MTU则分片（修改总长度、标志、片偏移）
- 不修改源/目的IP地址

### 4. **实际应用技巧**

- 从十六进制抓包数据中识别IP首部字段
- 判断是否需要分片：比较IP总长度 vs MTU
- 计算片偏移时注意单位是**8字节**

### 📌 第1张图：ICMP 概述

> **标题**：4.8 网际控制报文协议 ICMP
>  **核心内容**：
>
> - ICMP 是为更有效地转发 IP 数据报、提升交付成功率而设计的。
> - 主机或路由器使用 ICMP 发送两类报文：
>   1. **差错报告报文**
>   2. **询问报文**

🔹 **关键点**：

- ICMP **不是传输层协议**，而是**网络层协议**，封装在 IP 数据报中传输。
- 它不提供可靠传输，但能反馈网络异常。

------

### 📌 第2张图：ICMP 差错报告报文 —— 终点不可达

> **类型**：终点不可达（Destination Unreachable）

#### 🧩 场景说明：

- 当路由器 R1 收到一个 IP 数据报，发现无法转发（如没有路由表项），就会丢弃该数据报，并向源主机 H1 发送 ICMP “终点不可达” 报文。

#### 💡 常见原因包括：

1. 目的网络不可达
2. 目的主机不可达
3. 目的协议不可达（例如 UDP 端口不存在）
4. 目的端口不可达
5. 目的网络未知 / 主机未知等（共13类细分）

> ✅ 用途：告知源主机“这条路走不通”。

------

### 📌 第3张图：ICMP 差错报告报文 —— 源点抑制

> **类型**：源点抑制（Source Quench）

#### 🧩 场景说明：

- 路由器 R2 或主机 H2 因拥塞导致缓冲区满，无法处理更多数据包 → 丢弃数据报。
- 向源主机 H1 发送 ICMP “源点抑制” 报文，提示其**降低发送速率**。

> ⚠️ 注意：现代网络中已很少使用，被显式拥塞通知（ECN）取代。

> ✅ 用途：实现简单的流量控制机制。

------

### 📌 第4张图：ICMP 差错报告报文 —— 时间超过

> **类型**：时间超过（Time Exceeded）

#### 🧩 场景说明：

- 路由器 R2 收到一个 IP 数据报，TTL 字段值减 1 后变为 0。
- 此时路由器丢弃该数据报，并向源主机 H1 发送 ICMP “时间超过” 报文。

> 🔁 这正是 `traceroute` 命令的工作原理！

> ✅ 用途：
>
> - 防止数据报无限循环
> - 可用来探测路径中的跳数（每跳 TTL 减 1）

------

### 📌 第5张图：ICMP 差错报告报文 —— 参数问题

> **类型**：参数问题（Parameter Problem）

#### 🧩 场景说明：

- 路由器 R1 接收到 IP 数据报后，检查首部校验和发现错误（或字段非法）。
- 丢弃该数据报，并向源主机 H1 发送 ICMP “参数问题” 报文。

> ❗ 说明：IP 首部出错，可能是篡改或传输损坏。

> ✅ 用途：检测并报告 IP 首部格式或内容错误。

------

### 📌 第6张图：ICMP 差错报告报文 —— 改变路由（重定向）

> **类型**：改变路由（Redirect）

#### 🧩 场景说明：

- 路由器 R1 发现从 H1 到 N2 的最优路径不应经过自己，而应通过 R4 更快。
- 所以 R1 向 H1 发送 ICMP “改变路由” 报文，建议 H1 下次将数据发给 R4。

> ✅ 用途：
>
> - 动态优化路由选择
> - 提高网络性能（避免绕远路）

> 🔄 示例：H1 默认网关是 R1，R1 通知它：“下次去 N2 应该走 R4！”

------

### 📌 第7张图：哪些情况不应发送 ICMP 差错报告？

> **重要规则**：为了避免产生大量 ICMP 报文造成网络风暴，以下情况**不发送 ICMP 差错报告**：

| 情况                                | 是否发送 ICMP                  |
| ----------------------------------- | ------------------------------ |
| 对 ICMP 差错报告报文本身            | ❌ 不发送                       |
| 对第一个分片之后的所有后续分片      | ❌ 不发送（只对第一个分片响应） |
| 对具有多播地址的数据报              | ❌ 不发送                       |
| 对特殊地址（如 127.0.0.0、0.0.0.0） | ❌ 不发送                       |

> ✅ 设计目的：防止无限递归或广播风暴。

------

### 📌 第8张图：常用的 ICMP 询问报文

> **两种主要类型**：

#### 1️⃣ 回送请求和回答（Echo Request & Reply）

- 主机 A 发送 ICMP Echo Request 给主机 B
- 主机 B 回复 Echo Reply
- 就是我们常用的 `ping` 命令！

> ✅ 用途：
>
> - 测试目标主机是否可达
> - 测量往返延迟
> - 检查网络连通性

#### 2️⃣ 时间戳请求和回答（Timestamp Request & Reply）

- 请求方发送 TimeStamp Request
- 对方回复当前时间（从 1900年1月1日起的秒数）
- 包含发送时间、接收时间、发送回执时间

> ✅ 用途：
>
> - 时钟同步（如 NTP 的基础）
> - 测量网络延迟

### 🔹 第3~5张图：traceroute 工作原理详解（动态演示）

#### 🧩 场景设定：

- H1 想知道到达 H2 的路径上有哪些路由器？
- 路径：H1 → R1 → R2 → H2

#### 🔄 工作流程（三步走）：

------

#### ✅ 第一步：TTL=1 → 找到第一跳路由器 R1

- H1 发送一个 **TTL=1** 的 ICMP 回送请求报文给 H2
- R1 收到后，TTL 减 1 变为 0 → 丢弃数据报
- R1 向 H1 发送 **ICMP 时间超过差错报告**
- H1 得知：“第一个路由器是 R1”

> 💡 关键：利用 **TTL=0 触发时间超时报文**

------

#### ✅ 第二步：TTL=2 → 找到第二跳路由器 R2

- H1 再次发送一个 **TTL=2** 的 ICMP 回送请求
- 经过 R1（TTL→1），再传到 R2（TTL→0）
- R2 丢弃，并返回 **ICMP 时间超过差错报告**
- H1 得知：“第二个路由器是 R2”

------

#### ✅ 第三步：TTL=3 → 到达终点 H2

- H1 发送 **TTL=3** 的 ICMP 回送请求
- 经过 R1、R2 后，TTL 还剩 1，最终到达 H2
- H2 正常接收并回复 **ICMP 回送回答报文**
- H1 收到回复，表示已到达目标主机

> ✅ 结果：H1 构建出完整路径：H1 → R1 → R2 → H2

## 🔹 图1–图5：**虚拟专用网（VPN）**

### ✅ 概念引入

> **什么是虚拟专用网（VPN）？**

- **部门A** 在北京，使用私有IP地址 `10.1.0.x`
- **部门B** 在上海，使用私有IP地址 `10.2.0.x`
- 两者通过**因特网**连接，中间经过路由器 R1 和 R2。

### 🔐 工作流程（图3–图4）

1. **内部数据报封装**：
   - 来自 `10.1.0.3` 的数据包，目标为 `10.2.0.3`
   - 内部IP数据报被封装进一个新的IP数据报中
   - 新的源地址为 R1 的公网IP：`125.1.2.3`
   - 新的目的地址为 R2 的公网IP：`194.4.5.6`
2. **加密传输**：
   - 数据在进入因特网前进行**加密**，保证安全性
   - 因特网只看到 `125.1.2.3 → 194.4.5.6` 的通信
3. **解密与转发**：
   - 到达 R2 后，解密并还原成原始内部数据报
   - 转发给 `10.2.0.3`

### 💡 技术要点

- 使用 **IP隧道技术** 构建安全通道
- 实现了跨地域的安全通信
- 私有IP地址无需申请，可自由分配

### 📌 分类说明（图5）

| 类型            | 描述                                   |
| --------------- | -------------------------------------- |
| **内联网VPN**   | 同一机构内部不同部门之间通过因特网连接 |
| **外联网VPN**   | 机构与外部合作伙伴建立安全连接         |
| **远程接入VPN** | 员工在外通过公网接入公司内网           |

## 🔹 图6–图9：**网络地址转换（NAT）与NAPT**

### ✅ 背景问题

- IPv4地址稀缺 → 一个组织无法获得足够多的公网IP
- 解决方案：使用**私有IP地址 + NAT**

### 🧩 私有IP地址范围（图6）

text







```
110.0.0.0 ~ 10.255.255.255     (10/8)
2172.16.0.0 ~ 172.31.255.255   (172.16/12)
3192.168.0.0 ~ 192.168.255.255 (192.168/16)
```

这些地址可以在局域网内自由使用，但不能直接用于公网通信。

------

### 🔁 NAT 工作机制（图7）

#### 示例：

- 专用网内主机：`192.168.0.2`
- 目标公网主机：`218.75.230.30`
- NAT路由器拥有公网IP：`172.38.1.5`

#### 步骤：

1. 修改源地址：将 `192.168.0.2` 改为 `172.38.1.5`
2. 记录映射关系：`172.38.1.5 ↔ 192.168.0.2`
3. 发送数据包到公网

#### 回程处理：

- 公网主机回包给 `172.38.1.5`
- NAT路由器查表，发现对应的是 `192.168.0.2`
- 将目的地址改为 `192.168.0.2` 并转发

✅ 实现了多个私有IP共享一个公网IP上网。

------

### ⚙️ NAPT（网络地址与端口号转换）（图8–图9）

#### 为什么需要NAPT？

- 如果只有一个公网IP，但有多台主机要上网？
- 可以结合**端口号**来区分不同的主机

#### NAPT 原理：

- 使用 **IP + 端口** 对进行映射
- 例如：
  - 内部主机 A: `192.168.0.2:5000` → 外部：`172.38.1.5:10000`
  - 内部主机 B: `192.168.0.3:5001` → 外部：`172.38.1.5:10001`

这样，**一个公网IP可以支持成千上万的内部主机同时上网**。

------

### ❌ 安全性特点（图9）

> **外网主机能否主动发起连接？**

- **不可以！**
- 原因：NAPT 路由器只会响应**已有会话**的回包
- 如果外网主机发送数据包给 `172.38.1.5`，但没有对应的映射记录，会被丢弃
- 这种机制提供了一定程度的**防火墙功能**

| 特性     | VPN                    | NAT/NAPT                 |
| -------- | ---------------------- | ------------------------ |
| 目的     | 安全通信、跨地域互联   | 解决IPv4地址不足         |
| 使用场景 | 企业分支机构、远程办公 | 局域网接入互联网         |
| IP地址   | 使用私有IP             | 私有IP + 公网IP映射      |
| 安全性   | 加密、隧道保护         | 限制外网主动访问（NAPT） |
| 关键技术 | IP隧道、加密           | 地址转换、端口映射       |

## 🎯 学习重点提炼

1. **私有IP地址** 是本地使用的，不需申请，也不可在公网路由。
2. **VPN** 通过加密隧道实现在公网上传输私有数据，保障安全。
3. **NAT** 允许多个私有IP共用一个公网IP，节省地址资源。
4. **NAPT** 更进一步，利用端口号实现多对一映射，提升效率。
5. **NAPT 提供基本防火墙功能**：防止外部未授权访问。

## 🔍 内容详解

### ✅ 一、文字部分解析

> **原文：** 对于一些P2P网络应用，需要外网主机主动与内网主机进行通信，在通过NAT时会遇到问题，需要网络应用自己使用一些特殊的NAT穿越技术来解决问题。
>
> 另外，由于NAT对外网屏蔽了内网主机的网络地址，能为内网的主机提供一定的安全保护。

#### 💡 意义解读：

1. **P2P 应用的问题**：

   - P2P（Peer-to-Peer）如迅雷、BitTorrent、VoIP 等，通常要求双方都能互相发起连接。
   - 但如果某一方在**NAT后的内网中**，其真实IP被隐藏，外部主机无法直接访问它。
   - 因此必须采用 **NAT穿越技术**（如 STUN、TURN、ICE、UPnP、端口映射等）才能建立连接。

2. **安全性优势**：

   - NAT 本身不提供加密或认证，但它起到了“

     防火墙作用

     ”：

     - 外部主机不知道内部主机的真实IP
     - 不能主动发起连接（除非有映射规则）
     - 所以对内网主机有一定保护作用

# 第五章

###  教学主题：**5.1 运输层概述**

#### ✅ 核心目标：

解释运输层在计算机网络体系结构中的作用，特别是它如何为**不同主机上的应用进程之间提供端到端的通信服务**。

------

## 🔍 图片内容逐层解析

### 📌 第一张图：网络拓扑与层次关系

- **顶部文字说明：**
  - 物理层、数据链路层、网络层解决了主机之间的**通信问题**（即主机到主机）。
  - 但真正进行通信的是**运行在主机上的进程**（如 AP1 和 AP3）。
  - 因此，**运输层的任务**是为不同主机上的应用进程提供直接通信服务 → 即“**端到端协议**”。
- **底部示意图：**
  - 左右两端分别是两台主机，分别运行着应用进程 `AP1`, `AP2` 和 `AP3`, `AP4`。
  - 中间经过 LAN1 → R1（路由器）→ WAN（广域网）→ R2（路由器）→ LAN2。
  - 用两条线表示两个作用范围：
    - **橙色虚线**：网络层的作用范围（从一端主机到另一端主机）
    - **蓝色虚线**：运输层的作用范围（从一个应用进程到另一个应用进程）

> ✅ 关键点：
>
> - 网络层负责**主机间通信**（IP 地址层面）。
> - 运输层负责**进程间通信**（端口号层面），实现“端到端”逻辑通信。

------

### 📌 第二张图：OSI 模型视角下的分层结构

- 展示了 **五层模型**（应用层 → 运输层 → 网络层 → 链路层 → 物理层）。
- 左右两边为主机，中间是网络核心（R1, R2, WAN）。
- **红色虚线箭头** 表示：运输层提供的**逻辑通信路径**，跨越整个网络，连接两个主机的应用进程（AP1 ↔ AP3 或 AP2 ↔ AP4）。
- 在每一台主机上，**运输层通过端口（Port）** 将数据传给对应的应用程序。

> 💡 “端口” 是运输层识别进程的关键机制。例如：
>
> - AP1 使用端口 A 发送数据
> - AP3 使用端口 B 接收数据
> - 运输层确保这些数据正确地发送到目标端口

> ✅ 核心观点：
>  **运输层屏蔽了底层网络细节**，让应用进程感觉像是直接在彼此之间通信。

------

### 📌 第三张图：补充文字说明 + 强调重点

- **关键句总结：**

  > “运输层向高层用户屏蔽了下面网络核心的细节（如网络拓扑、路由选择协议等），使应用进程看起来好像在两个运输层实体之间有一条端到端的逻辑通信信道。”

- 提出两种主要运输协议：

  - **TCP（Transmission Control Protocol）**：面向连接，可靠传输。
  - **UDP（User Datagram Protocol）**：无连接，不可靠但高效。

> ✅ 本章重点：
>
> - TCP 和 UDP 的对比与使用场景
> - 如何实现端到端的可靠/不可靠通信

------

## 🧩 总结：运输层的核心职责

| 功能                 | 说明                             |
| -------------------- | -------------------------------- |
| **端到端通信**       | 实现不同主机上应用进程之间的通信 |
| **端口寻址**         | 利用端口号区分不同的应用进程     |
| **屏蔽底层复杂性**   | 不需要应用关心路由、拥塞等问题   |
| **提供两种服务模式** | TCP（可靠） vs UDP（快速）       |

------

## 🔄 类比理解（便于记忆）

你可以把运输层想象成：

> 🚚 **快递公司**：
>
> - 网络层 = 负责把包裹从城市A送到城市B（地址是 IP 地址）
> - 运输层 = 负责把包裹从你家送到对方家门口（地址是门牌号/手机号）
> - 应用层 = 你是谁要寄什么（比如微信聊天）

## 🎯 核心主题：

> **如何通过端口号实现多进程间的网络通信？** —— 端口是运输层的关键机制，用于区分同一台主机上的不同应用进程。

------

## 🔍 图片内容逐图解析

------

### ✅ 图1：端口号的基本概念（文字说明）

#### 主要知识点：

| 内容           | 解释                                                       |
| -------------- | ---------------------------------------------------------- |
| 进程标识符 PID | 操作系统内部使用，但跨平台不统一（Windows/Linux/Mac 不同） |
| 需要统一标识   | 因特网中不同操作系统需共用标准方式来识别应用进程           |
| **端口号**     | TCP/IP 使用端口号作为统一标识，解决跨平台通信问题          |

#### 端口号范围（16比特）：

- **0 ~ 65535**
  - **熟知端口号（Well-known Ports）**：0~1023
    → IANA 分配给重要协议（如 HTTP:80, DNS:53）
  - **登记端口号（Registered Ports）**：1024~49151
    → 用户程序申请注册，避免冲突（如 RDP:3389）
  - **短暂端口号（Ephemeral Ports）**：49152~65535
    → 客户端临时使用，通信结束后可被其他进程重用

> ✅ 强调：**端口号只具有本地意义！**
>
> - 同一端口号在不同机器上没有联系。
> - 例如：两台电脑都用 80 端口跑 Web 服务，彼此互不影响。

------

### ✅ 图2：发送方“复用”与接收方“分用”

#### 核心思想：

> **复用（Multiplexing）**：多个应用进程的数据交给同一个运输层协议处理
>  **分用（Demultiplexing）**：运输层根据端口号将数据正确送达对应的应用进程

#### 结构图解析：

plaintext







```
1发送方：
2应用进程1 → UDP复用 → 用户数据报 → IP复用 → IP数据报
3应用进程2 → TCP复用 → 报文段       → IP复用 → IP数据报
```

plaintext







```
1接收方：
2IP数据报 → IP分用 → UDP分用 → 应用进程1
3IP数据报 → IP分用 → TCP分用 → 应用进程2
```

#### 关键点：

- **UDP 复用/分用**：封装为 `用户数据报`，协议字段 = 17
- **TCP 复用/分用**：封装为 `报文段`，协议字段 = 6
- **IP 层负责路由**，而运输层负责“把数据交给谁”

> 💡 类比理解：
>
> - 像快递公司：
>   - 发送时：多个包裹打包成一个大箱子（复用）
>   - 接收时：拆箱并按地址贴标签送到各自门口（分用）

| **登记端口** | 1024~49151，用户注册使用               |
| **短暂端口** | 49152~65535，客户端临时使用            |
| **复用**     | 多个应用进程共享一个运输层协议发送数据 |
| **分用**     | 运输层根据端口号将数据交付给正确进程   |
| **本地意义** | 不同主机相同端口号无关联               |

## 🎯 核心主题：

> **UDP vs TCP：两种运输层协议的本质区别**

| 特性     | UDP                  | TCP                   |
| -------- | -------------------- | --------------------- |
| 是否连接 | 无连接               | 面向连接              |
| 可靠性   | 不可靠               | 可靠                  |
| 通信模式 | 支持单播、多播、广播 | 仅支持单播            |
| 数据单位 | 报文（Datagram）     | 字节流（Byte Stream） |
| 头部开销 | 小（8字节）          | 大（20~60字节）       |

## 🔍 图片内容逐图解析

------

### ✅ 图1：连接建立过程对比

#### 左侧：UDP

- **无连接**：发送前不需要任何握手过程。
- 直接发送数据报 → 网络中传输 → 接收方接收。
- 时间轴上没有“准备阶段”，直接进入“数据传输”。

#### 右侧：TCP

- **必须先建立连接**：“三报文握手”（Three-Way Handshake）
- 数据传输完成后，需通过“四报文挥手”（Four-Way Wave）释放连接。
- 时间轴显示了明确的三个阶段：
  1. 建立连接（三报文握手）
  2. 数据传输
  3. 释放连接（四报文挥手）

> 💡 类比理解：
>
> - UDP 像发短信：说一句就发，不管对方有没有收到。
> - TCP 像打电话：先拨号→接通→通话→挂断。

------

### ✅ 图2：通信模式支持对比

#### 左侧：UDP 支持多种通信模式

- **单播**（一对一）
- **多播**（一对多）
- **广播**（一对所有）

> 📌 示例：
>
> - DNS 查询通常使用 UDP 广播或多播；
> - 视频直播可能用 UDP 多播来同时推送给多个客户端。

#### 右侧：TCP 仅支持 **单播**

- 每个 TCP 连接只能是 **两个端点之间的一对一通信**。
- 不支持多播或广播。

> ❗ 为什么？
>
> - TCP 是面向连接的，需要维护状态（如序列号、确认号），无法处理多个接收者。

------

### ✅ 图3：数据传输模型对比

#### 左侧：UDP —— 面向应用报文（Message-Oriented）

- 发送方将每个应用层报文作为一个独立的数据单元交给 UDP。
- UDP 不做拆分，直接封装成一个用户数据报。
- 接收方收到的是完整的原始报文（不丢失也不拼接）。

> 📌 特点：
>
> - “原样交付”：你发什么，我就收什么。
> - 如果应用层发了一个大报文，UDP 可能会因 MTU 超限而分片（但由 IP 层完成，UDP 不关心）。

#### 右侧：TCP —— 面向字节流（Stream-Oriented）

- 应用层可以连续写入数据（如文件读取），TCP 将其视为一个连续的 **字节流**。
- TCP 自动进行分段（Segmentation）并编号（Sequence Number）。
- 接收方按序重组，最终向上层交付一个连续的字节流。

> 📌 示例：
>
> - 文件传输时，即使你写了多个小块数据，TCP 也会把它们合并成一段发送；
> - 也可能将一个大文件切分成多个 TCP 报文段发送。

> ⚠️ 注意：
>
> - TCP 不保证边界保留（即不能区分“这是第一个报文”还是“这是第二个报文”）；
> - 若需边界，需由应用层自行处理（如 HTTP 协议中的 Content-Length）。

------

### ✅ 图4：可靠性对比

#### 左侧：UDP —— 不可靠传输

- 网络中可能出现：
  - 丢包
  - 误码
  - 乱序
  - 重复
- UDP **不做任何处理**，只负责“尽力而为”的交付。
- 若有错误，直接丢弃，不重传、不通知。

> 📌 使用场景：
>
> - 实时性要求高的应用：IP电话、视频会议、在线游戏
> - 允许少量丢包，但不能容忍延迟

#### 右侧：TCP —— 可靠传输

- 提供 **面向连接的可靠信道**，确保：
  - 所有数据正确到达
  - 顺序一致
  - 无重复
  - 无遗漏
- 实现机制包括：
  - 序列号 + 确认号
  - 超时重传
  - 流量控制（滑动窗口）
  - 拥塞控制

> 📌 使用场景：
>
> - 文件下载（FTP）、网页浏览（HTTP）、邮件（SMTP）

------

### ✅ 图5：服务类型总结

| 项目                  | UDP                               | TCP                               |
| --------------------- | --------------------------------- | --------------------------------- |
| 服务类型              | 向上提供 **无连接不可靠传输服务** | 向上提供 **面向连接可靠传输服务** |
| 适用应用              | 实时应用（如 VoIP、视频会议）     | 可靠性要求高（如文件传输、Web）   |
| 是否使用流量/拥塞控制 | ❌ 否                              | ✅ 是                              |
| 首部长度              | 仅8字节                           | 最小20字节，最大60字节            |

> 📌 补充说明：
>
> - “尽最大努力交付” = 不保证成功，但尽量尝试。
> - TCP 的可靠性是通过复杂的机制实现的，代价是性能略低。

------

### ✅ 图6：首部结构对比（最核心部分）

#### 左侧：UDP 用户数据报首部（共8字节）

| 字段     | 长度  | 作用                        |
| -------- | ----- | --------------------------- |
| 源端口   | 2字节 | 发送方端口号                |
| 目的端口 | 2字节 | 接收方端口号                |

| 检验和   | 2字节 | 检查数据完整性（可选）      |

> ✅ 总结：
>
> - 极简设计，适合轻量级通信。
> - 检验和用于检测错误，但不纠错。

#### 右侧：TCP 报文段首部（最小20字节，最大60字节）

##### 固定部分（20字节）：

| 字段                            | 作用                                  |
| ------------------------------- | ------------------------------------- |
| 源端口 / 目的端口               | 同UDP                                 |
| 序号（Sequence Number）         | 当前报文段第一个字节的序号            |
| 确认号（Acknowledgment Number） | 期望收到的下一个字节序号              |
| 数据偏移                        | 首部长度（以4字节为单位）             |
| 保留                            | 6位，目前未用                         |
| 控制位（6个标志位）             | SYN, ACK, FIN, RST, PSH, URG          |
| 窗口大小                        | 流量控制用，表示接收缓冲区可用空间    |
| 检验和                          | 检查TCP报文段完整性                   |
| 紧急指针                        | 指向紧急数据结束位置（当URG=1时有效） |

##### 可变部分（最多40字节）：

- 选项字段（如最大报文段长度 MSS、时间戳等）

> ✅ 总结：
>
> - TCP 首部复杂，包含大量控制信息，支撑其可靠性功能。

##  核心主题：

> **TCP 流量控制（Flow Control）—— 使用“滑动窗口”避免接收方被淹没**

------

# 🔍 图片内容逐图解析与总结

------

### ✅ 图1：引入流量控制概念

#### 内容要点：

- 我们希望数据传输越快越好。
- 但如果发送方发得太快，接收方来不及处理 → 数据可能丢弃。
- **流量控制目的**：让发送方不要发送太快，要让接收方来得及接收。
- 实现方式：**利用滑动窗口机制**。

> 💡 类比理解：
>
> - 发送方像一个水龙头，接收方像一个水桶；
> - 如果水龙头开太大，水桶装不下就会溢出；
> - 流量控制就是调节水龙头大小，不让水溢出。

------

### ✅ 图2~图6：详细案例演示（核心！）

这是一个完整的 **TCP 流量控制流程图**，展示了主机 A 向主机 B 发送数据，B 用“接收窗口”控制 A 的发送速率的过程。

#### 背景设定：

- 主机 A 是发送方
- 主机 B 是接收方
- 已建立 TCP 连接
- 初始时 B 的接收窗口为 300 字节
- 每个报文段携带一定字节数的数据，按序号编号

------

#### 第一步：正常发送与确认

| 时间 | 操作                                                     |
| ---- | -------------------------------------------------------- |
| ①    | A 发送 `seq=1` 的 DATA（1~100 字节）                     |
| ②    | A 发送 `seq=101` 的 DATA（101~200 字节）                 |
| ③    | A 发送 `seq=201` 的 DATA（201~300 字节）→ **但丢失了！** |

> ⚠️ 注意：虽然第3个报文段丢失了，但后续仍可继续发送，因为 TCP 支持连续发送多个报文段。

------

#### 第二步：接收方反馈接收窗口（rwnd）

- B 收到了前两个报文段（1~200），但第三个没收到。
- B 回复 ACK 报文：
  - `ACK=1`（表示期望收到下一个字节是 201）
  - `ack=201`（累计确认已收到到 200）
  - `rwnd=300`（告诉 A：“我现在还能接收 300 字节”）

> ✅ 解读：
>
> - rwnd = 接收缓冲区剩余空间
> - A 可以继续发送最多 300 字节的新数据（即 201~500）

------

#### 第三步：A 继续发送，B 更新窗口

| 时间 | 操作                                                         |
| ---- | ------------------------------------------------------------ |
| ④    | A 发送 `seq=301`（301~400）                                  |
| ⑤    | A 发送 `seq=401`（401~500）                                  |
| ⑥    | A 重传 `seq=201`（之前丢失的那个）                           |
| ⑦    | B 收到 301~500，更新状态 → 回复 `ACK=1`, `ack=501`, `rwnd=100` |

> ✅ 解读：
>
> - B 现在只允许再接收 100 字节（缓冲区快满了）
> - 所以 A 只能发送 501~600 字节

------

#### 第四步：接收方关闭窗口（rwnd=0）

| 时间 | 操作                                                   |
| ---- | ------------------------------------------------------ |
| ⑧    | A 发送 `seq=501`（501~600）                            |
| ⑨    | B 收到后，缓冲区满 → 回复 `ACK=1`, `ack=601`, `rwnd=0` |

> ❗ 此时 A 不再能发送任何新数据！

> 📌 原因：
>
> - 接收窗口为 0，说明 B 暂时无法接收更多数据
> - A 必须暂停发送，等待 B 释放空间

------

#### 第五步：零窗口探测（Zero Window Probe）

由于 B 的窗口为 0，A 不能发送，但也不能一直等下去。

| 时间 | 操作                                                       |
| ---- | ---------------------------------------------------------- |
| ⑩    | A 启动 **持续计时器（Persist Timer）**                     |
| ⑪    | 计时器超时后，A 发送 **零窗口探测报文**（携带 1 字节数据） |
| ⑫    | B 收到该报文 → 回复 `ACK=1`, `rwnd=0`（假设此时仍为 0）    |
| ⑬    | A 再次启动计时器，再次发送探测报文                         |
| ⑭    | B 缓冲区有空间 → 回复 `ACK=1`, `rwnd=300`（恢复接收能力）  |

> ✅ 结果：
>
> - 成功打破“死锁”局面
> - A 可以重新开始发送数据

> 📌 关键点：
>
> - 零窗口探测报文不是真正的数据，而是用于“探路”
> - 它携带 1 字节数据是为了触发对方响应（否则纯 ACK 无法区分）

------

### ✅ 图7：真题解析（2010年考研题）

#### 题目回顾：

> 主机甲和主机乙之间建立了 TCP 连接，最大段长度为 1000 字节。
>  主机甲向主机乙连续发送两个最大段（共 2000 字节），成功收到第一个段的确认，其中通告的接收窗口为 2000 字节。
>  问：此时主机甲还可以向主机乙发送的最大字节数是多少？

#### 分析过程：

1. **发送情况**：
   - 甲发送了两个最大段：`0~999` 和 `1000~1999`（共 2000 字节）
2. **确认信息**：
   - 乙返回第一个段的确认，说明收到了 `0~999`
   - 乙通告的接收窗口为 **2000 字节**
3. **计算发送窗口**：
   - 发送窗口 = min(拥塞窗口, 接收窗口)
   - 题目未给出拥塞窗口，所以默认使用接收窗口值
   - 当前发送窗口 = 2000 字节
4. **当前可发送范围**：
   - 已发送：`0~1999`
   - 下一个可发送区间：`2000~2999`（共 1000 字节）

> ✅ 答案：**A. 1000 字节**

> 📌 解释：
>
> - 虽然接收窗口是 2000，但由于已经发送了 2000 字节，只有接下来的 1000 字节在允许范围内
> - TCP 是基于字节流的，发送窗口是从当前已发送位置开始计算的

------

### ✅ 图8：总结要点

#### 关键结论：

1. **TCP 流量控制由接收方主导**：
   - 接收方通过 `rwnd` 字段告知发送方自己的接收能力
   - 发送方根据这个值调整自己的发送窗口
2. **滑动窗口机制实现流量控制**：
   - 发送窗口大小受接收窗口限制
   - 接收窗口动态变化，反映接收缓冲区状态
3. **当接收窗口为 0 时，发送方停止发送**：
   - 启动持续计时器
   - 定期发送零窗口探测报文
   - 直到接收方恢复接收能力
4. **零窗口探测报文的作用**：
   - 防止“死锁”：避免双方都在等待而无动作
   - 探测接收方是否准备好接收数据

| 项目                        | 内容                                                   |
| --------------------------- | ------------------------------------------------------ |
| **目的**                    | 防止发送方发送过快导致接收方缓冲区溢出                 |
| **实现机制**                | 滑动窗口 + 接收窗口（rwnd）                            |
| **控制主体**                | 接收方控制发送方                                       |

| **接收窗口为 0 时怎么办？** | 发送方停止发送，启动持续计时器，定期发送零窗口探测报文 |
| **零窗口探测报文特点**      | 携带 1 字节数据，用于触发对方响应                      |
| **累计确认机制**            | 只需确认最后一个连续收到的字节，无需逐个确认           |

## 🎯 学习建议 & 常见误区

### ✅ 如何理解“滑动窗口”？

- 想象一条传送带上的数据块
- 窗口代表当前可以发送的字节范围
- 每收到一个确认，窗口向前滑动
- 若接收方窗口变小，发送方窗口也相应缩小

### ❌ 常见误区纠正：

| 误区                                     | 正确理解                                     |
| ---------------------------------------- | -------------------------------------------- |
| “接收窗口为0就不能再发任何数据”          | 对，但会启动持续计时器，发送探测报文         |
| “只要发送了数据就必须等确认才能发下一段” | 错！TCP 支持管道化传输，可连续发送多个报文段 |
| “接收窗口大小固定”                       | 错！它随接收缓冲区空闲空间动态变化           |
| “零窗口探测报文是纯 ACK”                 | 错！必须携带 1 字节数据才能触发对方响应      |

------

## 📌 总结一句话：

> **TCP 流量控制的核心是“让接收方决定发送方的速度”，通过“接收窗口（rwnd）”和“滑动窗口机制”实现，避免接收方被淹没；当窗口为0时，使用“零窗口探测”防止死锁。**



### 📌 图1：拥塞的定义与影响

- **核心概念**：
  - 当对网络资源的需求超过其可用容量时，就会发生 **拥塞（congestion）**。
  - 网络资源包括带宽、交换结点的缓存和处理能力等。
  - 若不进行拥塞控制，整个网络的吞吐量会随输入负载增加而下降。
- **图表说明**：
  - 横轴：输入负载
  - 纵轴：吞吐量
  - 三条曲线：
    - **红色曲线（无拥塞控制）**：随着负载上升，吞吐量先升后降，最终导致“死锁”（吞吐量为0）。
    - **蓝色曲线（实际拥塞控制）**：吞吐量平稳增长，避免崩溃。
    - **绿色曲线（理想拥塞控制）**：吞吐量达到最大并保持稳定。

> ✅ 结论：拥塞控制至关重要，能防止网络性能恶化。

### 📌 图2：四种拥塞控制算法介绍

- 四种机制：
  1. **慢开始**（Slow Start）
  2. **拥塞避免**（Congestion Avoidance）
  3. **快重传**（Fast Retransmit）
  4. **快恢复**（Fast Recovery）
- 假设前提条件：
  1. 数据单向传输，反方向只发确认。
  2. 接收方缓冲区足够大 → 发送窗口大小由网络拥塞程度决定。
  3. 以 **MSS（最大报文段长度）个数** 为单位讨论问题，而非字节。

> 🔍 这些假设简化了模型，便于理解拥塞控制机制的核心思想。

### 📌 图3：发送方状态变量说明

- 发送方维护两个关键变量：
  - `cwnd`（Congestion Window）：拥塞窗口，动态变化，反映当前允许发送的数据量。
  - `ssthresh`（Slow Start Threshold）：慢开始门限值，用于切换算法。
  - `snd`（Send Window）= `cwnd`（在本场景下）
- 关键规则：
  - 如果没有拥塞 → `cwnd` 增加；
  - 如果出现拥塞（如超时重传）→ `cwnd` 减少。
  - 判断拥塞依据：**未按时收到确认报文（即超时重传）**
- 算法选择逻辑：
  - `cwnd < ssthresh`：使用 **慢开始**
  - `cwnd > ssthresh`：改用 **拥塞避免**
  - `cwnd = ssthresh`：两者皆可

### 📌 图4～图8：慢开始 + 拥塞避免过程演示

#### ▶️ 图4：慢开始阶段（初期）

- 起始时 `cwnd = 1`
- 每轮收到确认，`cwnd += 1`（指数增长）
- 示例：第1轮发1个报文段，第2轮发2个，第3轮发4个……
- 当 `cwnd` 达到 `ssthresh = 16` 时，进入下一阶段。

> ✅ 此阶段称为“慢开始”，但不是因为速度慢，而是因为初始注入数据少，逐步试探网络承载能力。

#### ▶️ 图5：进入拥塞避免阶段

- `cwnd` 已达 `ssthresh = 16`，开始执行 **拥塞避免**
- 每次成功传输一轮，`cwnd += 1`（线性增长）
- 例如：从16→17→18→...→24

> 💡 目的是让网络流量平滑上升，避免突然激增造成拥塞。

#### ▶️ 图6：发生拥塞（超时重传）

- 假设在 `cwnd = 24` 时，部分报文丢失 → **超时重传**
- 触发拥塞处理机制：
  1. 将 `ssthresh` 更新为 `cwnd / 2 = 12`
  2. 将 `cwnd` 设置为 1
  3. 重新启动 **慢开始**

> ⚠️ 说明：一旦检测到严重拥塞（超时），立即大幅降低发送速率。

#### ▶️ 图7：重启慢开始

- `cwnd` 从 1 开始再次增长
- 当 `cwnd` 达到新的 `ssthresh = 12` 时，再次切换到拥塞避免

> 🔄 形成一个周期性的“探测—增长—拥塞—恢复”循环。

#### ▶️ 图8：完整示意图

- 整体流程图展示：
  - 初始 `ssthresh = 16`
  - 慢开始阶段：指数增长至16
  - 拥塞避免阶段：线性增长至24
  - 拥塞发生 → `ssthresh = 12`, `cwnd = 1`
  - 再次慢开始 → 达到新 `ssthresh = 12` 后进入拥塞避免
- 图中还标注了：
  - “慢开始” ≠ 增长慢，而是**初始发送量小**
  - “拥塞避免” ≠ 完全避免拥塞，而是通过**线性增长**来减少拥塞概率

| 阶段         | 特征                             | cwnd变化方式                    | 触发条件           |
| ------------ | -------------------------------- | ------------------------------- | ------------------ |
| **慢开始**   | 初始阶段，试探性发送             | 每轮翻倍（指数增长）            | `cwnd < ssthresh`  |
| **拥塞避免** | 稳定传输阶段                     | 每轮+1（线性增长）              | `cwnd >= ssthresh` |

| **快恢复**   | 快速恢复连接，不完全退回到慢开始 | `cwnd = ssthresh`，然后线性增长 | 快重传后触发       |

### 📌 图1：快重传与快恢复的背景介绍

#### ✅ 核心内容：

- **慢开始 + 拥塞避免** 是 1988 年提出的 TCP Tahoe 版本的核心算法。

- 1990 年提出改进版本 TCP Reno

  ，增加了两个新机制：

  - **快重传（Fast Retransmit）**
  - **快恢复（Fast Recovery）**

> 🔍 目标：提升 TCP 性能，避免因个别报文丢失而误判为网络拥塞。

#### ❗️ 问题：为何需要改进？

- 网络中有时会**个别报文段丢失**，但整体并未发生拥塞。
- 如果使用原始机制（Tahoe），会导致：
  - 发送方超时 → 认为网络拥塞
  - 将 `cwnd` 设为 1，重启慢开始
  - 导致传输效率下降（浪费带宽）

> ⚠️ 所以需要更智能的机制来区分“真正拥塞”和“偶然丢包”。

#### ✅ 解决方案：快重传

- 让发送方**尽早知道某个报文段丢失**，而不必等待超时。
- 关键规则：
  - 接收方收到失序报文后，**立即发送重复确认（duplicate ACK）**
  - 发送方一旦收到 **3 个连续的重复确认**，就立刻重传该报文段
  - 不再等待超时计时器到期

> 💡 优点：减少延迟，提高吞吐量（可提升约 20%）

------

### 📌 图2：快重传的工作流程示意图

#### 🔁 场景描述：

- 发送方按顺序发送 M1, M2, M3, M4, M5, M6
- M3 在传输过程中**丢失**
- 接收方收到 M4 后发现不连续（期望的是 M3），于是对 M2 发出**重复确认**
- 后续收到 M5、M6，仍无法填补缺口，继续发出对 M2 的重复确认

#### 📊 时间线说明：

| 时间              | 事件                                |
| ----------------- | ----------------------------------- |
| 发送 M1 → M6      | 正常发送                            |
| 收到 M4           | 接收方发现缺少 M3 → 发出重复确认 M2 |
| 收到 M5 → M6      | 继续发重复确认 M2                   |
| 收到第3个重复确认 | 发送方立即重传 M3                   |

> ✅ **关键点**：不需要等到 RTO（超时重传时间）到来，就能快速响应。

#### ✅ 快重传核心原则：

1. 接收方不要等自己发数据才捎带确认 → **立即发送确认**
2. 即使收到失序报文，也要**立即发送重复确认**
3. 发送方收到 **3 个连续重复确认** → **立即重传对应报文段**

> 📌 注：为什么是“3个”？因为网络中可能有乱序或重复，3次可以有效避免误判。

### 📌 图1：基本概念引入

#### 🔹 标题：5.6 TCP超时重传时间的选择

> ✅ 说明：这是 TCP 协议中最复杂的问题之一。

#### 🔹 图形示意：

- A 和 B 是两个主机，已建立 TCP 连接。
- A 发送一个数据报文段 0 → B 收到后返回确认报文段 0。
- 时间轴显示了从发送到收到确认的全过程。

#### 🔹 关键术语：

- **RTT0**：第一次测量得到的往返时间（Round-Trip Time）
- **RTO**：超时重传时间（Retransmission TimeOut），即发送方等待确认的最大时间

#### 🔹 核心原则：

> ❗️ **RTO 应略大于 RTT**

✅ 原因：

- 如果 RTO 设置得太小（小于实际 RTT），会误判为“丢包”而提前重传；
- 如果 RTO 太大，则会导致传输延迟增加，降低效率。

> 💡 所以 RTO 必须合理设置，既不能太短也不能太长。

------

### 📌 图2：多次交互下的 RTT 变化

#### 🔹 新增内容：

- 第二次通信：A 发送数据报文段 1 → B 返回确认报文段 1
- 对应的往返时间为 **RTT1**
- 若此时确认未及时返回，可能触发 **重传报文段1**

#### 🔹 关键观察：

- 不同的数据报文段在不同时间传输，其 RTT 通常不相等
- 网络环境动态变化 → RTT 波动较大
- 因此不能用某一次的 RTT 直接作为 RTO 的依据！

> ⚠️ 示例：若上次 RTT = 50ms，但这次由于网络拥塞导致 RTT = 100ms，如果仍用 50ms 作 RTO，就会错误地重传。

------

### 📌 图3：如何计算 RTO？—— 加权平均法

#### 🔹 核心思想：

> ❌ 不能直接使用单次测量的 RTT 样本来设定 RTO
>  ✅ 应该利用历史 RTT 数据进行平滑处理，得出一个稳定的估计值

#### 🔹 方法一：加权平均法（RFC 6298 推荐）

##### 公式：

新的 *RT**T**s*=(1−*α*)×旧的 *RT**T**s*+*α*×新的 RTT 样本

其中：

- *RT**T**s*：**加权平均往返时间**（也称平滑往返时间）
- *α*：平滑因子，取值范围 0≤*α*<1
- RFC 6298 建议 *α*=1/8=0.125

##### 分析：

| α 值  | 影响                            |
| ----- | ------------------------------- |
| α ≈ 0 | 新样本影响小 → 平滑性强，响应慢 |
| α ≈ 1 | 新样本影响大 → 响应快，但波动大 |

> ✅ 实际中选择 α=0.125 是为了平衡“稳定性”和“响应性”。

#### 🔹 步骤总结：

1. 每次收到确认，记录当前 RTT 样本（如 RTT0、RTT1…）
2. 使用上述公式不断更新 *RT**T**s*
3. 最终的 RTO 应略大于 *RT**T**s*

> 💡 这样做可以有效过滤掉瞬时抖动，获得更可靠的网络延迟估计。

------

### ✅ 总结：TCP 超时重传时间选择的关键要点

| 内容                 | 说明                           |
| -------------------- | ------------------------------ |
| **RTO ≠ RTT**        | RTO 必须略大于 RTT，防止误判   |
| **不能用单一 RTT**   | 网络环境不稳定，需综合历史数据 |
| **使用加权平均**     | 计算平滑往返时间 *RT**T**s*    |
| **推荐 α = 0.125**   | RFC 6298 标准建议              |
| **最终 RTO > RTT_s** | 避免频繁重传                   |

### 🧠 补充知识：RTO 的进一步优化（进阶）

虽然这里只讲了基础方法，但现代 TCP 实现还会做更多改进：

1. **偏差估算（Deviation）**：
   - 计算 RTT 的波动程度（标准差）
   - RTO = *RT**T**s*+4×偏差
   - 更精确地反映网络不确定性
2. **Karn’s Algorithm**：
   - 在重传发生后，不再使用重传后的 RTT 样本参与计算
   - 防止因重传导致的 RTT 估算失真
3. **Jacobson Algorithm**：
   - 结合 RTT 和偏差动态调整 RTO
   - 是广泛使用的算法基础

###  一、核心主题：TCP 超时重传时间的选择

TCP 协议需要估计网络往返时间（RTT），并据此设置一个合理的超时时间 RTO，用于判断数据包是否丢失。

- 如果 RTO 设置得太小 → 频繁误判为丢包，导致不必要的重传。
- 如果 RTO 设置得太大 → 等待时间过长，影响传输效率。

因此，如何动态、准确地计算 RTO 是关键。

------

### 🔹 二、基本公式：RTO 的计算

> **RTO = RTTs + 4 × RTTd**

其中：

- **RTTs**：加权平均往返时间（Smoothed Round-Trip Time）
- **RTTd**：RTT 偏差的加权平均（Round-Trip Time Deviation）

#### ✅ 公式详解：

| 名称   | 公式                                                         | 参数说明                   |
| ------ | ------------------------------------------------------------ | -------------------------- |
| `RTTs` | 新的 RTTs = (1 - α) × 旧 RTTs + α × 新 RTT 样本 α = 0.125（即 1/8） | 平滑处理 RTT，避免剧烈波动 |
| `RTTd` | 新的 RTTd = (1 - β) × 旧 RTTd + β ×                          | RTTs - 新 RTT 样本         |

> 这些参数由 RFC6298 推荐使用，已成为标准做法。

------

### 🔹 三、Karn 算法及其问题

#### 🟩 Karn 算法提出背景：

当发生 **超时重传** 时，无法确定收到的 ACK 是对原始报文段还是重传报文段的响应，从而导致 RTT 测量不准确。

👉 **Karn 解决方案**：

> **一旦发生重传，就不再使用该报文段的 RTT 样本进行 RTTs 和 RTTd 的更新。**

✅ 目的：防止因重传造成 RTT 计算偏差。

#### ❌ Karn 算法的问题：

如果网络延迟突然增大（如拥塞、路由变化），而此时又因为 Karn 算法拒绝使用重传后的 RTT 样本，则：

- RTO 无法及时调整；
- 导致报文段持续超时重传；
- 出现“**反复重传**”现象，降低性能。

------

### 🔹 四、修正策略：指数退避（Exponential Backoff）

为了解决 Karn 算法带来的问题，引入了 **RTO 指数增长机制**：

> **每次发生超时重传时，将新的 RTO 设为旧 RTO 的 2 倍。**

📌 示例：

- 初始 RTO₁ = 90
- 第一次超时后：RTO₂ = 2 × 90 = 180
- 再次超时：RTO₃ = 2 × 180 = 360
- ...

这个策略称为 **慢启动中的指数退避**，有助于在网络拥塞或异常情况下避免频繁重传。

------

### 🔹 五、图示分析（结合时间轴）

#### 图中展示的是主机 A 向 B 发送数据的过程：

| 时间点 | RTT 样本           | RTTs    | RTTd   | RTO                        |
| ------ | ------------------ | ------- | ------ | -------------------------- |
| 1      | 30                 | 30      | 15     | 90                         |
| 2      | 26                 | 29.5    | 12.25  | 78.5                       |
| 3      | 32                 | 29.8125 | 9.8125 | 69.0625                    |
| 4      | 24                 | 29.0859 | 8.8125 | 64.3359                    |
| 5      | **80**（超时重传） | ——      | ——     | **128.6718**（=2×64.3359） |

⚠️ 注意：

- 在第 5 次发送时发生了 **超时重传**（RTT=80 > RTO=64.3359）
- 此时不能用 RTT=80 更新 RTTs 和 RTTd（遵循 Karn 算法）
- 但必须将 RTO 加倍 → RTO₅ = 2 × RTO₄ = 128.6718

这样可以给网络更多恢复时间，避免因短暂抖动导致持续重传。

------

### 🔹 六、重点结论总结

| 项目             | 内容                                    |
| ---------------- | --------------------------------------- |
| **RTO 计算公式** | RTO = RTTs + 4 × RTTd                   |
| **RTTs 更新**    | 使用加权平均，α = 0.125                 |
| **RTTd 更新**    | 使用偏差加权平均，β = 0.25              |
| **Karn 算法**    | 超时重传时不使用 RTT 样本               |
| **Karn 缺陷**    | 不利于 RTO 动态调整，可能导致死循环重传 |
| **修正方法**     | 每次超时重传，RTO × 2（指数退避）       |

------

### 🔹 七、实际意义

1. **提高稳定性**：即使网络突发变慢，也不会立即触发大量重传。
2. **适应性更强**：RTO 可以随网络状况动态调整。
3. **符合 TCP 拥塞控制思想**：通过重传次数和 RTO 增大来感知网络状态。

------

### ✅ 总结一句话：

> TCP 通过 **加权平均 RTT** 和 **指数退避机制** 来智能地设置 RTO，在保证可靠性的同时尽量减少无效重传，是网络协议设计中的经典优化策略。

如果你正在准备考试或面试，记住以下几点即可：

- RTO = RTTs + 4×RTTd
- α = 0.125，β = 0.25
- Karn 算法：重传时不采样 RTT
- 超时重传 → RTO × 2

##  一、核心主题：TCP 可靠传输的实现

TCP 使用 **以字节为单位的滑动窗口机制** 实现可靠数据传输，确保数据按序、无差错地送达接收方。

------

### ✅ 图1：发送窗口的基本结构

#### 📌 滑动窗口模型图示

- 发送方有一个“发送窗口”，大小为 20（表示可以连续发送最多 20 字节未被确认的数据）。
- 窗口范围：从 **31 到 50**（即允许发送字节序号 31~50）。
- 窗口分为三部分：
  - **已发送并收到确认**（如 26~30）→ 可删除
  - **已发送但未确认**（31~50）→ 在窗口内
  - **不允许发送**（>50）→ 超出窗口

#### 📌 窗口边界移动规则

| 边界           | 移动方式                                                     |
| -------------- | ------------------------------------------------------------ |
| **后沿（P1）** | 向前移动 → 收到新确认时，已确认数据可移出窗口                |
| **前沿（P3）** | 三种情况： ① 正常向前移动（收到确认且对方窗口不变） ② 不动（无新确认或窗口缩小） ③ 向后收缩（对方通知窗口变小） |

> ⚠️ 注意：**前沿不能向后移动**！但在某些情况下（如接收方窗口缩小），前沿可能“看起来”向后缩，实际是窗口整体缩小。

------

### ✅ 图2：用三个指针描述发送窗口状态

引入三个指针来精确描述窗口状态：

| 指针   | 含义                                               |
| ------ | -------------------------------------------------- |
| **P1** | 当前最小未确认字节序号（即最后一个已确认字节 + 1） |
| **P2** | 下一个待发送字节的序号（当前窗口的起始位置）       |
| **P3** | 最大允许发送的字节序号（窗口右边界）               |

#### 💡 关键公式：

- `P3 - P1` = 发送窗口尺寸（当前可用空间）
- `P2 - P1` = 已发送但尚未确认的字节数
- 小于 P1：已确认，可丢弃
- 大于等于 P3：不允许发送

👉 示例中：

- P1 = 31（已确认到 30）
- P2 = 31（下一个要发的是 31）
- P3 = 51（最大可发到 50）
- 所以窗口大小 = 51 - 31 = 20 ✔️

------

### ✅ 图3 & 图6：关键知识点汇总

#### 1. 发送窗口 ≠ 接收窗口

虽然发送方的窗口基于接收方的通知设置，但由于网络延迟和拥塞控制，两者**不一定相等**。

> 原因：

- 网络传输存在滞后；
- 发送方可根据自身拥塞状况主动减小发送窗口。

#### 2. 不按序到达的数据如何处理？

TCP **没有明确规定必须丢弃**，而是通常采取以下策略：

- 先临时缓存不按序到达的数据；
- 等到缺失的字节到达后，再按序交付给上层应用。

✅ 这样做可以提高网络资源利用率，避免重复重传。

#### 3. 累积确认 + 捎带确认机制

- TCP 使用 **累积确认**：确认号表示“期望收到的下一个字节序号”。
- 支持 **捎带确认**：当接收方有数据要发送时，可以把确认信息附在响应报文中一起发送，减少额外开销。

> ❗ 规定：确认不应过分推迟（不超过 0.5 秒）。若收到多个最大长度报文段，则每接一个就发一次确认（RFC 1122）。

#### 4. 全双工通信

- TCP 是全双工通信，每一方都有自己的：
  - 发送窗口（发送缓冲区）
  - 接收窗口（接收缓冲区）

> 因此讨论“窗口”时必须明确是哪一方的窗口。

------

## 🔍 总结要点（重点记忆）

| 内容             | 说明                                                |
| ---------------- | --------------------------------------------------- |
| **滑动窗口单位** | 字节级，不是报文段                                  |
| **窗口边界**     | 后沿（P1）前进 → 收到确认；前沿（P3）可能不动或收缩 |
| **三个指针**     | P1: 最小未确认；P2: 下一个发送；P3: 最大可发        |
| **确认号含义**   | 表示“期望收到的下一个字节序号”                      |
| **累积确认**     | 不要求逐个确认，只要顺序连续即可                    |
| **捎带确认**     | 减少确认开销，提高效率                              |
| **不按序处理**   | 缓存等待，之后按序交付                              |
| **全双工通信**   | 每一方都有发送/接收窗口                             |

- 即使后面来了 102~200，也不能跳过 101 直接确认 201。

##  一、核心主题：TCP 连接的建立

### ✅ TCP 是面向连接的协议

- 在传输数据前必须先建立连接。
- 每一次通信都分为三个阶段：
  1. **建立 TCP 连接**
  2. **数据传送**
  3. **释放 TCP 连接**

> 🎯 连接管理的目标：确保连接可靠建立和正常释放。

------

## 🔹 二、“三报文握手”详解

### 📌 基本流程（三次交互）

| 步骤 | 发送方 | 接收方 | 报文内容                       | 状态变化                                               |
| ---- | ------ | ------ | ------------------------------ | ------------------------------------------------------ |
| ①    | 客户端 | 服务器 | `SYN=1, seq=x`                 | 客户端从 CLOSED → SYN-SENT；服务器从 LISTEN → SYN-RCVD |
| ②    | 服务器 | 客户端 | `SYN=1, ACK=1, seq=y, ack=x+1` | 服务器进入 SYN-RCVD；客户端等待确认                    |
| ③    | 客户端 | 服务器 | `ACK=1, seq=x+1, ack=y+1`      | 双方均进入 ESTABLISHED，连接建立完成                   |

------

### 🔍 图解说明（逐图分析）

#### 🖼️ 第一张图：整体流程概览

- 左侧为 **TCP 客户端**，右侧为 **TCP 服务器**
- 时间轴 t 表示通信时间顺序
- 分为三个阶段：
  - “三报文握手” → 建立连接
  - 数据传送 → 实际通信
  - “四报文挥手” → 断开连接

> ✅ 关键点：**TCP 是面向连接的，每次通信都要先建连再传数**

------

#### 🖼️ 第二张图：第一步 —— 客户端发起请求

- 客户端主动打开连接，状态由 `CLOSED` → `SYN-SENT`
- 发送一个报文段：
  - `SYN = 1`：表示这是一个连接请求
  - `seq = x`：客户端选择的初始序号（随机值）
- 该报文不携带数据，但会消耗一个序号（x 被占用）

> 💡 注意：这是“同步已发送”状态，表示正在等待服务器响应。

------

#### 🖼️ 第三张图：第二步 —— 服务器响应

- 服务器收到 SYN 请求后，从 `LISTEN` → `SYN-RCVD`
- 回复一个报文段：
  - `SYN = 1`：表示服务器也想建立连接
  - `ACK = 1`：确认收到了客户端的 SYN
  - `seq = y`：服务器选择自己的初始序号
  - `ack = x + 1`：对客户端初始序号 x 的确认（期望下一个字节是 x+1）

> ✅ 此时双方都在协商连接参数，且各自发出了 SYN。

------

#### 🖼️ 第四张图：第三步 —— 客户端确认

- 客户端收到服务器的 SYN+ACK 后，发送最后一个确认报文：
  - `ACK = 1`：确认服务器的 SYN
  - `seq = x + 1`：上一次用了 x，现在用 x+1
  - `ack = y + 1`：期望服务器下次发 y+1 开始的数据
- 客户端状态变为 `ESTABLISHED`
- 服务器收到后也进入 `ESTABLISHED`

> ✅ 此时连接正式建立，可以开始数据传输。

------

## 🔹 三、典型例题解析（2011年题39）

> 【题目】主机甲向主机乙发送一个 `(SYN=1, seq=11220)` 的 TCP 段，期望建立连接。若主机乙接受请求，则它应发送什么？

### 📌 选项分析：

| 选项 | 内容                                 | 是否正确？ | 原因                                                    |
| ---- | ------------------------------------ | ---------- | ------------------------------------------------------- |
| A    | (SYN=0, ACK=0, seq=11221, ack=11221) | ❌          | 不是 SYN 报文，无法建立连接                             |
| B    | (SYN=1, ACK=1, seq=11220, ack=11220) | ❌          | `ack` 应为 `x+1=11221`，不能等于 x                      |
| C    | (SYN=1, ACK=1, seq=11221, ack=11221) | ✅          | 正确！SYN 和 ACK 都置 1，seq 是服务器选的 y，ack 是 x+1 |
| D    | (SYN=0, ACK=0, seq=11220, ack=11220) | ❌          | 无 SYN，无 ACK，不是有效响应                            |

### ✅ 正确答案：**C**

> 解析：

- 主机乙作为服务器，需回应：
  - `SYN=1`：表示自己也要建立连接
  - `ACK=1`：确认收到客户端的 SYN
  - `seq=y`：可任意选择（如 11221）
  - `ack=x+1=11221`：对客户端 seq=11220 的确认

## 🔹 四、关键知识点总结

| 内容                        | 说明                                                   |
| --------------------------- | ------------------------------------------------------ |
| **SYN 字段**                | 标志连接请求或响应，置 1 表示同步                      |
| **ACK 字段**                | 标志确认，置 1 表示有确认信息                          |
| **seq（序列号）**           | 发送方当前报文的第一个字节编号                         |
| **ack（确认号）**           | 期望接收的下一个字节编号，即“已收到的最后一个字节 + 1” |
| **SYN 报文是否消耗序号？**  | ✅ 是！即使不带数据，SYN=1 的报文也会消耗一个序号       |
| **普通 ACK 是否消耗序号？** | ❌ 否！只有 SYN 或 FIN 才会消耗序号                     |

> 💡 特别提醒：
>
> - `ack = 对方 seq + 1`
> - `seq = 自己选的初始值（或上次+1）`

## 🔹 五、常见问题答疑

### ❓ 为什么需要三次握手？

1. **防止旧的连接请求突然到达**（如网络延迟导致重复请求）
2. **双向同步初始化序列号**
3. **确保双方都能收发数据**

### ❓ 如果只用两次握手会怎样？

- 有可能出现“半连接”状态，导致资源浪费或错误连接。

### ❓ 为什么第三次握手不能省略？

- 第三次是客户端对服务器 SYN 的确认，否则服务器不知道客户端是否收到它的 SYN。

------

## 🔹 六、补充说明（红框注意）

> ⚠️ 注意事项：

1. **SYN=1 的报文段不能携带数据**，但要消耗一个序号。
2. **普通的 ACK 报文如果不携带数据，则不消耗序号**。

> 示例：

- 若客户端在第一次握手时携带数据，则 `seq=x` 后面跟着数据，此时 `seq` 就是第一个数据字节的序号。
- 若不携带数据，`seq=x` 仅用于同步，后续数据从 `x+1` 开始。

## ✅ 总结口诀（便于记忆）

> **“三报文握手，SYN起头，ACK回应，seq自定，ack加一。”**

- 第一步：我发 SYN=1, seq=x → 我想连接
- 第二步：你回 SYN=1, ACK=1, seq=y, ack=x+1 → 我也想连，我收到了你的请求
- 第三步：我回 ACK=1, seq=x+1, ack=y+1 → 我收到了你的响应，我们连上了！

### 图1：TCP 四报文挥手 —— 第一阶段

#### 🔹 主要内容：

- 展示了 TCP 连接释放的“四报文挥手”过程中的前两步。
- 客户端主动发起关闭连接请求（主动关闭），服务器被动响应（被动关闭）。

#### 🔹 状态变化与流程：

| 步骤 | 发送方 | 接收方 | 报文标志                     | 说明                                                         |
| ---- | ------ | ------ | ---------------------------- | ------------------------------------------------------------ |
| ①    | 客户端 | 服务器 | `FIN=1, ACK=1, seq=u, ack=v` | 客户端发送 FIN 报文，表示自己没有数据要发送了，进入 `FIN-WAIT-1` 状态。 |
| ②    | 服务器 | 客户端 | `ACK=1, seq=v, ack=u+1`      | 服务器收到 FIN 后，回复确认 ACK，此时客户端进入 `FIN-WAIT-2`，服务器进入 `CLOSE-WAIT`。 |

> ✅ 注意：此时连接处于半关闭状态，服务器仍可向客户端发送数据。

#### 🔹 关键点：

- `FIN=1` 表示发送方完成数据发送。
- `ACK=1` 是对之前报文的确认。
- 客户端进入 `FIN-WAIT-1` → `FIN-WAIT-2`。
- 服务器进入 `CLOSE-WAIT`，等待应用层关闭。

------

### 📌 图2：TCP 四报文挥手 —— 第二阶段（完整）

#### 🔹 延续上图，展示后两步：

| 步骤 | 发送方 | 接收方 | 报文标志                       | 说明                                                         |
| ---- | ------ | ------ | ------------------------------ | ------------------------------------------------------------ |
| ③    | 服务器 | 客户端 | `FIN=1, ACK=1, seq=w, ack=u+1` | 服务器也准备关闭连接，发送自己的 FIN 报文，进入 `LAST-ACK` 状态。 |
| ④    | 客户端 | 服务器 | `ACK=1, seq=u+1, ack=w+1`      | 客户端收到服务器的 FIN 后，发送最终确认，进入 `TIME-WAIT` 状态。服务器收到后进入 `CLOSED`。 |

#### 🔹 状态演变：

- 客户端：`ESTABLISHED` → `FIN-WAIT-1` → `FIN-WAIT-2` → `TIME-WAIT` → `CLOSED`
- 服务器：`ESTABLISHED` → `CLOSE-WAIT` → `LAST-ACK` → `CLOSED`

#### 🔹 特别注意：

- **TIME-WAIT 的作用**：等待可能迟到的报文（如第4个 ACK 丢失），确保对方能正确接收最后一个确认。
- 时间长度为 **2MSL（Maximum Segment Lifetime）**，通常建议为 2 分钟。

------

### 📌 图3：异常情况 —— 最终确认丢失

#### 🔹 情景模拟：

- 客户端发送最后一个 `ACK` 报文后，该报文在传输过程中 **丢失**（红色星号标注）。
- 服务器未收到这个确认，会重传 `FIN` 报文（超时重发机制）。
- 客户端再次收到 `FIN`，重新发送 `ACK`，直到成功为止。

#### 🔹 结果：

- 服务器最终收到 ACK 后进入 `CLOSED`。
- 客户端在 `TIME-WAIT` 状态等待 2MSL 后才关闭连接。

#### 🔹 设计目的：

- 防止旧连接的报文干扰新连接（比如同一个端口复用时）。
- 保证所有延迟报文都消失，避免混淆。

------

### 📌 图4：连接故障检测 —— 保活计时器（Keep-Alive）

#### 🔹 背景问题：

- 如果客户端突然崩溃或断网，服务器无法立即知道连接已中断。
- 需要一种机制来探测对端是否还存活。

#### 🔹 解决方案：保活计时器（Keep-Alive Timer）

- 当服务器每收到一次客户端的数据，就会重启一个 **2小时** 的保活计时器。
- 若计时器到期仍未收到数据，则开始发送 **探测报文段（Keep-Alive Probe）**。
- 初始间隔为 75 秒，共发送 10 次。
- 若 10 次都没有回应，则认为客户端主机出故障，关闭连接。

#### 🔹 关键参数：

- **保活计时器周期**：2 小时
- **探测间隔**：75 秒
- **最大探测次数**：10 次
- **标准参考**：RFC 793

#### 🔹 优点：

- 可以及时发现对端失效，释放资源。
- 减少无效连接占用系统资源。

------

### ✅ 总结：TCP 连接释放的核心要点

| 内容                 | 说明                                                         |
| -------------------- | ------------------------------------------------------------ |
| **四报文挥手**       | 主动关闭方先发 FIN，被动方回 ACK；再由被动方发 FIN，主动方回 ACK。 |
| **状态变迁**         | 客户端：ESTABLISHED → FIN-WAIT-1 → FIN-WAIT-2 → TIME-WAIT → CLOSED 服务器：ESTABLISHED → CLOSE-WAIT → LAST-ACK → CLOSED |
| **TIME-WAIT 的意义** | 等待 2MSL 时间，防止旧报文干扰；确保连接彻底释放。           |
| **保活机制**         | 用于检测长时间无数据传输的连接是否正常，避免“僵尸连接”。     |

2. **理解 MSL 和 2MSL**：为什么需要等这么长时间？是为了让网络中所有可能存在的旧报文都过期。

4. **实际应用**：Web 服务、数据库连接池等都会使用这些机制来管理长连接。

## 总体结构：TCP 首部组成

TCP 报文段由两部分构成：

1. **首部（Header）**
2. **数据载荷（Data Payload）**

### ✅ 首部分为两部分：

| 类型     | 字节数       | 说明                                           |
| -------- | ------------ | ---------------------------------------------- |
| 固定首部 | 20 字节      | 必须包含的基本信息                             |
| 扩展首部 | 最大 40 字节 | 可选字段，用于增强功能（如时间戳、窗口缩放等） |

> 🔹 总长度：**20 ~ 60 字节**

------

## 🔍 各字段详解（按顺序）

### 1️⃣ 源端口（Source Port）—— 16 比特

- 作用：标识发送该 TCP 报文段的应用进程。
- 示例：客户端浏览器使用随机端口（如 49152），服务器使用固定端口（如 80）。
- 协议中称为“源端口号”，用于返回响应时定位原应用。

> 💡 举个例子：当你访问 `www.hnust.cn`，你的浏览器可能用端口 49152 发送请求，服务器用端口 80 响应。

------

### 2️⃣ 目的端口（Destination Port）—— 16 比特

- 作用：标识接收该 TCP 报文段的应用进程。
- 示例：HTTP 服务通常监听 80 端口，HTTPS 是 443。
- 是决定报文交给哪个上层协议处理的关键依据。

> 🌐 图中示例：从网页到服务器，目的端口为 80，表示目标是 HTTP 服务。

------

### 3️⃣ 序号（Sequence Number, seq）—— 32 比特

- 作用：指出本 TCP 报文段数据载荷的第一个字节在整个数据流中的序号。
- 范围：`[0, 2³² - 1]`，循环使用（满后回绕到 0）。
- 实现可靠传输的基础：确保数据有序重组。

> 📌 示例图解：
>
> - 若序号 = 166，则第一个字节编号为 166。
> - 后续字节依次递增（167, 168...），直到下一个报文。

> ⚠️ 注意：序号不是报文编号，而是字节流的序号！

------

### 4️⃣ 确认号（Acknowledgment Number, ack）—— 32 比特

- 作用：期望收到的下一个字节的序号。
- 仅当 ACK=1 时有效。
- 表示“我已经收到了到序号 X 的所有数据，请继续发 X+1 开始的数据”。

> ✅ 示例：
>
> - 客户端发送：序号=201，长度=100 → 数据范围 [201, 300]
> - 服务器回复：确认号=301 → 表示已收到前 300 字节，期待 301 开始的新数据。

------

### 5️⃣ 数据偏移（Data Offset）—— 4 比特

- 也叫“首部长度”或“首部长度字段”
- 单位：**4 字节**（即以 4 字节为单位计算）
- 值范围：最小值 `0101₂ = 5`（对应 20 字节），最大值 `1111₂ = 15`（对应 60 字节）

> 🧮 计算公式：
>
> text
>
> 
>
> 
>
> 
>
> ```
> 1首部长度 = 数据偏移 × 4 字节
> ```

> ✅ 示例：
>
> - 数据偏移 = 0101（二进制）→ 5 × 4 = 20 字节（固定首部）
> - 数据偏移 = 1111 → 15 × 4 = 60 字节（含扩展选项）

------

### 6️⃣ 保留字段（Reserved）—— 6 比特

- 当前未使用，必须设为 0。
- 未来可能扩展用途。

------

### 7️⃣ 控制位（Flags）—— 6 个标志位（共 6 比特）

| 标志位 | 全称           | 作用                             |
| ------ | -------------- | -------------------------------- |
| URG    | Urgent         | 紧急指针有效（紧急数据）         |
| ACK    | Acknowledgment | 确认号有效（ACK=1）              |
| PSH    | Push           | 接收方应尽快交付给应用层         |
| RST    | Reset          | 重置连接（异常终止）             |
| SYN    | Synchronize    | 同步序号，用于建立连接           |
| FIN    | Finish         | 发送方完成数据发送，准备关闭连接 |

> 🔁 特别强调：
>
> - **SYN=1**：用于三次握手建立连接。
>   - 客户端发起：SYN=1, seq=x
>   - 服务器回应：SYN=1, ACK=1, seq=y, ack=x+1
>   - 客户端确认：ACK=1, seq=x+1, ack=y+1
> - **FIN=1**：用于四次挥手关闭连接。

------

### 8️⃣ 窗口（Window Size）—— 16 比特

- 单位：字节
- 表示发送方允许接收方最多还能发送多少字节的数据。
- 实现 **流量控制**（Flow Control）的核心机制。

> 🔄 工作原理：
>
> - 接收方通过窗口字段告诉发送方：“我还能接收这么多字节。”
> - 发送方根据此值调整自己的发送窗口大小。
> - 若窗口为 0，发送方暂停发送，等待对方通知窗口变大。

> 📌 示例：
>
> - 服务器发送：窗口=1000 → 客户端最多可发 1000 字节
> - 客户端发送完后，再等待新窗口更新

------

### 9️⃣ 校验和（Checksum）—— 16 比特

- 作用：检测 TCP 报文段在传输过程中是否出错。
- 检查范围包括：
  - TCP 首部
  - TCP 数据载荷
  - **伪首部（Pseudo Header）**：IP 层的部分信息（源 IP、目的 IP、协议号、TCP 长度）
- 在计算校验和时，需添加 12 字节的伪首部。

> ✅ 目的：提高可靠性，防止比特错误导致误判。

------

### 10️⃣ 紧急指针（Urgent Pointer）—— 16 比特

- 仅当 URG=1 时有效。
- 指向紧急数据的最后一个字节的序号。
- 用于实现“带外数据”传输（如中断信号）。

> 🛠️ 使用场景：
>
> - 用户按 Ctrl+C 中断程序，操作系统可通过紧急指针快速传递中断指令。

------

### 11️⃣ 选项（Options）—— 可变长度（最长 40 字节）

- 用于扩展 TCP 功能。
- 常见选项：
  - **MSS（Maximum Segment Size）**：最大报文段长度
  - **时间戳（Timestamp）**：用于精确测量 RTT 和防乱序
  - **窗口缩放（Window Scale）**：支持更大的窗口（>65535 字节）

> 🔧 例如：MSS=1460 表示最大数据载荷为 1460 字节（加上 20 字节 TCP 头，总包长 1480 字节）

------

### 12️⃣ 填充（Padding）

- 保证选项字段后的报文段边界对齐（通常是 4 字节边界）。
- 无实际含义，只是占位符。

------

> 场景：TCP 客户端与服务器通信

| 方向            | 报文           | 参数                                      |
| --------------- | -------------- | ----------------------------------------- |
| 客户端 → 服务器 | 第一个数据报文 | 序号=201，数据长度=100，确认号=800，ACK=1 |
| 服务器 → 客户端 | 回应报文       | 序号=800，数据长度=200，确认号=301，ACK=1 |

- 服务器希望客户端接下来发送序号为 301 的数据

> ✅ 这体现了 TCP 的 **全双工通信 + 流量控制 + 可靠传输** 特性。

### 🔹 图1：终止标志位 FIN —— “四报文挥手”释放连接

#### ✅ 内容要点：

- **FIN = 1**：表示发送方已经完成数据发送，请求关闭连接。
- 使用“**四报文挥手**”过程来安全释放连接。

#### 💡 四次挥手流程（图示）：

| 步骤 | 发送方          | 接收方                             | 含义                               |
| ---- | --------------- | ---------------------------------- | ---------------------------------- |
| 1    | 客户端 → 服务器 | `FIN=1, ACK=1`, 序号=u, 确认号=v   | 客户端通知：“我发完了，可以关了。” |
| 2    | 服务器 → 客户端 | `ACK=1`, 序号=v, 确认号=u+1        | 服务器确认收到客户端的关闭请求     |
| 3    | 服务器 → 客户端 | `FIN=1, ACK=1`, 序号=w, 确认号=u+1 | 服务器也准备关闭，通知客户端       |
| 4    | 客户端 → 服务器 | `ACK=1`, 序号=u+1, 确认号=w+1      | 客户端确认，连接正式断开           |

> ✅ 特点：
>
> - 双向关闭，保证双方都完成了数据发送。
> - 每个方向独立关闭，允许半关闭状态（如服务器仍可接收数据）。

> ⚠️ 注意：FIN 不一定携带数据，只是表示“不再发送”。

------

### 🔹 图2：复位标志位 RST —— 异常中断连接

#### ✅ 内容要点：

- **RST = 1**：表示 TCP 连接出现异常，必须立即终止连接。
- 用于以下情况：
  - 端口不存在（SYN 到非监听端口）
  - 连接已关闭但收到数据
  - 应用层崩溃或重启
  - 收到非法序号的数据包

#### 💡 示例场景：

text







```
1客户端发送 SYN 到一个未开启服务的端口 → 服务器返回 RST
```

> ❗ RST 是强制性的，不需要对方回应，直接终止连接。

> 📌 区别于 FIN： | 标志位 | 用途 | 是否需要协商 | |--------|------|--------------| | FIN    | 正常关闭 | 需要四次挥手 | | RST    | 异常终止 | 单方面强制 |

------

### 🔹 图3：紧急标志位 URG 和紧急指针

#### ✅ 内容要点：

- **URG = 1**：表示紧急指针字段有效。
- **紧急指针**：占 16 比特，指出紧急数据在报文段中的长度（以字节为单位）。

#### 💡 工作机制：

- 当有紧急数据时（如 Ctrl+C 中断信号），可将该数据插入到发送缓存最前面，并立即封装成 TCP 报文段。
- 接收方收到后，根据紧急指针快速提取紧急数据，无需等待普通数据处理完毕。
- 紧急数据之后仍是正常数据。

> 🧩 示例：

text







```
1数据载荷: [紧急数据] + [普通数据]
2紧急指针指向：紧急数据的最后一个字节位置
```

> ⚠️ 注意：

- 紧急数据不占用序列号空间（不会影响主数据流顺序）
- 实际应用较少，现代操作系统多用其他方式实现优先级通信

------

### 🔹 图4：选项字段（Options）—— 扩展功能支持

#### ✅ 内容要点：

- 位于扩展首部，长度可变（最大 40 字节）
- 主要包括三种常见选项：

| 选项                             | 功能                    | 说明                                                         |
| -------------------------------- | ----------------------- | ------------------------------------------------------------ |
| **MSS（Maximum Segment Size）**  | 最大报文段长度          | 表示 TCP 数据载荷的最大长度，通常由 MTU 减去 IP 和 TCP 头得出（如 1460 字节） |
| **窗口扩大选项（Window Scale）** | 扩大窗口大小            | 允许窗口值超过 65535 字节（原始 16 位限制），提高吞吐率      |
| **时间戳选项（Timestamp）**      | 计算 RTT & 防止序号绕回 |                                                              |

- 用于精确测量往返时间（RTT）
- 防止序号绕回问题（PAWS：Protect Against Wrapped Sequence numbers）|

> 📌 PAWS 原理：
>
> - 序号每 2³² 字节循环一次（约 4GB）
> - 如果两个不同连接使用相同序号，可能造成混淆
> - 时间戳帮助区分是否是旧连接重传

> ✅ 小结：选项字段让 TCP 更灵活、高效、可靠。

------

### 🔹 图5：填充（Padding）

#### ✅ 内容要点：

- **作用**：确保整个 TCP 首部长度能被 4 字节整除。
- **原因**：因为“数据偏移”字段是以 4 字节为单位的（即首部长必须是 4 字节倍数）。
- 若选项部分长度不是 4 的倍数，则添加填充字节补足。

> 🧮 示例：
>
> - 固定首部：20 字节
> - 选项：12 字节 → 总长 32 字节（可被 4 整除）→ 无需填充
> - 选项：13 字节 → 总长 33 字节 → 添加 3 字节填充 → 成为 36 字节

> ✅ 填充无实际含义，仅为了对齐。

------

### 🔹 图6：TCP 的面向字节流模型

#### ✅ 内容要点：

- TCP 是 **面向字节流** 的协议，而不是面向消息的。
- 发送方从应用进程读取字节流，将其分段打包成 TCP 报文段。
- 接收方将多个报文段重新组合成连续字节流交给上层应用。

#### 💡 图解说明：

text







```
1发送方：[21][20][19]... → TCP 分段 → [18][17][16][15][14] + TCP头
2        ↓
3接收方：[5][4]... ← 组合 → [13][12][11] + TCP头
```

> 🔄 关键特性：

- 不保证每个报文段大小一致
- 不保留边界（不像 UDP）
- 序列号按字节编号，而非报文编号

> ✅ 优势：

- 提高传输效率（动态分段）
- 支持流式数据（如视频、文件传输）

| 填充           | ⭐⭐       | 为什么需要？因数据偏移是4字节单位         |
| 面向字节流     | ⭐⭐⭐⭐     | 与 UDP 的面向报文对比                     |

------

## ✅ 总结一句话：

> **TCP 首部通过精心设计的字段实现了可靠传输、流量控制、连接管理与错误检测，其核心在于“面向字节流”的设计理念和丰富的控制机制。**

## 🎯 本节主题：两种网络通信模式对比

> **客户端/服务器（C/S） vs 对等（P2P）**

这是现代互联网应用的基础架构模型，决定了服务如何组织、资源如何分配、性能如何扩展。

------

# 🔹 图1：客户/服务器方式（Client/Server, C/S）

### ✅ 核心定义：

- **客户（Client）**：主动发起请求的服务请求方。
- **服务器（Server）**：被动等待并响应请求的服务提供方。

### 📌 关键特点：

| 特性               | 说明                                                      |
| ------------------ | --------------------------------------------------------- |
| **角色固定**       | 客户是请求者，服务器是提供者，分工明确                    |
| **服务器常驻运行** | 始终处于监听状态，等待连接（如 HTTP 默认端口 80）         |
| **IP 和端口固定**  | 服务器有固定的 IP 地址和端口号（例如 `www.baidu.com:80`） |
| **进程关系**       | 描述的是两个应用进程之间的服务与被服务关系                |

### 🧩 工作流程图解（图中 A → B）：

1. **① 请求服务**：客户 A 运行客户程序，向服务器 B 发送请求（如访问网页）
2. **② 提供服务**：服务器 B 接收请求后处理，并返回响应数据
3. **网络核心**：中间由路由器、交换机等构成的网络基础设施承载通信

> 💡 示例：
>
> - 浏览器（客户） → 访问百度网站（服务器）
> - QQ 邮箱登录 → 邮件服务器
> - FTP 下载文件 → 文件服务器

### ⚠️ 缺点：

- **服务集中型**：所有用户都依赖少数几个服务器
- **易成为瓶颈**：当用户量激增时，服务器可能“扛不住”
- **单点故障风险**：若服务器宕机，整个服务中断

> ✅ 解决方案：使用 **计算机群集（Cluster）或虚拟服务器** 来提升性能和可靠性。

------

# 🔹 图2 & 图3：对等（Peer-to-Peer, P2P）方式

### ✅ 核心定义：

> 在 P2P 模式中，**没有固定的客户与服务器之分**，每个节点既是服务请求者，也是服务提供者。

### 📌 关键特点：

| 特性           | 说明                                           |
| -------------- | ---------------------------------------------- |
| **角色对等**   | 所有参与节点地位相同，可互相提供服务           |
| **直接通信**   | 节点之间可以直接通信，无需经过中心服务器       |
| **服务分散型** | 服务不集中在少数服务器上，而是分布在整个网络中 |
| **去中心化**   | 不依赖单一中心控制点，抗单点故障能力强         |

### 🧩 工作流程图解（图中 E ↔ F, C ↔ D）：

- 多个终端（E, F, C, D）运行 P2P 程序
- 直接建立连接进行数据交换（红色箭头表示双向通信）
- 网络核心仅负责转发，不参与内容分发

> 💡 示例：
>
> - **BitTorrent 下载**：你下载文件的同时也在上传已下载的部分给其他人
> - **迅雷、电驴（eMule）**
> - **即时通讯软件**：如早期的 Skype（部分功能基于 P2P）
> - **区块链网络**：比特币节点之间互为对等

### ✅ 突出优势：

#### 1. **可扩展性强**

> 每增加一个对等方，不仅增加了用户数量，还**同时增加了服务能力**！
> → 系统规模越大，整体性能越强（正反馈效应）

> 🌐 类比：一个人在看视频，另一个人也看同样的视频 → 两人可以共享缓存，减轻源服务器压力

#### 2. **成本低**

> 不需要昂贵的专用服务器集群和带宽资源
> → 用户自己贡献计算能力和上传带宽，服务商节省大量成本

#### 3. **高容错性**

> 即使某个节点退出，其他节点仍能继续通信，不会影响全局服务

------

# 🔹 图4：C/S 与 P2P 的对比总结（双栏对比表）

| 项目           | 客户/服务器（C/S）                  | 对等（P2P）                             |
| -------------- | ----------------------------------- | --------------------------------------- |
| **角色划分**   | 固定：客户（请求）、服务器（提供）  | 动态：每个节点既是请求者又是提供者      |
| **服务集中度** | 服务集中型 → 少数服务器承担全部负载 | 服务分散型 → 分布在大量普通计算机中     |
| **典型应用**   | WWW、电子邮件、FTP、DNS             | BT下载、P2P流媒体、即时通信、分布式存储 |
| **扩展能力**   | 易出现瓶颈，需集群支持              | 可扩展性强，随节点增加而增强            |
| **成本结构**   | 需要大型服务器设施和宽带            | 成本低，利用用户终端资源                |
| **稳定性**     | 易受服务器故障影响                  | 抗单点故障，更稳定                      |
| **部署复杂度** | 较简单，易于管理                    | 较复杂，需协调机制（如DHT）             |

## 核心知识点提炼

### ✅ C/S 方式适合什么场景？

- **专业服务**：银行系统、企业邮件系统、在线购物平台
- **高安全性要求**：便于统一管理和监控
- **高质量服务保障**：服务器可配置高性能硬件

### ✅ P2P 方式适合什么场景？

- **大规模资源共享**：文件下载、视频分发
- **低成本运营**：如直播平台引入 P2P 加速（如抖音、快手）
- **去中心化需求**：区块链、匿名通信、抗审查网络

------

## 🔄 实际融合趋势：混合模式（Hybrid Model）

现实中很多系统采用 **C/S + P2P 混合架构**：

> 🌐 例如：**YouTube 视频分发**

- 用户访问视频 → 先从 CDN（C/S 模式）获取
- 同时，如果启用 P2P 加速，则会从其他观看同一视频的用户那里下载片段（P2P 模式）

> 🛠️ 如今流行的直播平台（B站、斗鱼）也普遍采用 **边缘节点 + P2P 分发** 来降低带宽成本。

------

## 📘 总结一句话：

> **C/S 是传统、成熟、可控的集中式架构；P2P 是新兴、灵活、高效的去中心化架构。两者各有优劣，未来的发展方向是融合共存。**



### 一、DHCP 的核心作用

#### ✅ 主要功能：

- **自动分配 IP 地址及其他网络参数**，实现“即插即用”。
- 减少手动配置错误，提高网络管理效率。

#### 🔧 可配置的信息包括：

- **IP 地址**：如 `192.168.0.1 ~ 192.168.0.251`
- **子网掩码**：`255.255.255.0`
- **默认网关**：`192.168.0.254`
- **DNS 服务器**：`192.168.0.253`

> 示例中使用的是私有地址段 `192.168.0.x`，属于局域网常用范围。

------

### 二、DHCP 的工作过程（四步握手）

DHCP 使用 **UDP 协议** 进行通信，客户端使用端口 **68**，服务器使用端口 **67**。

#### 🔄 四个关键报文（DORA 模型）：

| 报文              | 含义                                      | 发送方 | 目标                                 |
| ----------------- | ----------------------------------------- | ------ | ------------------------------------ |
| **DHCP DISCOVER** | 客户端广播寻找可用的 DHCP 服务器          | 客户端 | 所有设备（广播地址 255.255.255.255） |
| **DHCP OFFER**    | 服务器响应，提供一个 IP 地址租约          | 服务器 | 客户端（广播）                       |
| **DHCP REQUEST**  | 客户端选择某个服务器提供的 IP，并请求确认 | 客户端 | 所选服务器（单播或广播）             |
| **DHCP ACK**      | 服务器确认租约成功                        | 服务器 | 客户端                               |

> ⚠️ 注意：在没有获得 IP 前，客户端源 IP 为 `0.0.0.0`。

------

### 三、具体交互流程详解

#### 1. **DHCP DISCOVER**

- 客户端开机后广播 `DHCP DISCOVER`。
- 源 IP：`0.0.0.0`，目的 IP：`255.255.255.255`
- 被所有 DHCP 服务器接收（图中有两个服务器：1 和 2）

#### 2. **DHCP OFFER**

- 多个服务器可同时回复 `OFFER`，包含：
  - 可用 IP 地址
  - 子网掩码
  - 租期
  - 默认网关
  - DNS 服务器
- 服务器会先通过 **ARP** 检查所选 IP 是否已被占用（防止冲突）

#### 3. **DHCP REQUEST**

- 客户端从多个 `OFFER` 中选择一个（通常按优先级或响应时间）
- 广播发送 `REQUEST` 给选定的服务器，表示：“我接受你给的这个 IP”
- 包含：
  - 事务 ID
  - MAC 地址
  - 接受的 IP
  - 服务器 IP

#### 4. **DHCP ACK / NACK**

- 若服务器同意，则返回 `ACK`，正式确认租约。
- 若拒绝（例如该 IP 已被释放），则返回 `NACK`，客户端需重新发起 `DISCOVER`。

------

### 四、IP 地址冲突检测机制

✅ **使用 ARP 检测 IP 是否已被占用：**

- 客户端收到 `ACK` 后，会发送一个 **ARP 请求** 来探测目标 IP 是否已被其他主机使用。
- 若有回应 → 表示 IP 被占 → 发送 `DHCP DECLINE` 撤销租约，重新申请。
- 若无回应 → 可安全使用该 IP。

> 💡 这是保障网络稳定的重要机制。

------

### 五、IP 租期管理（续租机制）

#### ⏳ 租期到期前的行为：

| 时间点               | 行动                                                |
| -------------------- | --------------------------------------------------- |
| **租期 50% 时**      | 客户端尝试向原服务器发送 `DHCP REQUEST` 请求续租    |
| **若成功**           | 收到 `ACK`，获得新租期                              |
| **若失败（无响应）** | 在租期 87.5% 时再次尝试                             |
| **仍失败**           | 到达租期结束 → 停止使用当前 IP，重新发送 `DISCOVER` |

> ❗ 若租期过期且未续租，IP 将被释放回池中供他人使用。

------

### 六、DHCP 中继代理（Relay Agent）

#### 🌐 实际部署问题：

- 不可能每个子网都部署一台 DHCP 服务器。
- 路由器可以作为 **DHCP 中继代理**。

#### 🔁 工作原理：

- 客户端发送 `DHCP DISCOVER`（广播）→ 路由器接收到
- 路由器将广播转为 **单播**，转发至远端 DHCP 服务器
- 服务器回复后，路由器再将响应传回客户端

> ✅ 优点：减少服务器数量，简化管理；支持跨子网动态配置。

------

### 七、关键知识点总结

| 知识点       | 内容                                         |
| ------------ | -------------------------------------------- |
| **协议类型** | 应用层协议，基于 UDP                         |
| **端口号**   | 客户端 68，服务器 67                         |
| **初始 IP**  | `0.0.0.0`（未获取前）                        |
| **报文类型** | DISCOVER, OFFER, REQUEST, ACK, NACK, RELEASE |
| **ARP 检测** | 防止 IP 冲突                                 |
| **租期策略** | 50% 和 87.5% 触发续租                        |
| **中继代理** | 路由器可代理转发 DHCP 报文                   |

### 九、常见疑问解答（基于图片内容）

❓ **为什么 DHCP 使用广播？**

> 因为客户机不知道任何服务器地址，必须通过广播找到可用的 DHCP 服务器。

❓ **客户端如何决定选哪个 Offer？**

> 一般根据响应速度、优先级或预设规则（如本地服务器优先）。

❓ **如果两个服务器都 offer 同一个 IP？**

> 会导致冲突，因此服务器应在分配前用 ARP 检查可用性。

❓ **DHCP RELEASE 是做什么的？**

> 主动释放 IP 地址，比如用户主动断开连接，通知服务器回收资源。

## 一、核心问题引入：为什么不能只用一台 DNS 服务器？

### ❓ 提问：“因特网是否可以只使用一台 DNS 服务器？”

#### ✅ 答案：**不可以！**

> **原因如下：**

- 因特网规模巨大，单台服务器会因超负荷而崩溃。
- 若该服务器故障 → 整个互联网将瘫痪（单点故障）。

#### ✅ 解决方案：

1983 年起，采用 **层次树状结构的命名体系 + 分布式 DNS 系统**，实现：

- 高可用性
- 负载均衡
- 故障隔离

> 🔍 **关键思想**：分布式、分层管理、本地解析优先。

## 🌲 二、域名结构：层次树状结构

### ✅ 结构形式：

text







```
1... .三级域名 .二级域名 .顶级域名
```

> 示例：`nic.hnust.edu.cn`

| 层级     | 名称    | 含义                                 |
| -------- | ------- | ------------------------------------ |
| 四级域名 | `nic`   | 湖南科技大学网络信息中心（自行管理） |
| 三级域名 | `hnust` | 湖南科技大学                         |
| 二级域名 | `edu`   | 教育机构（中国教育网）               |
| 顶级域名 | `cn`    | 中国国家代码                         |

### ✅ 规则说明：

- 每级域名由英文字母/数字组成，不超过 63 字符，不区分大小写。
- 完整域名 ≤ 255 字符。
- 最低级别在左，最高级别（顶级域）在右。
- 不规定各级含义，但有约定俗成的命名规范。

> 💡 类比：外国人姓名顺序 —— “姓.名”，如 `Zhang.San`。

## 🏷️ 三、顶级域名 TLD（Top Level Domain）

分为三大类：

| 类型                  | 说明                                | 示例                                                         |
| --------------------- | ----------------------------------- | ------------------------------------------------------------ |
| **国家顶级域名 nTLD** | ISO 3166 标准，代表国家或地区       | `.cn`（中国）、`.us`（美国）、`.uk`（英国）                  |
| **通用顶级域名 gTLD** | 表示组织类型                        | `.com`（公司企业）、`.net`（网络服务）、`.org`（非营利组织）、`.edu`（美国教育）、`.gov`（政府部门）、`.mil`（军事） |
| **反向域 arpa**       | 用于 IP 地址反向解析（如 PTR 记录） | `in-addr.arpa`                                               |

### 🔍 特别注意：

> 在我国 `.cn` 下也有一个名为 `.com` 的**二级域名**，它不是国际通用的 `.com`，而是中国的商业类二级域名。

| 我国二级域名分类 | 示例                                                  | 含义                             |
| ---------------- | ----------------------------------------------------- | -------------------------------- |
| **类别域名**     | `.ac`, `.com`, `.edu`, `.gov`, `.net`, `.mil`, `.org` | 分别对应科研、企业、教育、政府等 |
| **行政区域名**   | `.bj`（北京）、`.sh`（上海）、`.js`（江苏）           | 代表省级行政单位                 |

> ⚠️ 注意区分：
>
> - `.com` 是全球通用的企业域名
> - `.cn.com` 是中国境内的企业域名（即 `.cn` 下的 `.com`）

text







```
1        树根
2       /     \
3      /       \
4   net ...    com   org   int   edu   gov   mil   cn   jp   uk   us
5         \     /       \
6          \   /         \
7           cctv ... ibm  ti
8                   |
9                  mail

```

### ✅ 层级解释：

- **树根**：无名称，是整个域名空间的起点。
- **顶级域名**：如 `com`, `cn`, `edu` 等。
- **二级域名**：如 `cctv.com`, `ibm.com`, `bj.cn`, `edu.cn`。
- **三级域名**：如 `mail.cctv.com`, `tsinghua.edu.cn`。
- **四级域名**：如 `nic.hnust.edu.cn`, `lib.tsinghua.edu.cn`。

> 💡 **重要提示**：
>
> - 域名只是逻辑概念，不代表物理位置。
> - 这种分层结构便于维护唯一性和高效查询。

## 🧩 五、DNS 服务器类型（四种）

| 类型               | 功能                                                         | 说明                                               |
| ------------------ | ------------------------------------------------------------ | -------------------------------------------------- |
| **根域名服务器**   | 全球共 13 组（实际多台服务器构成集群），知道所有顶级域名服务器的 IP 地址 | 不直接解析域名，而是返回“负责该顶级域的服务器地址” |
| **顶级域名服务器** | 管理某个顶级域下的所有二级域名                               | 如 `dns.com` 管理所有 `.com` 域名                  |
| **权限域名服务器** | 管理某具体区域的域名（如 `abc.com`）                         | 每个主机必须在此注册其域名和 IP 映射关系           |
| **本地域名服务器** | 用户主机默认配置的 DNS 服务器，通常由 ISP 或学校提供         | 起代理作用，转发请求到上级服务器                   |

> ✅ 查询路径：
> 用户 → 本地域名服务器 → 根 → 顶级 → 权限 → 返回结果

## 🔍 六、域名解析方式：递归 vs 迭代查询

### 1️⃣ **递归查询（Recursive Query）**

- 客户端要求服务器“必须给我最终答案”。
- 所有中间步骤由服务器完成。
- 适用于客户端对响应时间敏感的情况。

> ✅ 图解流程：

text







```
1(1) m.xyz.com → dns.xyz.com (递归)
2(2) dns.xyz.com → 根服务器 (递归)
3(3) 根 → 顶级域名服务器 dns.com (递归)
4(4) dns.com → 权限服务器 dns.abc.com (递归)
5(5) dns.abc.com → 返回 y.abc.com 的 IP
6(6)-(8) 逐级返回给客户端

```

### 2️⃣ **迭代查询（Iterative Query）**

- 服务器不负责查完，只告诉“下一个该问谁”。
- 客户端自己继续询问下一级。
- 更节省资源，减轻服务器负担。

> ✅ 图解流程：

text







```
1(1) m.xyz.com → dns.xyz.com (递归)
2(2) dns.xyz.com → 根服务器 (迭代)
3(3) 根 → 返回 dns.com 的地址
4(4) dns.xyz.com → dns.com (迭代)
5(5) dns.com → 返回 dns.abc.com 的地址
6(6) dns.xyz.com → dns.abc.com (迭代)
7(7) dns.abc.com → 返回 y.abc.com 的 IP
8(8) 返回给客户端

```

> 🎯 实际中采用混合模式：
>
> - 主机到本地服务器是 **递归查询**
> - 本地服务器到其他服务器是 **迭代查询**

## 🚀 七、高速缓存（Caching）机制

### ✅ 目的：

- 提高查询效率
- 减轻根域名服务器压力
- 减少 DNS 报文数量

### ✅ 缓存位置：

- **本地域名服务器**：保存最近查询过的域名映射
- **用户主机**：操作系统也会缓存（如 Windows 的 DNS Client 服务）

### ✅ 缓存策略：

- 每条记录设置 **TTL（Time To Live）**，如 2 天
- 超过 TTL 后自动删除，避免陈旧数据

> 💡 示例：你访问 `www.baidu.com` 一次后，下次可能直接从缓存获取，无需再查询。

## 🧪 八、典型习题解析（2016年真题）

> **题目**：假设所有域名服务器均采用迭代查询方式，当 H4 访问 `www.abc.xyz.com` 时，域名服务器 201.1.1.1 可能发出 DNS 查询的最少和最多次数分别是？

### ✅ 已知条件：

- 所有主机默认域名服务器均为 `201.1.1.1`
- 使用迭代查询
- H4 的 DNS 高速缓存中可能已有记录

### ✅ 分析过程：

#### 最少次数：**0 次**

- 如果 H4 的本地 DNS 缓存中已有 `www.abc.xyz.com` 的记录 → 不需要查询任何服务器

#### 最多次数：**4 次**

- 本地服务器依次向以下服务器发起查询：
  1. 根域名服务器
  2. `.com` 顶级域名服务器
  3. `xyz.com` 权限域名服务器
  4. `abc.xyz.com` 权限域名服务器

> ✅ 正确答案：**C. 0, 4**

## 一、FTP 概述：什么是文件传送协议？

### ✅ 定义：

> **FTP（File Transfer Protocol）** 是因特网上使用最广泛的文件传送协议，用于在两台计算机之间通过网络传输文件。

### ✅ 核心功能：

- 实现跨平台、跨网络的文件上传与下载。
- 支持交互式访问，用户可指定文件类型和权限。
- 屏蔽操作系统差异，适用于异构网络环境。

### ✅ 历史地位：

- 在互联网早期，FTP 占据了约 **1/3 的通信量**。
- 直到 **1995 年万维网（WWW）出现后**，其流量才被超越。
- 尽管如今已被 HTTP 等协议部分替代，但 FTP 仍广泛应用于批量文件传输场景。

------

## 💡 二、FTP 的主要特点

| 特点                   | 说明                                                         |
| ---------------------- | ------------------------------------------------------------ |
| 🔹 **交互式访问**       | 用户可通过命令行或图形界面控制文件操作（如 `get`, `put`, `ls`）。 |
| 🔹 **支持多种文件格式** | 可选择 ASCII 或二进制模式传输： - ASCII：文本文件（自动处理换行符） - 二进制：图像、音频、压缩包等非文本文件 |
| 🔹 **权限控制**         | 文件具有存取权限，访问需经过身份验证（用户名+密码）。        |
| 🔹 **屏蔽系统差异**     | 不同操作系统之间的文件传输无需关心底层细节。                 |

> ⚠️ 注意：FTP 是一种 **应用层协议**，运行在 TCP 之上，提供可靠的数据传输服务。

------

## 🌐 三、FTP 的典型应用场景

### ✅ 应用 1：**计算机间文件传输**

- 例如：学校老师将作业提交到 FTP 服务器，学生从客户端下载。

- 图中显示了一个典型的 FTP 站点界面：

  text

  

  

  

  ```
  1ftp://192.168.124.16
  
  ```

  - 显示文件列表（`.mp3`, `.pdf`, `.txt`, `.zip`）
  - 支持右键下载、上传、删除等操作

### ✅ 应用 2：**网站内容批量上传**

- 网站开发者使用 FTP 工具（如 FileZilla、Xftp）将网页、图片、脚本等大量文件上传至 Web 服务器。
- 这是构建静态网站的基础方式之一。

> 💡 提示：现代云存储（如阿里云 OSS、腾讯云 COS）已逐渐取代传统 FTP，但在企业内部网、开发部署中仍常见。

## 🔗 四、FTP 的基本工作原理：双连接机制

FTP 使用 **两个并行的 TCP 连接** 来完成通信：

| 类型         | 用途                                      | 端口号                                    | 是否长期保持         |
| ------------ | ----------------------------------------- | ----------------------------------------- | -------------------- |
| **控制连接** | 传递 FTP 命令（如 `list`, `get`, `quit`） | 默认 21                                   | 整个会话期间一直打开 |
| **数据连接** | 传输实际文件内容                          | 默认 20（主动模式）或随机端口（被动模式） | 每次传输完成后关闭   |

> 🧩 关键理解：
>
> - 控制连接负责“说什么”，数据连接负责“传什么”。

------

## 🔄 五、FTP 的两种工作模式：主动 vs 被动

### 1️⃣ **主动模式（Active Mode）**

#### 🔹 流程：

1. 客户端发起控制连接 → 使用 **任意临时端口** → 连接到服务器 **21 端口**
2. 当需要传输数据时，客户端通知服务器：“我准备好了，请连接我的另一个临时端口”
3. 服务器主动发起数据连接 → 使用 **20 端口** → 连接到客户端的临时端口

#### 🔹 特点：

- 服务器主动连接客户端
- 需要客户端开放端口接收连接（防火墙可能阻止）

> ❌ 缺点：若客户端处于 NAT 后面或有防火墙，可能导致连接失败。

------

### 2️⃣ **被动模式（Passive Mode）**

#### 🔹 流程：

1. 控制连接同上（客户端 → 服务器 21 端口）
2. 数据传输时，服务器告知客户端：“我打开了一个临时端口，你来连我吧”
3. 客户端主动发起数据连接 → 连接到服务器的临时端口

#### 🔹 特点：

- 客户端主动连接服务器
- 更适合穿越防火墙和 NAT 设备

> ✅ 优点：适用于大多数现代网络环境，尤其是家用路由器后的设备。

## 📝 六、经典真题解析

### ✅ 【2009年 题40】

> FTP 客户和服务器间传递 FTP 命令时，使用的连接是？
> A. 建立在 TCP 之上的控制连接
> B. 建立在 TCP 之上的数据连接
> C. 建立在 UDP 之上的控制连接
> D. 建立在 UDP 之上的数据连接

#### ✅ 正确答案：**A**

> 🔍 解析：
>
> - FTP 使用两个 TCP 连接
> - **控制连接**：用于发送命令（如 `get file.txt`），在整个会话中持续存在
> - **数据连接**：仅在传输文件时建立，传输完毕即关闭
> - 所以，**命令通过控制连接传输，该连接基于 TCP**

------

### ✅ 【2017年 题40】

> 下列关于 FTP 协议的叙述中，错误的是？
> A. 数据连接在每次数据传输完毕后就关闭
> B. 控制连接在整个会话期间保持打开状态
> C. 服务器与客户端的 TCP 20 端口建立数据连接
> D. 客户端与服务器的 TCP 21 端口建立控制连接

#### ✅ 正确答案：**C**

> 🔍 解析：
>
> - A 正确：数据连接是按需建立、用完即关
> - B 正确：控制连接维持整个会话
> - D 正确：控制连接使用 21 端口（服务器）
> - **C 错误**：虽然默认情况下服务器使用 **20 端口** 发起数据连接（主动模式），但是否使用 20 端口取决于传输模式：
>   - 主动模式：服务器使用 20 端口
>   - 被动模式：服务器使用临时端口，由客户端协商决定
>   - 所以不能说“一定使用 20 端口”

> ⚠️ 关键点：**TCP 20 端口不是固定的，仅在主动模式下使用；被动模式下不固定。**
